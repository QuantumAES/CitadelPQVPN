# Выпуск релиза и настройка CI/CD

Сборка, тесты и публикация идут на **двух self-hosted раннерах** — linux и windows. Здесь: что
должно быть на раннерах, какие нужны секреты, как выпускается релиз и почему сделано именно так.

## 1. Что происходит автоматически

| Workflow | Когда | Раннер | Что делает |
|---|---|---|---|
| `ci.yml` → `rust` | push в `main`/`dev`, PR | linux | `cargo clippy -D warnings` + `cargo test` по воркспейсу |
| `ci.yml` → `app` | push в `main`/`dev`, PR | linux | `flutter analyze`, инварианты JNI и иконок, кросс-чек `windows-gnu` |
| `ci.yml` → `e2e` | push, вручную | linux | оба контейнерных харнеса (туннель и консольный клиент) |
| `windows.yml` → `rust` | push, PR по путям | windows | тесты/сборка/clippy под MSVC |
| `windows.yml` → `installer` | push, вручную | windows | установщик Inno (неподписанный) — артефактом |
| `release.yml` | тег `v*`, вручную | оба | гейт → установщик → сборка всего → подпись → GitHub Release |

### Безопасность прогонов на своей машине

Раннер исполняет код из репозитория на вашем железе, поэтому job'ы **не запускаются для pull
request'ов из форков** — в каждом job'е стоит условие на `pull_request.head.repo`. Без него
любой посторонний, открывший PR, выполнил бы у вас произвольный скрипт.

Это условие — не вся защита. Включите в настройках репозитория
**Settings → Actions → General → Fork pull request workflows** режим одобрения мейнтейнером, а
раннеры не давайте публичным форкам (GitHub об этом предупреждает отдельно). Проверять PR из
форка стоит либо на GitHub-hosted раннере, либо после ревью кода — глазами.

Workflow'ы ничего не устанавливают на раннер и не меняют его глобально: они проверяют наличие
инструментов и падают с внятным сообщением. Машина остаётся вашей.

## 2. Что должно быть на раннерах

### Linux (метки `self-hosted, linux, x64`)

- **rustup stable 1.96+** — системный `cargo` 1.85 не соберёт зависимости; workflow проверяет
  версию и падает, если PATH ведёт не туда;
- `cmake`, `clang` — для `aws-lc-rs`;
- **Flutter stable 3.44+**;
- **Android SDK + NDK 27 + cargo-ndk**, `apksigner` в `PATH` (проверка подписи APK);
- **docker** + compose v2, загруженный модуль `tun` (`/dev/net/tun` должен существовать);
- `minisign`, `zstd`, `gh` (авторизация не нужна — используется `GITHUB_TOKEN`);
- **секрет minisign** — `~/.citadel/release/citadel-release.key` (или `CITADEL_RELEASE_KEY_DIR`).

Всё это ставит `tools/setup-dev-env.sh`. Раннер должен видеть `~/.cargo/bin` и `~/flutter/bin` —
workflow добавляет их в PATH сам, но домашний каталог должен быть тем же, что у разработчика.

### Windows (метки `self-hosted, windows, x64`)

- Visual Studio 2022 с Desktop C++ (MSVC + Windows SDK);
- rustup stable 1.96+ с таргетом `x86_64-pc-windows-msvc`;
- `nasm` (для `aws-lc-rs`), Flutter stable с включённым windows-desktop;
- **Inno Setup 6**, причём `ISCC` в `PATH`;
- **`packaging\windows\wintun.dll`** (amd64) — положить один раз вручную.

Про `wintun.dll`: раньше workflow скачивал его с `wintun.net` на каждый прогон. Тянуть по сети
бинарь стороннего драйвера прямо в установщик — ровно тот класс supply-chain-риска, от которого
проект защищается подписью артефактов, поэтому файл кладётся на раннер осознанно и один раз.
Обновляя его, сверьте хеш с сайтом WireGuard.

Раннер работает **без интерактивной админ-сессии**, поэтому WinTUN-адаптер, WFP-фильтры и служба
вживую в CI не поднимаются. Это компиляция, юнит-тесты и упаковка. Живой device-E2E — руками,
чеклист в `packaging/windows/README.md` §4.

## 3. Секреты репозитория

Settings → Secrets and variables → Actions:

| Секрет | Что это |
|---|---|
| `CITADEL_RELEASE_PASSWORD` | пароль minisign-секрета |
| `ANDROID_KEYSTORE_BASE64` | релизный keystore Android в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | алиас ключа |
| `ANDROID_KEY_PASSWORD` | пароль ключа |

**Сам minisign-ключ в секретах не хранится.** Он лежит файлом на linux-раннере и не покидает эту
машину; в GitHub уезжает только пароль. Секреты репозитория доступны любому workflow, который в
нём выполняется, — а ключ подписи релиза это единственное, что отличает наши бинари от чужих.

`ANDROID_KEYSTORE_BASE64` такой защиты не получает (сборка APK иначе невозможна). Потеря
keystore означает невозможность выпускать обновления — сделайте офлайн-бэкап.

```sh
base64 -w0 citadel-release.jks     # значение для секрета
```

## 4. Выпуск релиза

```sh
# 1. Ветка в порядке, CI зелёный, CHANGELOG заполнен.
git switch main && git merge --ff-only dev

# 2. Подписанный тег.
git tag -s v0.8.0 -m "CitadelPQVPN v0.8.0"
git push origin main --follow-tags
```

Дальше `release.yml` делает всё сам:

1. **гейт** — clippy, тесты, инварианты и оба e2e-харнеса **на том коммите, который публикуется**
   (тег могли поставить на что-то, что через CI не проходило);
2. **windows** — установщик `CitadelPQVPN-Setup-<версия>.exe`, передаётся артефактом;
3. **publish** — серверные бинари (`mk-release.sh --no-sign`) → установщик кладётся в
   `dist/<тег>/` → `mk-client-release.sh` собирает клиентов, считает `sha256sums` по **всему**
   каталогу и подписывает **один раз** → `publish-release.sh` пере-проверяет подпись и хеши и
   создаёт GitHub Release с notes.

Порядок не случаен: `mk-release.sh` очищает `dist/<тег>/`, поэтому он обязан отработать раньше,
чем туда попадёт `.exe`. Тег с суффиксом `-pre`/`-rc`/`-beta` публикуется как prerelease.

Всё это — те же скрипты, которыми релиз собирают руками. CI их вызывает, а не повторяет: иначе
«собрано на машине» и «собрано в CI» со временем расходятся, и расхождение обнаруживается на
пользователях.

### Собрать релиз вручную

```sh
tools/mk-release.sh        v0.8.0 --no-sign
cp CitadelPQVPN-Setup-0.8.0.exe dist/v0.8.0/     # если установщик уже собран
tools/mk-client-release.sh v0.8.0                # клиенты + sha256sums + подпись
tools/publish-release.sh   v0.8.0
```

`publish-release.sh` идемпотентен: повторный запуск обновляет ассеты и notes существующего
релиза, поэтому доложить забытый артефакт можно тем же способом.

## 5. Если прогон упал

- **«на раннере нет X»** — инструмент не в `PATH` службы раннера. Служба стартует не из вашей
  интерактивной сессии: правьте окружение раннера, а не `~/.bashrc`.
- **«cargo 1.85 старее 1.96»** — в `PATH` системный cargo. Нужен `~/.cargo/bin` первым.
- **`нет /dev/net/tun`** — `sudo modprobe tun` на раннере (и в автозагрузку).
- **e2e упал** — харнесы гасят стенды сами и печатают вердикт со списком провалившихся проверок;
  повторить локально: `bash docker/run-demo.sh`, `bash docker/run-cli-tests.sh`.
- **`отказываюсь класть debug-APK в релиз`** — не подхватился keystore: проверьте секреты
  `ANDROID_*` и то, что шаг развёртывания keystore отработал.
- **minisign не подписал** — пароль отдаётся ему на stdin (без терминала он читает оттуда);
  проверьте `CITADEL_RELEASE_PASSWORD` и наличие файла ключа на раннере.
