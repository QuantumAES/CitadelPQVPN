# CitadelPQVPN — Альтернативы гибридному сертификату Ed25519+ML-DSA-65

**Документ-компаньон к SPEC.md (раскрывает §3.2), серверная аутентификация**
Дата: 2026-06-18

---

## 1. Проблема

Гибридный серверный сертификат `Ed25519 + ML-DSA-65` даёт постквантовую аутентификацию, но **сильно раздувает handshake-flight сервера**:

- ML-DSA-65: публичный ключ **1952 Б**, подпись **3309 Б** → +~5.3 КБ к цепочке.
- В QUIC это значит многопакетный server-flight, рост латентности на потерях, и взаимодействие с MTU/anti-amplification (SPEC §11). Для **консьюмерского VPN в плохих/цензурируемых сетях** лишние килобайты на установке = заметно хуже UX и больше «хвост» при потерях.

Нужны варианты, раздувающие цепочку **приемлемо** (или не раздувающие вовсе).

---

## 2. Ключевая свобода: аутентификация не срочна по HNDL

Подделать аутентификацию задним числом нельзя — forging требует CRQC **в момент** хендшейка (SPEC §0, §3.2). Значит, в отличие от обмена ключами (который обязан быть PQ уже сейчас), у нас есть **свобода манёвра**: можно выбрать дешёвую по размеру схему и мигрировать без спешки.

---

## 3. Сравнение вариантов

Размеры — то, что **добавляется в handshake поверх классики**. Меньше — лучше.

| Вариант серверной аутентификации | PubKey | Подпись/данные | Раздувание handshake | PQ? | Примечание |
|---|---:|---:|---:|:--:|---|
| Ed25519 (baseline, этап 1) | 32 Б | 64 Б | — | ✗ | крошечный, не PQ |
| **Ed25519 + ML-DSA-65** (исходный) | +1952 Б | +3309 Б | **+~5.3 КБ** | ✓ | то, что заменяем |
| **① Внешний PSK (RFC 8773 / PSK+DHE)** | 0 | 0 | **+0 Б** | ✓(симм.) | переиспользует наш PSK; **рекомендуется** |
| **② Ed25519 + Falcon-512** | +897 Б | +~666 Б | **+~1.6 КБ** | ✓ | подпись в ~5× меньше ML-DSA; подписывать офлайн |
| ② Ed25519 + Falcon-1024 | +1793 Б | +~1280 Б | +~3.1 КБ | ✓(L5) | если нужен уровень 5 |
| **③ Hash-based вне handshake** (SLH-DSA / LMS-XMSS) | — | вне провода | **+0 Б в handshake** | ✓ | консервативный якорь доверия в конфиге |
| ④ KEMTLS (ML-KEM-768 для auth) | 1184 Б (ek) | 1088 Б (ct) | ~+2.3 КБ, но **меняет форму** | ✓ | риск fingerprint для mimicry |
| ⑤ Merkle Tree Certs (MTC) | — | малый inclusion-proof | мал. | ✓ | новьё (IETF), на будущее |

Справочно — размеры подписных PQ-схем:
- ML-DSA-44/65/87: подпись 2420/3309/4627 Б, pubkey 1312/1952/2592 Б.
- Falcon-512/1024: подпись ~666/~1280 Б, pubkey 897/1793 Б.
- SLH-DSA-128s/128f: подпись 7856/17088 Б (поэтому **только вне handshake**).

## 4. Разбор вариантов

### ① Внешний PSK, подмешанный в key schedule TLS 1.3 — *рекомендуемый primary*
**Идея:** мы уже распространяем на клиента per-server секрет (`PSK_master` → `PSK_tls_auth`, см. PHASE0-OBFS §2). Подмешав его в key schedule TLS 1.3 (через `pre_shared_key`), получаем **постквантовую аутентификацию с нулевым раздуванием**: даже квантовый противник без PSK не сможет выдать себя за сервер и не выведет сессионные ключи.

- **Стандарты:** RFC 8446 (нативный PSK+(EC)DHE, `psk_dhe_ke`) для PSK-only; **RFC 8773** — если нужно сохранить и сертификат (PKI-идентичность), и PSK одновременно (cert-based auth + external PSK).
- **Квантовая стойкость:** PSK симметричный 256-бит → Grover даёт 128-бит → стойко.
- **Бонус к конфиденциальности:** PSK входит в key schedule → defense-in-depth поверх гибридного KEM (даже если и X25519, и ML-KEM-768 гипотетически падут, PSK ещё держит сессию).
- **Mimicry-дружелюбно (важно для нас!):** на проводе `pre_shared_key` от внешнего PSK **неотличим от обычного TLS session-resumption**, который вездесущ в вебе. Плюс всё закрыто ECH и завёрнуто L1 (PHASE0-OBFS). То есть это не добавляет отличительного отпечатка.
- **Минусы:** PSK общий для всех клиентов сервера (аутентифицирует «сервер своей клиентуре» — ровно консьюмерская модель доверия); требует ротации (уже предусмотрена для obfs).

> Это лучший фит под нашу архитектуру: переиспользуем уже существующий механизм PSK, 0 байт в handshake, держим форму обычного TLS.

### ② Falcon (FN-DSA) вместо ML-DSA — *если нужна подпись в цепочке*
Подпись Falcon-512 ~666 Б против 3309 Б у ML-DSA-65 — в ~5 раз меньше; раздувание падает с ~5.3 КБ до ~1.6 КБ.

- **Главный аргумент против Falcon обычно** — сложность constant-time подписи (floating-point гауссово сэмплирование, side-channels). **Но для серверного сертификата это почти не важно:** подпись над сертификатом создаётся **офлайн при выпуске** (CA / провижининг), а **клиент только верифицирует** — верификация целочисленная, быстрая и без секрето-зависимых FP-операций. Слабое место Falcon (подпись) выносится из горячего пути.
- **Минус:** FIPS 206 на момент cutoff в финализации (draft) → держать за crypto-agility, не как единственный путь.

### ③ Hash-based вне handshake (SLH-DSA / LMS / XMSS) — *консервативный якорь*
Подписи hash-based огромны (7.8–30 КБ) → **никогда в handshake**. Но их можно использовать там, где размер не важен:
- подпись **конфига/подписки** (out-of-band доставка серверных параметров и pinned-ключей);
- **аттестация pinned-ключа** сервера: клиент при провижининге проверяет hash-based-подпись над Ed25519/Falcon-ключом сервера, а в рантайме хендшейк остаётся маленьким.

Это **полностью развязывает** PQ-якорь доверия и размер handshake. Стойкость опирается только на хеш-функции (самое консервативное предположение). LMS/XMSS — stateful (нельзя переиспользовать индекс OTS → операционный риск), подходят для редких офлайн-подписей (рекомендация CNSA для firmware).

### ④ KEMTLS / AuthKEM — упоминание с оговоркой
Аутентификация без подписи: сервер доказывает владение долговременным KEM-ключом декапсуляцией (ML-KEM). Суммарно меньше, чем ML-DSA (~2.3 КБ против ~5.3 КБ), и переиспользует тот же примитив ML-KEM (одна constant-time реализация на всё).
- **Минус для нас:** меняет *форму* хендшейка (нет `CertificateVerify`-подписи, иной стейт-машина) → это **отличительный отпечаток** для DPI и противоречит цели mimicry; в `rustls` из коробки нет. Для consumer-анти-DPI — нежелательно. Держать на радаре, не брать в v1.

### ⑤ Merkle Tree Certificates — на будущее
IETF-направление специально против PQ-раздувания: вместо подписи в каждом сертификате — компактный Merkle inclusion-proof против пакетно-подписанного дерева. Сильно режет объём аутентификации. Незрело → forward-looking.

## 5. Рекомендация для CitadelPQVPN (консьюмер, без комплаенса)

Комбинация, дающая PQ-аутентификацию при **минимальном** раздувании:

1. **Primary PQ-auth — внешний PSK (①)**, подмешанный в key schedule (RFC 8773 поверх сертификата либо `psk_dhe_ke`). **+0 байт**, переиспользует `PSK_tls_auth` из PHASE0-OBFS §2, сохраняет форму обычного TLS (mimicry).
2. **Лист — Ed25519, pinned.** Идентичность/PKI-семантика; благодаря pinning **цепочка на провод не идёт** (клиент уже знает ключ) → дополнительная экономия.
3. **Когда нужна настоящая PQ-подпись в цепочке — Falcon-512 (②)**, подписывать офлайн, клиент только верифицирует (~1.6 КБ вместо ~5.3 КБ).
4. **Якорь/конфиг — hash-based (③, SLH-DSA или LMS/XMSS)** вне handshake: консервативный PQ-корень доверия без влияния на размер хендшейка.
5. **ML-DSA-65 — оставить только опцией crypto-agility** (suite `CitadelPQVPN-2`) на случай требований стандартной PKI-интероперабельности.

**Эффект:** server-flight остаётся маленьким → нет многопакетного ответа, меньше «хвост» на потерях, легче MTU/anti-amplification (SPEC §11) — то есть быстрый и надёжный хендшейк именно там, где это критично для consumer-VPN.

### Предлагаемая правка реестра шифрсьютов (SPEC §3.3)
| Suite ID | KEX | Серверная аутентификация | Раздувание | Статус |
|---|---|---|---|---|
| `CitadelPQVPN-1` (default) | X25519MLKEM768 | Ed25519 (pinned) **+ внешний PSK** | +0 Б | активен |
| `CitadelPQVPN-1f` | X25519MLKEM768 | Ed25519 + **Falcon-512** (+PSK) | +~1.6 КБ | опция PQ-подписи |
| `CitadelPQVPN-2` | X25519MLKEM768 | Ed25519 + **ML-DSA-65** | +~5.3 КБ | agility/PKI-интероп |

## 6. Замечания по реализации (Rust)
- Внешний PSK в TLS 1.3: `rustls` поддерживает external PSK / `psk_dhe_ke` — задать provider и preshared key; держать домен-разделение `PSK_tls_auth` ≠ `PSK_obf` (PHASE0-OBFS §2).
- Falcon: верификация — из проверенного крейта (`pqcrypto-falcon`/liboqs-привязка); подпись — офлайн-инструментом при выпуске, не в рантайме сервера.
- SLH-DSA/LMS: только офлайн-подпись конфига; на клиенте — только верификация.
- Pinning: клиент хранит ожидаемый Ed25519/Falcon-ключ сервера из подписки; сервер может слать минимальную/пустую цепочку.
