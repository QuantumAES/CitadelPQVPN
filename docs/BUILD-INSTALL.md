# Сборка и установка CitadelPQVPN

Клиент = Flutter-GUI + Rust-ядро (Linux/Android); сервер-exit = Docker-контейнер.
Полная настройка окружения — `tools/setup-dev-env.sh` (rustup, Flutter, Android SDK/NDK,
кросс-таргеты, cmake). Ниже — краткая выжимка.

## Окружение

- **Rust** — rustup **stable 1.96+** (НЕ системный `/bin/cargo` 1.85: зависимости требуют новее).
- **cmake** (для `aws-lc-rs`) — системный `/bin/cmake`; НЕ ставь `.venv` первым в `PATH`.
- **Flutter** — stable 3.44+ (`$HOME/flutter/bin`).
- **Android** (для APK) — SDK 36 + build-tools 36 + NDK 27 (`ANDROID_NDK_HOME`), cargo-ndk.
- PATH для сборок: `export PATH="$HOME/flutter/bin:$HOME/.cargo/bin:$PATH"`.

## Клиент — Linux (desktop)

```sh
cd app
flutter build linux --release                 # → build/linux/x64/release/bundle/
( cd .. && cargo build --release -p citadel-helper )   # TUN-хелпер (polkit)
```

Установка (на машине **с TUN**, нужен root/pkexec):

```sh
sudo tools/install-desktop.sh --with-app       # helper + polkit (политика + правило) + app → /opt/citadel-pqvpn
sudo usermod -aG citadel-vpn $USER              # чтобы GUI не спрашивал пароль (затем ПЕРЕЛОГИН)
/opt/citadel-pqvpn/app                          # запуск GUI
```

**Про запрос пароля.** GUI поднимает туннель через `pkexec citadel-helper`, и polkit по умолчанию
просит пароль администратора — причём не только на первое подключение: каждый автоматический
реконнект (смена Wi-Fi/LTE, восстановление связи) запускает хелпер заново, то есть спрашивает
снова. Установщик поэтому ставит правило `/etc/polkit-1/rules.d/49-citadel-pqvpn.rules`: членам
группы `citadel-vpn` (та же группа, что даёт право управлять туннелем консольному клиенту)
подтверждение не требуется. Кто не в группе — работает как раньше, по паролю.
Не нужно такого поведения — `sudo tools/install-desktop.sh --with-app --ask-password`.
Добавлять в группу стоит только тех, кому доверяете администрирование сети машины (член группы
может завернуть весь её трафик в свой exit) — поэтому установщик никого не добавляет сам,
`--user ИМЯ` делает это по явной просьбе.

### Чистка кешей сборки

Дерево сборки растёт до десятков гигабайт (`target/` + `app/build` + per-ABI Rust под Android):

```sh
bash tools/clean-caches.sh -n            # показать, что и сколько удалится
bash tools/clean-caches.sh               # безопасно: incremental-кеши + мусор docker
bash tools/clean-caches.sh --deep        # + cargo clean, flutter clean, gradle-трансформы
```

`--deep` означает полную пересборку в следующий раз (cargo ~10–15 мин из-за aws-lc-rs, APK ~6–8 мин
из-за четырёх ABI). Скрипт не трогает исходники, `dist/` с релизами, `~/.cargo/registry`,
`~/.pub-cache`, хранилища профилей и ключи; удаляет только то, что пересоздаётся сборкой.

## Клиент — Android (APK)

```sh
cd app
flutter build apk --release                     # все ABI; либо конкретные:
flutter build apk --release --target-platform android-arm64,android-x64
# → build/app/outputs/flutter-apk/app-release.apk
```

### Сборка Rust-части и pub.dev

Rust-крейт под Android собирает **cargokit** — gradle-таск `cargokitCargoBuildRust_lib_app*`,
который дёргает `app/rust_builder/cargokit/run_build_tool.sh`. Скрипт разворачивает во временной
папке (`app/build/rust_lib_app/build/build_tool`) микропакет `build_tool_runner` и делает для него
`dart pub get` — **поход в сеть на pub.dev в середине 8–12-минутной сборки APK**. Кратковременный
сбой DNS в этот момент ронял весь релиз:

```
ClientException with SocketException: Failed host lookup: 'pub.dev' … /advisories
Process '…/run_build_tool.sh' finished with non-zero exit value 69   # EX_UNAVAILABLE
```

Две наши правки в `run_build_tool.sh` (обе помечены `CitadelPQVPN patch`) это снимают:

* при недоступности pub.dev `pub get` повторяется с `--offline` — все зависимости `build_tool`
  запинены в его `pubspec.yaml` и лежат в `~/.pub-cache`, так что резолв проходит без сети;
* хэш-маркер `.package_hash`, по которому решается, нужен ли `pub get` вообще, считается теперь
  от листинга **изнутри** пакета. В апстриме в него попадала строка пути, которым позвали скрипт
  (gradle зовёт `…/cargokit/gradle/../run_build_tool.sh`, CMake — нормализованный путь), маркер
  инвалидировался на ровном месте, и в сеть ходила каждая сборка.

Следствие: `~/.pub-cache` нужен «прогретый» — после `tools/clean-caches.sh` он не чистится, но на
свежей машине первую сборку всё-таки надо делать с интернетом.

### Подпись APK

`applicationId` приложения — **`com.quantumaes.citadelpqvpn`**. Менять его нельзя: для Android
это другое приложение, обновление поверх не встанет. Имя пакета зашито ещё и в имена
JNI-символов (`Java_com_quantumaes_citadelpqvpn_CitadelVpnService_…` в `app/rust/src/android_jni.rs`),
причём связываются они в рантайме — расхождение даст собравшийся APK, который падает при
старте VpnService. Инвариант сторожит `tools/check-android-jni.py` (гоняется в CI).

Keystore Gradle ищет в двух местах, ни одно из них не в репозитории:

1. `app/android/key.properties` (в `.gitignore`):

   ```properties
   storeFile=/абсолютный/путь/citadel-release.jks
   storePassword=…
   keyAlias=citadel
   keyPassword=…
   ```

2. переменные окружения — так делает CI:
   `CITADEL_KEYSTORE`, `CITADEL_KEYSTORE_PASSWORD`, `CITADEL_KEY_ALIAS`, `CITADEL_KEY_PASSWORD`.

Создать keystore (**сделайте офлайн-бэкап: потеря = невозможность выпускать обновления**):

```sh
keytool -genkeypair -v -keystore citadel-release.jks -alias citadel \
        -keyalg RSA -keysize 4096 -validity 10000
```

Ключа нет — Gradle откатывается на debug-ключ и говорит об этом в логе сборки. Такой APK
годится только для локальной проверки, и `tools/mk-client-release.sh` откажется класть его в
релиз (обход для своих сборок — `CITADEL_ALLOW_DEBUG_APK=1`).

Установка:

```sh
adb install -r build/app/outputs/flutter-apk/app-release.apk
# либо скинуть APK на телефон и поставить вручную (разрешив установку из неизвестных источников)
```

Подключение (оба клиента): **«Добавить профиль» → вставить `citadel://`-ссылку → «Подключить»**.
Профиль сохраняется сразу при добавлении (удалить можно в меню профиля).

## Сервер — exit (режим Admin)

Первая установка — скриптом **на самом сервере, без клиента** (детали: `docs/CLIENT-ARCH.md` §8).
Бинарь тянется с GitHub Release и проверяется подписью minisign (supply-chain).

**Один раз (мейнтейнер) — ключ подписи релиза:**
```sh
tools/gen-release-key.sh          # → packaging/release/citadel-release.pub (коммитится)
#   секрет — вне репо (~/.citadel/release, password-protected); сделай ОФЛАЙН-БЭКАП, не коммить
git add packaging/release/citadel-release.pub
```

**Собрать + подписать + выложить релиз (под арку сервера):**
```sh
tools/mk-release.sh    vX.Y.Z      # → dist/vX.Y.Z/{citadel-m1,citadel-linkgen}-<arch>.zst + sha256sums(.minisig)
gh auth login
tools/publish-release.sh vX.Y.Z    # выкладка на GitHub Release
```

**Развернуть на сервере (root):**
```sh
CITADEL_VERSION=vX.Y.Z ./install-citadel-server.sh
# авто-Docker → verified-pull бинаря → keygen на сервере → docker compose up → печать citadel://
```

**Порты** (M-8, аудит-4): порт туннеля и порт издателя **выбираются случайно при первой
установке** (10000–31999) и запоминаются в `$DIR/etc/ports.env`; повторный запуск установщика
берёт их оттуда, поэтому уже выданные ссылки не ломаются. Прежние 4433/7000 были узнаваемой
«подписью» Citadel — деплой опознавался сканером без единого пакета в туннель. Задать свои:
```sh
./install-citadel-server.sh vX.Y.Z --udp-port 5443 --issuer-port 7300
# то же через env: CITADEL_UDP_PORT / CITADEL_TCP_PORT / CITADEL_ISSUER_PORT / CITADEL_ADMIN_PORT
./install-citadel-server.sh --help      # полный список флагов
```
Клиент берёт порты **из ссылки** — на устройствах ничего настраивать не нужно; после смены портов
нужно раздать новые ссылки (установщик их печатает). Порт `--tcp-port` остаётся **443** намеренно:
это не дефолт, а камуфляж под HTTPS. Установщик проверяет диапазон, конфликты портов между
собой и предупреждает, если порт уже занят на хосте.

> **Firewall:** открой на VDS входящие **`--udp-port`/udp** (PQ-QUIC — номер печатает установщик,
> он же лежит в `$DIR/etc/ports.env`), **`--tcp-port`/tcp** (obfs-fallback, 443) и
> **`--issuer-port`/tcp** (издатель токенов) — в облачной security-group провайдера и, при
> наличии, в `ufw`/`nftables`. Иначе клиент увидит «ни один exit недоступен». Порт admin-канала
> (`--admin-port`, 7001) при установке **на один сервер** (`--role all`) наружу не публикуется
> вовсе — открывать его не нужно и нечего. При **раздельном** деплое он публикуется на машине
> издателя: в него стучится exit-машина, см. «Два сервера» ниже.

> **⚠ `ufw` не фильтрует порты, опубликованные docker'ом.** `ports:` — это DNAT в
> `nat/PREROUTING`: пакет из WAN уходит в `FORWARD` (`DOCKER-USER` → `DOCKER`) и в `INPUT`, где
> живут правила `ufw`, не попадает никогда. Практические следствия, каждое из которых наблюдалось
> живьём: `ufw allow …` на такой порт ничего не открывает (он и так открыт), `ufw deny` и
> `default deny incoming` ничего не закрывают, а `nmap` снаружи показывает `open` (часто
> `tcpwrapped` — ядро доводит TCP-хендшейк, а закрывает соединение уже приложение). Фильтровать
> такой трафик можно только в цепочке `DOCKER-USER`: её создаёт сам docker и при рестарте демона
> не чистит. Установщик пользуется ровно ей — см. `$DIR/etc/admin-fw.sh`. Порты, которые слушает
> сам хост (ssh), `ufw` фильтрует как обычно.

> **Хост машины из туннеля закрыт (G1).** Абонент не должен через туннель ходить на публичный
> адрес самого сервера: F2 его не режет (адрес публичный), а ядровое `INPUT -i Citadel0 -j DROP`
> действует лишь в netns контейнера — пакет ушёл бы через FORWARD+MASQUERADE и постучался в
> хозяйское ядро с docker-бриджа, то есть мимо облачной security-group. Установщик поэтому кладёт
> в entrypoint exit'а `Citadel_DENY_DSTS` (публичный адрес машины, а при раздельном деплое ещё и
> адрес издателя) и `Citadel_ALLOW_DSTS` (единственное исключение — token-порт издателя: фоновая
> дозаправка кошелька идёт сквозь туннель намеренно). При старте exit печатает
> `[citadel-exit] G1: из туннеля закрыты …`. Если у машины несколько публичных адресов или рядом
> живёт ещё один сервис, который абонентам видеть незачем, — допиши адреса в те же переменные
> (список через запятую, исключения в виде `addr:port`); мусор в них роняет старт, а не молча
> сужает фильтр.

**ufw синхронизируется установщиком.** Если на машине активен `ufw` и порты этой установки
разошлись с открытыми (типично после переустановки с ротацией портов), установщик покажет, что
предлагает открыть и что закрыть, и спросит подтверждение: `--ufw` — применить без вопроса,
`--no-ufw` — не трогать. Прежние порты снимаются, чтобы на сервере не оставались открытыми порты,
которых уже никто не слушает. Облачную security-group скрипт не трогает — её правит провайдер.
Синхронизация идёт при **любой** роли, включая `--role issuer` (до 2026-08-19 секция стояла в
скрипте ниже точки, на которой установка издателя заканчивается, и на машине издателя не
выполнялась вовсе). Помни при этом про абзац выше: на опубликованные docker'ом порты правила
`ufw` не действуют — они про порты хоста и про гигиену (не держать открытым то, что никто не
слушает).

> **Обслуживать сервер из-под собственного туннеля нельзя** (следствие G1/G2). Адрес самой машины
> и — при раздельном деплое — адрес издателя закрыты для трафика из туннеля целиком, кроме
> token-порта издателя. Поэтому при поднятом туннеле `ssh` на сервер виснет, а уже открытая
> сессия рвётся в момент подъёма. Это не поломка: иначе любой абонент дотягивался бы из туннеля
> до `sshd`, docker-API и published-портов соседних контейнеров — мимо облачной security-group.
> Как работать: администрировать с машины, где туннель не поднят, либо в приложении
> «Раздельный туннель» → «По адресам назначения» → «В обход» добавить адреса своих серверов
> (`IP/32`) — тогда ssh к ним идёт напрямую, а весь остальной трафик остаётся в туннеле.

**Полоса на абонента** (F7/D3): `--rate-limit` / `--rate-burst` — вверх, `--rate-limit-down` /
`--rate-burst-down` — вниз. По умолчанию вниз симметрично вверх (10 MiB/с, всплеск 20 MiB);
`--rate-limit-down 0` снимает лимит только на скачивание. До аудита-4 (M-3-bis) обратное
направление не ограничивалось вовсе, хотя именно на нём живёт и основная нагрузка релея, и
амплификация «мало запросил — много получил».

**Порты выбираются случайно** (M-8) при первой установке и запоминаются в `$DIR/etc/ports.env`,
чтобы выданные ссылки не «переехали». Переустановка **с ротацией идентичности** (то есть без
`CITADEL_KEEP_KEYS=1`) выбирает порты заново: прежние ссылки в этом сценарии всё равно мертвы, а
сохранённый порт оставлял бы деплою прежнюю примету. С `CITADEL_KEEP_KEYS=1` порты сохраняются —
там ссылки обязаны продолжать работать. Установщик прямо предупреждает о смене портов: **новые
нужно открыть в firewall**, иначе абоненты увидят «сервер недоступен» при исправном сервере.

**Ротация ключа L1 (H-3)** включается сама, когда есть издатель: установщик генерит
`$DIR/keys/obfs.master` — серверный секрет, из которого выводится ключ обфускации каждой эпохи.
Файл появляется **при любой установке с издателем**, а не только при раздельной: exit и издатель
читают его с общего тома (`$DIR/keys`), и он же переживает рестарт контейнеров — иначе после
перезапуска стороны разошлись бы по ключам. При раздельном деплое он дополнительно уезжает на
exit-машину полем `CITADEL_OBFS_MASTER` в bundle. В ссылки мастер не попадает никогда.
Абонент получает ключ текущей эпохи у издателя после Layer-1, вместе с токеном; PSK из ссылки
теперь открывает только канал к издателю. Практические следствия: **ссылки перевыпускать не
нужно**, а `revoke` абонента гасит и его L1-доступ (со следующей эпохи). В установке
`--no-issuer` ротации нет — раздавать ключ некому.

Ссылку `citadel://` из вывода — вставить в клиент.

**Установщик печатает ОДНУ ссылку — мастер-ссылку, и та одноразовая (M-9).** Она активируется на
первом устройстве администратора: клиент заводит собственный ключ Layer-1, издатель переносит на
него подписку, а запись самой ссылки гасит. Вторая копия после этого не работает — пересланная
или подсмотренная ссылка доступа не даёт. Окно активации по умолчанию 24 часа (`--activate-secs`),
и вместе со ссылкой печатается **код сверки**: приложение спрашивает его при импорте, так ловится
подмена ссылки при доставке. Отдельной клиентской ссылки установщик больше не печатает — раньше
она была бессрочной и поднимала туннель с любого числа устройств; абонентов выдают из приложения
(«Абоненты» → выдать), и каждая такая ссылка одноразовая с самого начала. Практическое следствие:
**у администратора одно устройство**; второе — это либо переустановка, либо выданная себе
абонентская ссылка для обычного доступа.

#### Один сервер или два (exit и издатель)

Установка бывает в двух схемах. Обе рабочие; выбор — про то, чем платить.

| | **Один сервер** (`--role all`, умолчание) | **Два сервера** (`--role issuer` + `--role exit`) |
|---|---|---|
| Что стоит | exit + издатель на одной машине, общий том `keys/` | издатель отдельно, exit отдельно |
| Кража диска даёт | идентичность туннеля **и** издателя сразу | только одну из двух половин |
| Ключ эпохи (СЕКРЕТ, схема токенов v2) | издатель пишет его в общий том (0640, группа exit'а) | exit тянет по сети (сайдкар `citadel-keysync`, аутентифицируется своим seed'ом из bundle) |
| Цена | — | вторая машина, порядок установки, bundle между ними |

**Один сервер** — команда выше, больше ничего не нужно.

**Два сервера.** Сначала издатель:

```sh
# машина A (издатель)
./install-citadel-server.sh vX.Y.Z --role issuer --issuer-port 7300
```

Он напечатает **bundle** (`KEY=VALUE`: адрес, TLS-pin, PQ-обязательство, obfs-PSK, seed'ы абонента
и админа). Bundle — секрет уровня «доступ к сервису»: копировать `scp`, а не мессенджером, и
удалить после установки. Дальше exit:

```sh
# машина B (exit): положить bundle в issuer.env
./install-citadel-server.sh vX.Y.Z --role exit --issuer-bundle issuer.env
```

Ссылки печатает **машина B** — только у неё есть cert-pin и ML-DSA-ключ туннеля. Реестр абонентов и
`admin_id` остаются на **машине A**: выдача и отзыв идут туда (через туннель, как обычно).

Что нужно от firewall в этой схеме:

* на машине A: `--issuer-port` открыт для клиентов; `--admin-port` docker публикует наружу (в него
  стучится машина B через DNAT из туннеля), и доступ к нему режут три рубежа:
  1. **`--admin-bind <IP>`** — на каком адресе издателя вообще публиковать порт. Есть приватная
     сеть с машиной B (VPC, WireGuard) — задай её адрес, и на публичном интерфейсе порта не
     будет физически. По умолчанию `0.0.0.0`.
  2. **ядро машины A** — цепочка `CITADEL-ADMIN` в `DOCKER-USER`: адреса из `--admin-peer`
     пропускаются, остальные `DROP`. Ставит установщик (`$DIR/etc/admin-fw.sh`), переживает
     ребут и рестарт docker'а через `citadel-admin-fw.service`. Снаружи порт выглядит `filtered`.
     **`ufw` здесь бессилен** — см. предупреждение в начале раздела; правило `ufw allow from …`
     установщик тоже добавит, но это гигиена, а не рубеж.
  3. **сам издатель** — `--admin-peer <IP машины B>` **обязателен** при `--role issuer` (L-14,
     аудит-4): чужой адрес закрывается до TLS. Открыть всем осознанно — `--admin-peer any`
     (тогда установщик ядровое правило не ставит: это уже осознанное решение оператора).

  Проверить после установки: `iptables -nvL CITADEL-ADMIN` на машине A и `nmap -Pn -p <admin-port>
  <IP машины A>` снаружи — ожидание `filtered`. `open`/`tcpwrapped` означает, что правило не
  встало (нет `iptables`, docker без `DOCKER-USER`, `iptables -F` после установки);
* на машине B: `--udp-port` и `--tcp-port` для клиентов; входящих от издателя не требуется —
  `citadel-keysync` ходит исходящим соединением сам.

> **Почему установка exit'а проходит, даже когда `ufw` на машине A «не открыт»** — тот же
> docker-байпас: token-порт издателя опубликован docker'ом, и правила `ufw` на него не действуют,
> поэтому `citadel-keysync` получает ключ эпохи независимо от них. То есть успешная установка
> exit'а **не** доказывает, что правила `ufw` на издателе корректны; проверяй их сканом снаружи.

Установка exit'а не завершится «успешно» вслепую: она ждёт первую синхронизацию ключа эпохи с
издателем и падает с понятной причиной, если порт закрыт, PSK не совпал или pin/обязательство не те.

> Bundle издателя после аудита-4 несёт два новых поля — `CITADEL_KEYSYNC_SEED` (идентичность
> exit'а для получения секретного ключа эпохи) и `CITADEL_OBFS_MASTER` (мастер L1). Bundle,
> снятый с прежней версии, для новой установки не годится — сними его заново на машине A.

Bundle — секрет уровня «доступ к сервису» (в нём seed'ы абонента и админа и мастер L1), поэтому
установщик издателя **печатает его на экран и нигде не сохраняет**, а exit-машина умеет принять его
копипастом, не создавая файла:

```bash
./install-citadel-server.sh vX.Y.Z --role exit --issuer-bundle -   # вставить строки, затем Ctrl-D
```

Вариант с файлом (`--issuer-bundle issuer.env`) остаётся — он удобнее при автоматизации; тогда файл
после установки удаляют.

#### Если сервер скомпрометирован

Узел спроектирован **расходным**: восстановление — это переустановка, а не «чистка». Повторный
запуск установщика меняет всю идентичность (obfs-PSK, cert-pin, ML-DSA, ключи издателя), прежние
ссылки после этого мертвы — нужно раздать новые. Записанный ранее трафик расшифровать нельзя:
сессионные ключи эфемерны, а ключ подписи токенов живёт только в памяти издателя и ротируется
каждую эпоху. Разбор того, что даёт украденный диск и почему шифрование каталога ключей помогает
не от всего, — [`docs/SERVER-KEY-PROTECTION.md`](SERVER-KEY-PROTECTION.md).
