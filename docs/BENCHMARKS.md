# CitadelPQVPN — бенчмарки (M6)

Criterion, bench-профиль (opt-level 3), rustc 1.85. Запуск: `cargo bench -p <crate>`.
Числа — медиана разового прогона на dev-машине: **порядок величин**, не абсолют; для регрессий
сравнивать прогоны на одной машине (criterion хранит baseline в `target/criterion`).

## obfs L1 — hot path, на каждый пакет (`citadel-obfs`)

| Операция | Время | Throughput |
|---|---|---|
| KDF `k_hdr` (blake3 derive) | ~225 ns | — |
| KDF `k_sess` | ~245 ns | — |
| `seal` 64 B | ~3.17 µs | ~19 MiB/s |
| `open` 64 B | ~3.10 µs | ~20 MiB/s |
| `seal` 512 B | ~3.57 µs | ~137 MiB/s |
| `seal` 1024 B | ~4.29 µs | ~227 MiB/s |
| `seal` 1232 B | ~5.05 µs | ~233 MiB/s |
| `open` 1232 B | ~4.79 µs | ~245 MiB/s |
| `pad_len_for` (паддинг-политика) | ~4.3 ns | — |

**Находка → реализовано (`Sealer`/`Opener`, M6):** stateless `seal`/`open` пере-вычисляли KDF
(`k_hdr`+`k_sess` ≈ 450 ns) и пере-инициализировали ChaCha20Poly1305 на КАЖДЫЙ пакет. Кеш
ключей/cipher per-session убрал это:

| Размер | stateless | cached (`Sealer`/`Opener`) | выигрыш |
|---|---|---|---|
| seal 64 B | ~3.14 µs | ~2.68 µs | **−15 %** (~373k pps) |
| open 64 B | ~3.13 µs | ~2.68 µs | **−14 %** |
| seal 1232 B | ~5.10 µs | ~4.75 µs | −7 % |
| open 1232 B | ~5.36 µs | ~4.43 µs | −17 % |

Экономия ~460 ns/пакет (как раз 2× KDF-derive). Подключено в `ObfsUdpSocket` (`Sealer` — immutable
на send; `Opener` под Mutex на recv, кеш cipher по `sid`). Паддинг-политика практически бесплатна.

## data-plane parse — hot path (`citadel-masque`)

| Парсер | Время |
|---|---|
| `ip::parse_ipv4` | ~11.5 ns |
| `datagram::decode` | ~3.2 ns |
| `varint::decode` | ~6.8 ns |
| `capsule::decode` | ~6.3 ns |

**Вывод:** разбор пакетов ничтожен (наносекунды) против obfs-крипты (µs) и сети — не bottleneck.

## анонимные токены Layer-2 (VOPRF ristretto255) — control path, на подключение (`citadel-token`)

Схема v2 (M-6, 2026-08). В скобках — прежние цифры blind RSA-2048, чтобы был виден масштаб замены.

| Операция | Время | Было (blind RSA) | Роль |
|---|---|---|---|
| `epoch_keygen` | ~40 µs | ~10 **с** (RSA keygen) | издатель, раз в эпоху |
| `client_blind` | ~121 µs | ~515 µs | клиент (nonce + ослепление) |
| `issuer_evaluate` | ~228 µs | ~3.1 ms | издатель (вычисление вслепую + DLEQ) |
| `issuance_roundtrip` | ~603 µs | ~3.9 ms | вся выдача одного токена (blind→evaluate→finalize с проверкой DLEQ) |
| `token_redeem` | ~250 **ns** | — | клиент: отпечаток предъявления (в прежней схеме операции не было) |
| `verify_redemption` | ~108 µs | ~311 µs (`verify_token`) | exit (на подключение, НЕ per-packet) |

**Вывод:** выдача ≈ 0,6 мс/токен вместо ≈ 4 мс; издатель ~1650 выдач/с на поток вместо ~320.
Проверка на exit'е ~108 µs — control-path (один раз при коннекте), на throughput данных не влияет.
Отдельно стоит отметить `epoch_keygen`: ротация ключа эпохи перестала быть заметной операцией
(была ~10 с генерации RSA — на это время издатель фактически замирал на старте и на каждой смене
эпохи).

## overflow-checks в релизе (Ф0.2, замер 2026-08-16)

`[profile.release] overflow-checks = true` (корневой `Cargo.toml` и `app/rust/Cargo.toml`). До этого
переполнение целого в **релизной** сборке — единственной, которая доезжает до людей, — молча
заворачивалось по модулю, тогда как тесты гоняются в debug и поймали бы его паникой. Считает на
недоверенном вводе ровно то, что здесь и меряется: длины из пакетов, varint, арифметика MTU.

Метод: `cargo bench … --save-baseline before` до правки, `--baseline before` после, тулчейн и машина
те же, посторонняя нагрузка снята.

| Замер | Было | Стало | Изменение |
|---|---|---|---|
| `obfs/seal`, `obfs/open` (64…1232 Б, с кешем и без) | 2,75–5,12 µs | 2,76–5,16 µs | в пределах шума (±3 %) |
| `kdf/k_hdr`, `kdf/k_sess` | 243 / 251 нс | 237 / 234 нс | в пределах шума |
| `ip/parse_ipv4` | 10,88 нс | 10,69 нс | −1 % |
| `capsule/decode` | 6,60 нс | 6,29 нс | −4 % |
| `datagram/decode` | 4,12 нс | 4,04 нс | −2 % |
| **`varint/decode`** | **5,96 нс** | **6,96 нс** | **+20 %** |

**Как это читать.** Единственная реальная просадка — `varint::decode`: +1 нс на вызов, и она
воспроизводится от прогона к прогону. Это ожидаемо: там сдвиги и сложения над длиной из пакета, то
есть ровно те операции, ради которых проверка и включается. На пути пакета varint'ов единицы, а
бюджет пакета — микросекунды obfs-крипты: +3 нс против ~3200 нс, то есть **порядка 0,1 %** сквозной
стоимости. Критерий выхода Ф0.2 («не хуже 3 %») выполняется по per-packet пути; изолированный
микробенчмарк показан отдельно, чтобы никто не «открыл» эти 20 % заново и не снял проверку.

**Осторожно с шумом.** На коротких входах (`*_cached/64`) отдельные прогоны на этой машине дают
разброс до ±40 % при одном и том же бинаре — сверять надо повторным прогоном, а не первым числом.

## Итоги для дизайна
- **Throughput данных** ограничен obfs-криптой (~245 MiB/s на крупных пакетах) и фиксированным
  per-packet оверхедом, а не разбором пакетов. Кеш KDF/cipher — главный рычаг.
- **Аутентификация** (VOPRF-токен + ML-DSA-подпись сервера) — на установление сессии, не на поток; не влияет на скорость туннеля.
- Цифры покрывают добавленное в M3–M5 (паддинг ничтожен; пейсинг — это политика выпуска, не CPU).
