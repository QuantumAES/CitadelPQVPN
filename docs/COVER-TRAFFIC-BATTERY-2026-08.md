# Маскировка трафика: цена в батарее и предложение по доработке

**Дата:** 2026-08-13, обновлено 2026-08-14. **Статус: П1–П8 реализованы** — см. §7 (что именно
сделано, где отступили от предложения и почему). Разделы §1–§6 оставлены как есть: это разбор
состояния «до», и он остаётся точкой отсчёта для замеров.
**Повод:** маскировка постоянно генерирует исходящий трафик и сажает батарею на Android.

Документ отвечает на два вопроса — *что именно и куда уходит* и *что с этим делать* — и служил ТЗ
на заход. Все числа выведены из кода, файлы и строки указаны; замеров на живом устройстве ещё не
было (методика — в §6).

## 1. Коротко

Постоянный исходящий трафик дают **два независимых механизма**, и тумблер «Маскировка таймингов»
управляет только вторым:

| Источник | Когда работает | Провод (простой туннель) | Радио |
|---|---|---|---|
| Собственный keep-alive (M-8) | **всегда**, тумблер ни при чём | ~512 Б каждые 2–4 с ⇒ ~15 МБ/сут вверх + столько же ACK'ов вниз | передача каждые ~3 с — модем не уходит в idle **никогда** |
| Chaff тайминг-шейпинга | только при включённом тумблере | **~25 КБ/с ⇒ ~2.2 ГБ/сутки** | 200 таймерных пробуждений/с + непрерывная передача |

Главная находка: **эти два механизма усиливают друг друга**. Chaff льётся 500 мс после каждой
«реальной» отправки, а keep-alive для него — такая же реальная отправка. Поэтому в **простаивающем**
туннеле маячок каждые 2–4 с сам себе взводит окно chaff, и приложение, которое ничего не передаёт,
отправляет ~2.2 ГБ в сутки мусора. Маскировать при этом нечего: пользовательского трафика нет.

Ни один байт при этом не уходит никуда, кроме exit-сервера, и полезной информации в нём нет
(подробности — §3).

## 2. Откуда числа

### 2.1 Keep-alive (`crates/citadel-quic/src/dataplane.rs:276-293, 1041-1073`)

```rust
fn keepalive_delay() -> Duration {           // равномерно [2, 4] с, заново перед каждой отправкой
    Duration::from_millis(rand::thread_rng().gen_range(2_000..=4_000))
}
fn keepalive_body_len() -> usize { rand::thread_rng().gen_range(0..=96) }
```

Отправляется, только если за окно не ушло ни одной датаграммы (`tx_count` не двигался), то есть
**ровно в простое**. Верхняя граница 4 с выбрана «ниже `keep_alive_interval` quinn (5 с)»
(`crates/citadel-quic/src/lib.rs:209`), а не из свойств сети.

Размер на проводе: тело ≤96 Б + оверхед QUIC ⇒ `quic_len ≈ 85 Б`; L1 паддит политикой
`DEFAULT_RANDOM_PAD {floor: 256, jitter: 512, cap: 1255}`:
`wire = max(55 + 85, 256) + U[0,512] = U[256, 768]`, среднее **512 Б**.

Итог: **171 Б/с ≈ 14.7 МБ/сутки** вверх. Каждая датаграмма подтверждается ACK'ом exit'а, который
паддится той же политикой ⇒ ещё столько же вниз. Всего ≈ **30 МБ/сутки** на пустом туннеле.

### 2.2 Chaff (`crates/citadel-quic/src/obfs_socket.rs:145-206, 427-497`)

Профиль `"on"` (то, что включает тумблер, `app/rust/src/api/citadel.rs:1051`):
`Pacing::Slotted { slot: 5 мс, burst: 32, chaff: Adaptive { window: 500 мс } }`.

```rust
async fn pace_loop(weak: Weak<ObfsUdpSocket>) {
    let mut iv = tokio::time::interval(slot);      // 5 мс ⇒ 200 тиков/с, ВСЕГДА
    loop { iv.tick().await; … s.pace_tick(); }
}
fn pace_tick(&self) {
    …
    if sent_real == 0 {                            // слот пуст
        if chaff_decision(chaff, true, idle) {     // Adaptive: idle ≤ 500 мс
            let sealed = self.seal_chaff(dst);
            let _ = self.inner.load().try_send_to(&sealed, dst);   // мимо congestion control QUIC
        }
    }
}
```

`last_real` обновляется в `pace_tick` на **любой** выпущенной из очереди датаграмме — включая
keep-alive.

Размер chaff (`seal_chaff`): `wire = 256 + U[0, 999]`, среднее **755 Б**.

Простой туннель:
* каждые ~3 с keep-alive ⇒ окно 500 мс ⇒ `500/5 = 100` пустых слотов ⇒ 100 chaff-пакетов;
* 100 × 755 Б ≈ **75.5 КБ на один маячок**;
* ⇒ **25.2 КБ/с в среднем (≈0.2 Мбит/с), пиками 151 КБ/с (1.2 Мбит/с) внутри окна**;
* ⇒ **≈ 90 МБ/час, ≈ 2.18 ГБ/сутки**.

Ответных ACK'ов chaff не вызывает (приёмник дропает его до QUIC, `obfs_socket.rs:555`), так что
нисходящий трафик не растёт — но восходящий поток идёт мимо congestion control и на слабом uplink
конкурирует с полезным.

Профиль `Chaff::Always` (доступен через `Citadel_PACING`) даёт 200 пак/с непрерывно —
**1.2 Мбит/с, 13 ГБ/сутки**.

### 2.3 Почему это именно батарея, а не только трафик

1. **Радио.** У LTE после передачи модем удерживает RRC_CONNECTED ещё 5–10 с (tail timer). Пакет
   раз в 2–4 с всегда попадает внутрь хвоста ⇒ модем не возвращается в idle **никогда**. Разница
   между «в связи» и «в простое» — примерно 100–300 мВт против единиц милливатт; на аккумуляторе
   ~15 Вт·ч это порядка **десятков процентов заряда в сутки** только за удержание канала. Этот
   расход есть даже при выключенном тумблере — его создаёт keep-alive.
2. **CPU.** `interval(5 мс)` — 200 пробуждений в секунду у процесса, который держит foreground-сервис
   и потому не усыпляется Doze. Работы на тик почти нет, но регулярный таймер такой частоты не даёт
   ядру уходить в глубокие C-состояния.

### 2.4 Побочные находки

* **Chaff отличим по длине от данных.** Комментарий в `seal_chaff` утверждает, что распределение
  длин совпадает с DATA при `Random`-паддинге. Это не так: DATA получает
  `wire ∈ [max(55+quic_len, 256), +512]` (для мелких пакетов — 256…768), а chaff — равномерно
  256…1255. В простое на проводе видны «редкие пакеты 256–768» и «частые 256–1255» — chaff
  становится собственным признаком, то есть работает против своей же цели.
* **Потолок пропускной способности.** `burst = 32` за слот 5 мс ⇒ 6400 пак/с ⇒ ~61 Мбит/с потолка
  и +2.5 мс средней задержки при включённой маскировке.
* **У chaff нет бюджета.** Ни байтового, ни временного: сколько слотов, столько и пакетов. На
  мобильном тарифе это неограниченная статья расхода.
* **Exit по умолчанию не шейпит** — `Citadel_PACING` инсталлятором не выставляется (проверено по
  `docker/`, `packaging/`, `tools/`), так что нисходящего chaff сейчас нет. Это надо сохранить.

## 3. Что именно и куда передаётся

Оба потока идут **только на UDP-эндпоинт exit-сервера того же профиля** — тот же 5-tuple, что и сам
туннель (`last_dst` в `pace_tick` — адрес последней реальной отправки). Никаких других адресатов,
никакой телеметрии, никаких обращений к третьим сторонам.

| | Chaff | Keep-alive |
|---|---|---|
| Что внутри | кадр `TYPE_PAD`, полезной нагрузки нет, тело — нули | датаграмма `CTX_KEEPALIVE`, тело — 0…96 случайных байт |
| Слой | L1 (obfs), **ниже** QUIC | L3 (внутри туннеля), поверх QUIC |
| Шифрование | ChaCha20-Poly1305 на сессионном ключе obfs | шифруется дважды: TLS 1.3 туннеля + L1 |
| Что видит наблюдатель | псевдослучайный поток нужной длины | то же самое |
| Что видит exit | пакет `TYPE_PAD` — отбрасывает | датаграмму `CTX_KEEPALIVE` — отбрасывает |

То есть утечки данных здесь нет: расходуется исключительно канал и питание.

## 4. Предложение

Порядок — по отношению «эффект / риск». П1–П4 и П6 не меняют провод и катятся клиентом отдельно;
П5 требует согласованного деплоя exit'а.

### П1. Keep-alive не должен взводить окно chaff  ← главный

Chaff обязан маскировать **пользовательский** трафик; собственный маячок маскировать не от кого —
он и так неотличим по длине и не несёт информации о поведении человека.

*Как:* `last_real` обновлять не по факту выпуска датаграммы в `pace_tick`, а по движению счётчика
**inner-байтов** туннеля (он уже есть: `citadel_client::traffic_bytes`, счётчики в
`dataplane.rs:295+`). Передать `Arc<AtomicU64>` в `ObfsUdpSocket`; в `pace_tick` сравнивать со
снимком: сдвинулся — «был реальный трафик».

*Эффект:* простаивающий туннель перестаёт слать chaff вообще — **−2.18 ГБ/сутки, −100 % лишнего
трафика в простое**. Объём: ~40 строк + юнит-тест «маячок не порождает chaff».

### П2. Pacer не тикает в простое

*Как:* `tokio::sync::Notify`: `try_send` кладёт в очередь и будит pacer; `pace_loop` ждёт **либо**
уведомления, **либо** дедлайна следующего chaff-слота; когда очередь пуста и chaff политикой
запрещён — просто `notified().await` без таймера. (`Notify` хранит permit, поэтому гонки
«разбудили до `await`» нет.)

*Эффект:* 200 пробуждений/с → 0 в простое. Объём: ~50 строк, поведение под нагрузкой не меняется.

### П3. Бюджет chaff

*Как:* переиспользовать `citadel_quic::ratelimit::TokenBucket` — `chaff_budget` в
`ObfsUdpSocket`; нет токенов на пакет — слот пропускается. Профили: экономный 32 КиБ/мин, обычный
128 КиБ/мин, строгий — без лимита.

*Эффект:* у маскировки появляется предсказуемый потолок, который можно честно назвать в интерфейсе.
Объём: ~30 строк.

### П4. Затухание хвоста вместо плоских 500 мс

Ценность chaff максимальна сразу после всплеска — он прячет, где всплеск кончился. Ровные 500 мс на
200 пак/с дают на порядок больше пакетов при почти той же неопределённости для наблюдателя.

*Как:* геометрический шаг слота 5 → 10 → 20 → … → 320 мс, окно до 2 с.

*Эффект:* при активном пользовательском трафике — **−85 % chaff** при сопоставимой стойкости.

### П5. Адаптивный keep-alive (требует деплоя exit'а)

Интервал 2–4 с продиктован не сетью, а порогом quinn. Реальные NAT-таймауты для UDP — 30–120 с
(RFC 4787 рекомендует ≥2 мин), у CGNAT обычно 30–60 с.

*Как:* в простое — **20–45 с** (по-прежнему случайно: широкий разброс даже лучше для стойкости к
автокорреляции, чем узкий 2–4 с); `max_idle_timeout` 15 → 90 с; `keep_alive_interval(None)` —
иначе штатный PING quinn'а на 5 с начнёт срабатывать сам и вернёт в поток строгую периодичность,
ради ухода от которой всё и делалось.

*Эффект:* передач в эфир в простое **0.33/с → 0.03/с** — модем успевает уйти в idle между
маячками; это самая крупная экономия батареи, и она работает даже с выключенным тумблером.

*Риск и почему приемлем:* мёртвое соединение в простое замечается позже. Но в простое этого никто
не наблюдает, а как только пойдёт реальный трафик — сработает data-path watchdog (4 с), на смене
сети — Android-watchdog (C6/S1). **`max_idle_timeout` эффективно равен минимуму из объявленных
сторонами**, поэтому поднять его в одностороннем порядке нельзя: пункт катится вместе с exit'ом.

### П6. Длины chaff = эмпирические длины данных

*Как:* кольцевой буфер последних ~64 размеров реального провода; `seal_chaff` берёт случайный
элемент оттуда. Буфер пуст (chaff до первых данных) — текущее поведение.

*Эффект:* chaff перестаёт быть отдельным «горбом» в гистограмме длин. Объём: ~25 строк + тест.

### П7. Интерфейс: профиль вместо булева тумблера

`Выкл / Экономно / Строго` с честной ценой рядом («до N МБ/ч, заметный расход батареи») и
пояснением, что маскировка работает, пока идёт трафик. Сейчас тумблер не сообщает ни цены, ни того,
что львиную долю расхода создаёт не он.

### П8. Учитывать состояние устройства (Android)

Отдельного кода почти не требует: после П1 при погашенном экране и отсутствии пользовательского
трафика chaff и так равен нулю. Остаётся не повышать профиль до «строго» на батарее без явного
согласия.

### Совокупный эффект

| Показатель (простой туннель, маскировка включена) | Сейчас | После П1–П6 |
|---|---|---|
| Исходящий мусор | ~2.18 ГБ/сут | ~15 МБ/сут → **~1.5 МБ/сут** (с П5) |
| Пробуждений CPU | 200/с | 0 |
| Передач в эфир | 0.33/с | 0.03/с |
| Chaff при активном трафике | 200 пак/с в каждом окне | −85 % при сопоставимой стойкости |

## 5. Чего делать НЕ надо

* **Выключать keep-alive совсем.** Он держит NAT-биндинг; без него туннель молча умирает за
  ~30–60 с простоя у любого CGNAT.
* **Делать `Chaff::Always` дефолтом.** 13 ГБ/сутки — это не «профиль высокого риска», это неоплачиваемый
  счёт; для такого сценария нужен явный выбор и предупреждение.
* **Включать pacing на exit'е** без per-client сигнала: нисходящий chaff будит радио на приёме и
  бьёт по батарее всех клиентов сразу. Сейчас выключен — так и оставить.

## 6. Как проверить (до и после)

1. **Стенд:** `docker/run-demo.sh`, клиент с `Citadel_PACING=on`, туннель поднят и оставлен в покое
   на 10 минут; считать байты на интерфейсе (`/proc/net/dev` внутри контейнера — tcpdump/tshark в
   образе нет). Ожидаемо сейчас: ~15 МБ за 10 минут; после П1: единицы сотен килобайт.
2. **Диагностика:** добавить в debug-панель счётчик chaff-байт и число тиков pacer'а — иначе
   регрессия «маскировка снова жжёт» опять будет замечена только по батарее.
3. **Устройство:** `adb shell dumpsys batterystats --charged <пакет>` до/после ночного простоя;
   смотреть на «mobile radio active time» — именно он показывает, ушёл ли модем в idle.
4. **Гейт:** прогон демо (15/15) не должен измениться; юнит-тесты `chaff_decision` дополнить
   случаем «маячок не считается реальным трафиком».

## 7. Что сделано (2026-08-14)

Реализованы все восемь пунктов. Ниже — где реализация отличается от предложения и почему; в
остальном сделано как написано выше.

| Пункт | Где | Тест |
|---|---|---|
| П1 окно chaff взводит только пользовательский трафик | `dataplane::user_packets` (счётчик inner-датаграмм, обе стороны) → `obfs_socket::note_user_traffic` | `keepalive_does_not_trigger_chaff`, `chaff_decision_table` |
| П2 pacer не тикает в простое | `pace_parked` + `Notify`, сетка держится `next_slot` | `slot_grid_survives_parking` |
| П3 бюджет chaff | `Pacing::Slotted{budget}` + `TokenBucket` | `chaff_budget_caps_the_flood`, `profiles_carry_a_budget` |
| П4 затухающий хвост | `chaff_step_decision` (5→10→…→320 мс, окно 2 с) | `chaff_tail_decays_geometrically` |
| П5 редкий keep-alive | `keepalive_delay(relaxed)` + подсказка в капсуле + `IDLE_TIMEOUT` 90 с | `relaxed_keepalive_requires_peer_confirmation`, `idle_hint_is_backward_compatible` |
| П6 длины chaff = эмпирические | `WireHist` (64 последних длины провода) | `chaff_length_follows_real_traffic` |
| П7 профиль вместо тумблера | `off`/`lite`/`on` сквозь ядро → FFI → GUI (9 языков) | `flutter test` (полнота ключей) |
| П8 состояние устройства | `PowerManager.isPowerSaveMode` → `set_power_save` → понижение `on`→`lite` | — (платформенное, проверяется на устройстве) |

Гейты: `cargo test --workspace` — 0 провалов; clippy чисто; `flutter analyze` чисто; `flutter test`
40/40; `:app:compileDebugKotlin` собирается; демо в docker — 32 проверки, провалов нет.

**Отступления от предложения:**

1. **Редкий маячок — 15–28 с, а не 20–45 с.** У CGNAT UDP-биндинг живёт обычно 30–60 с, и
   обновлять его обязан ИСХОДЯЩИЙ трафик (RFC 4787 REQ-6; обновление по входящему не гарантировано
   ничем). Маячок в 45 с на таком NAT терял бы биндинг между отправками: туннель в простое молча
   умирает, а человек узнаёт об этом, когда достаёт телефон и ждёт реконнекта. Разница в батарее
   между 21 с и 32 с средних несопоставима с этой ценой.
2. **На exit'е keep-alive убран совсем** (в предложении этого не было). Иначе выигрыш съедался бы
   наполовину: встречный маячок exit'а будит радио телефона на приём и вынуждает его ответить
   ACK'ом, то есть эффективная частота передач у клиента удваивалась. Держать NAT-биндинг обязана
   сторона за NAT, а мёртвого клиента exit убирает по idle-таймауту.
3. **Редкий режим включается только по подсказке пира.** Эффективный `max_idle_timeout` — минимум
   из объявленных сторонами, а quinn его наружу не отдаёт. Поэтому exit называет своё значение
   необязательным хвостом капсулы `ADDRESS_ASSIGN`; старый клиент хвост игнорирует, новый клиент
   без хвоста остаётся на 2–4 с. Итог: П5 катится **без** согласованного деплоя — старая и новая
   стороны совместимы в любой комбинации, просто выигрыш появляется, когда обновлены обе.
4. **«Строго» — с бюджетом 128 КиБ/мин, а не без лимита.** Профиль без потолка в интерфейсе — это
   неоплачиваемый счёт на мобильном тарифе (§5). Constant-rate остался, но только явным выбором:
   `Citadel_PACING=max` либо ручная форма без бюджета.
5. **Диагностика (§6.2) сделана строкой в журнале ядра, а не панелью:** счётчики chaff-байт,
   пакетов, пропусков по бюджету и пробуждений pacer'а печатаются окном watchdog и только когда
   chaff реально шёл. Отдельная панель потребовала бы FFI+UI ради числа, которое нужно раз в жизни.

### 7.1 Замер на стенде (§6 п. 1–2, 2026-08-14)

`docker/run-demo.sh` с `Citadel_PACING=on` у клиента; после «Готово.» туннель оставлен в покое,
счётчики сняты с `eth0` клиентского контейнера (`/proc/net/dev`).

| Что мерили | Результат |
|---|---|
| Простой, 120 с | **6.2 КБ вверх / 5.6 КБ вниз** — 17 и 18 пакетов, т.е. ~51 Б/с. По старой схеме за те же 120 с ушло бы ~3 МБ chaff (25 КБ/с, §2.2): **разница ~500×** |
| После реального трафика (ping через туннель) | за ~50 с ушло 3.6 КБ / 14 пакетов — ping плюс затухающий хвост в ~10 пакетов, ровно как предписывает П4 |
| Пробуждения pacer'а | 3 626 за весь прогон (~5 мин активных тестов). При старой сетке `interval(5 мс)` их было бы ~60 000 — **П2 работает на живом туннеле** |
| Бюджет chaff | сработал: «16 пропущено по бюджету» в диагностической строке |
| Живучесть при редком маячке | после 120 с простоя `ping` через туннель прошёл сразу (0% потерь, RTT 53 мс) — сессия не разорвалась и не переподключалась |
| Демо целиком | 32 проверки, провалов нет (капсула с подсказкой idle совместимость не сломала) |

Диагностическая строка из §6 п. 2 выглядит так:

```
[pump] маскировка: chaff 27 КБ за 8с (222 пакетов всего, 16 пропущено по бюджету, 3626 пробуждений pacer'а)
```

**Чего это НЕ отменяет:** замеров на живом устройстве (§6 п. 3) не было — `dumpsys batterystats`
после ночного простоя на телефоне никто не снимал, и «mobile radio active time» до/после не
сравнивался. Выигрыш по радио выведен из интервалов, а не измерен.
