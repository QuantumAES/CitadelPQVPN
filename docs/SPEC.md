# CitadelPQVPN — постквантовый консьюмерский VPN

**Техническая спецификация v0.1 (черновик)**
Рабочее кодовое имя: **CitadelPQVPN**
Дата: 2026-06-18
Профиль: consumer VPN · QUIC/MASQUE · Rust · гибрид X25519+ML-KEM-768 · упор на анти-DPI и приватность

---

## 0. Цели и не-цели

### Цели
- **Постквантовая конфиденциальность сейчас** — защита от *Harvest-Now-Decrypt-Later*: весь обмен ключами гибридный (классика ⊕ решётка).
- **Цензуроустойчивость** — трафик неотличим от обычного веба для DPI; устойчивость к активному зондированию; работа в сетях с блокировкой UDP.
- **Приватность по умолчанию** — no-logs, минимизация метаданных, анонимная аутентификация (провайдер не может связать сессию с личностью).
- **Crypto-agility** — алгоритмы версионируются и заменяемы без слома протокола (готовность к переходу на HQC/смене параметров).
- **Кроссплатформенность** — единое ядро на Rust (Linux/Windows/macOS/iOS/Android), userspace.
- **Производительность** — пригодность для стриминга/браузинга; bewusst congestion control; миграция соединений при смене сети.

### Не-цели (явно вне области)
- Защита от компрометации эндпоинта (вредонос на устройстве пользователя).
- Стойкость к глобальной корреляции трафика (это однохоповый VPN, не Tor; анонимность от глобального наблюдателя не гарантируется).
- Формальный комплаенс FIPS/CNSA 2.0 (выбран профиль «без комплаенса» — приоритет гибкости; см. §3, миграция на 1024 возможна).
- Постквантовая *аутентификация* как срочная задача — см. §3.2 (обоснование, почему аутентификацию допустимо оставить классической на этапе 1).

## 1. Модель угроз и модель доверия (кратко)

> Полноценный STRIDE-разбор — отдельный документ. Здесь — рамка, на которой стоят решения.

### Противники
| # | Противник | Возможности | Наша защита |
|---|---|---|---|
| A1 | **Пассивный глобальный наблюдатель + будущий CRQC** | Пишет весь трафик сегодня, расшифровывает после появления квантового компьютера | Гибридный KEM (§3): секрет стоек, пока стойка хотя бы одна из двух схем |
| A2 | **Активный DPI-цензор** | Классификация и блокировка по сигнатурам протокола/SNI/размерам/таймингам | Обфускация + ECH + padding (§7); неотличимость от HTTP/3 |
| A3 | **Активный пробер** | Шлёт пробы на подозрительные серверы, ждёт «вынуждающего» ответа | Probe-resistance: сервер молчит/отдаёт decoy без знания obfs-ключа (§7) |
| A4 | **Сам VPN-провайдер** (honest-but-curious) | Видит exit-трафик, может пытаться логировать/деанонимизировать | Анонимные токены (§8), no-logs, разделение биллинга и трафика |
| A5 | **Сетевой MITM на пути** | Подмена/инъекция пакетов, downgrade | TLS 1.3 over QUIC, downgrade-protection (§3.3), pinning |

### Доверие
- Клиент **доверяет** ключу/сертификату своего exit-сервера (pinning + PKI).
- Клиент **минимально доверяет** провайдеру в части приватности → анонимная аутентификация, чтобы провайдер технически не мог связать оплату с трафиком.
- Сервер **не доверяет** входящим соединениям до прохождения obfs-гейта (анти-зондирование).

## 2. Слоистая архитектура

Слои строго разделены и общаются через узкие интерфейсы (Rust-трейты). Каждый слой заменяем независимо — это и есть основа crypto-agility и pluggable-обфускации.

```
            КЛИЕНТ                                              СЕРВЕР (exit)
┌─────────────────────────────────┐                ┌─────────────────────────────────┐
│ L4  Control / Privacy            │                │ L4  Control / Privacy            │
│  · анонимные токены (Privacy Pass)│◀─── auth ────▶│  · валидация токенов (unlinkable) │
│  · выбор сервера, kill-switch    │                │  · no-logs, политика выхода       │
├─────────────────────────────────┤                ├─────────────────────────────────┤
│ L3  Data plane / Tunnel          │   IP-пакеты    │ L3  Data plane / Tunnel          │
│  · TUN-устройство                │◀═══ MASQUE ═══▶│  · декапсуляция, NAT, маршрут      │
│  · CONNECT-IP (RFC 9484)         │  CONNECT-IP    │  · DoH/DoQ резолвер, leak-protect │
│  · DPLPMTUD, MSS-clamp           │                │                                   │
├─────────────────────────────────┤                ├─────────────────────────────────┤
│ L2  PQ-сессия / TLS 1.3 over QUIC│                │ L2  PQ-сессия / TLS 1.3 over QUIC │
│  · hybrid KEX X25519MLKEM768     │◀── handshake ─▶│  · hybrid KEX, ECH-decrypt        │
│  · ECH, suite-negotiation        │                │  · server cert (Ed25519[+ML-DSA]) │
│  · QUIC key-update (rekey/PFS)   │                │                                   │
├─────────────────────────────────┤                ├─────────────────────────────────┤
│ L1  Обфускация / Pluggable Transp│                │ L1  Обфускация / Pluggable Transp │
│  · obfs-гейт (probe-resistance)  │◀── obf frame ─▶│  · проверка obfs-ключа, decoy     │
│  · padding, keystream-wrap       │                │                                   │
├─────────────────────────────────┤                ├─────────────────────────────────┤
│ L0  Транспорт                    │                │ L0  Транспорт                    │
│  · UDP/443 (QUIC) ▸ осн.         │◀── datagrams ─▶│  · UDP/443 ▸ осн.                 │
│  · TCP/443 fallback (QUIC-in-TCP)│                │  · TCP/443 fallback              │
└─────────────────────────────────┘                └─────────────────────────────────┘
```

**Поток данных (упрощённо):** приложение → ОС-маршрутизация → TUN → инкапсуляция в CONNECT-IP → QUIC DATAGRAM → [obfs-wrap] → UDP → … → сервер → [obfs-unwrap] → QUIC → декапсуляция → NAT → интернет.

### Ключевое архитектурное решение: L0/L1 отделены от L2
QUIC обычно сам себе транспорт. Мы вставляем **L1 (обфускацию) между L0 и QUIC**, потому что у QUIC есть распознаваемые DPI-инварианты (поле версии, форма long-header, фиксированные биты). Obfs-слой заворачивает байты QUIC в keystream, убирая инварианты, и добавляет probe-resistance-гейт. Это позволяет менять стратегию маскировки (mimicry ↔ fully-random ↔ domain-fronting) **не трогая** криптоядро L2.

## 3. Криптопрофиль и crypto-agility

### 3.1 Обмен ключами (приоритет №1 — защита от HNDL)
- **Гибридная группа `X25519MLKEM768`** (IANA codepoint `0x11EC`) в TLS 1.3 поверх QUIC.
- Комбайнер — стандартный TLS-hybrid (конкатенация общих секретов в KDF транскрипта); реализован в `rustls` через PQ-провайдер.
- **Свойство:** сессионный ключ стоек, пока стойка ⩾ 1 из {X25519, ML-KEM-768}. Это защищает и от взлома решёток (классика держит), и от квантового противника (ML-KEM держит).
- **PFS:** эфемерные ключи на каждое соединение + периодический QUIC key-update.

### 3.2 Аутентификация (этап 2 — обоснованно не срочно)
Аутентификацию задним числом подделать нельзя: forging требует существования CRQC *в момент* хендшейка. Поэтому на этапе 1 допустимо:
- **Сервер:** сертификат `Ed25519` (крошечный → не раздувает хендшейк, см. §11) + pinning.
- **PQ-аутентификация без раздувания:** подмешивание внешнего PSK (`PSK_tls_auth`) в key schedule TLS 1.3 (RFC 8773) — **+0 байт**, переиспользует уже распространяемый секрет, держит форму обычного TLS (mimicry).
- **Если нужна PQ-подпись в цепочке:** `Falcon-512` (~1.6 КБ) вместо `ML-DSA-65` (~5.3 КБ); ML-DSA-65 — только опция crypto-agility.

> Полный разбор альтернатив (с размерами и обоснованием) — **[docs/AUTH-ALTERNATIVES.md](AUTH-ALTERNATIVES.md)**.

### 3.3 Реестр шифрсьютов и crypto-agility
Версионируемый идентификатор профиля, согласуется в L2. Downgrade защищён транскриптом TLS 1.3 + минимально допустимым профилем, заданным в политике клиента (клиент **отвергает** соединение ниже минимума).

| Suite ID | KEX | AEAD | Подпись сервера | Статус |
|---|---|---|---|---|
| `CitadelPQVPN-1` (default) | X25519MLKEM768 | ChaCha20-Poly1305 | Ed25519 | активен |
| `CitadelPQVPN-1a` | X25519MLKEM768 | AES-256-GCM | Ed25519 | активен (если есть AES-NI) |
| `CitadelPQVPN-2` | X25519MLKEM768 | ChaCha20-Poly1305 | Ed25519+ML-DSA-65 | этап 2 |
| `CitadelPQVPN-H` (резерв) | X25519 + **HQC** | ChaCha20-Poly1305 | Ed25519 | заложен на случай взлома решёток |

- AEAD: ChaCha20-Poly1305 по умолчанию (мобильные без гарантии AES-NI), AES-256-GCM при наличии аппаратного ускорения. **Симметрику не меняем** — Grover не пробивает 256 бит.
- Хеш/KDF: SHA-256/HKDF (TLS), BLAKE3 для внутренних KDF obfs-слоя.
- Параметры на `*-768`/уровень 3. Миграция на `*-1024` — смена suite, без слома протокола (готовность к CNSA 2.0, если профиль изменится).

## 4. Протокол хендшейка

Хендшейк трёхфазный. Фаза 0 (obfs-гейт) — наша надстройка; фазы 1–2 — стандартные QUIC/TLS/MASQUE, что даёт нам аудированную крипту и неотличимость от настоящего HTTP/3.

```mermaid
sequenceDiagram
    participant C as Клиент
    participant S as Сервер (exit)

    Note over C,S: ФАЗА 0 — Obfs-гейт (probe-resistance), ключ K_obf роздан вне канала
    C->>S: Obfs-Init [salt | AEAD_{K_obf}(magic,ts,nonce,pad)]
    Note right of S: проверка тега и окна ts;<br/>при провале — МОЛЧАНИЕ или decoy-HTTP
    S->>C: Obfs-Resp [salt' | AEAD(...)]  (только при валидном Init)
    Note over C,S: выведен per-conn keystream → все байты QUIC заворачиваются

    Note over C,S: ФАЗА 1 — QUIC + TLS 1.3, гибридный PQ-KEX (1-RTT)
    C->>S: QUIC Initial: ClientHello {ECH, group=X25519MLKEM768(ek_C), suites=[CitadelPQVPN-1,...]}
    S->>C: QUIC Initial/Handshake: ServerHello {ct (ML-KEM), key_share(X25519)} ,<br/>EncryptedExtensions, Certificate(Ed25519), CertVerify, Finished
    C->>S: (Handshake) Finished
    Note over C,S: общий секрет = KDF(X25519_ss ‖ MLKEM_ss ‖ transcript) → PFS, PQ-safe

    Note over C,S: ФАЗА 2 — MASQUE-туннель поверх HTTP/3
    C->>S: HTTP/3: Extended CONNECT → :protocol=connect-ip (RFC 9484)
    S->>C: 200 OK {assigned IP/prefix, routes, MTU, DNS}
    Note over C,S: туннель готов → IP-пакеты как QUIC DATAGRAM (RFC 9221)

    Note over C,S: ФАЗА 3 — Data plane (стационарная)
    C->>S: DATAGRAM [ctx_id | IP-пакет]  (через TUN)
    S->>C: DATAGRAM [ctx_id | IP-пакет]  (NAT ↔ интернет)
```

### Замечания по фазам
- **Фаза 0** гейтит активное зондирование (A3): без `K_obf` сервер не выдаёт ничего, отличимого от закрытого порта / случайного веб-сервера. `ts` + окно + кэш nonce → анти-replay.
  > **Статус реализации (аудит-2, 2026-07):** отдельный Phase-0 gate-хендшейк с `ts`+окном+nonce-cache в текущем транспорте НЕ подключён — L1 несёт сразу `TYPE_DATA` поверх PQ-QUIC. Анти-replay де-факто обеспечивает **внутренний QUIC** (номера пакетов + AEAD отвергают дубликат), а probe-resistance — AEAD-гейт L1 (невалидный тег → молчание). Отдельный obfs-replay-кэш — низкий приоритет (defense-in-depth), т.к. после S0.3 внутри obfs идёт настоящий QUIC/TLS. Данный пункт спеки — целевой дизайн, не текущий код.
- **Фаза 1**: 1-RTT. **0-RTT отключён по умолчанию** — нет PFS и есть replay; для смены сети используем не 0-RTT, а **миграцию соединения QUIC** (тот же Connection ID, новый путь — туннель не рвётся при WiFi↔LTE, PFS сохраняется). Obfs-keystream скоупится на соединение, не на путь → миграция совместима с обфускацией.
- **Фаза 2**: `CONNECT-IP` даёт полноценный IP-туннель (любой протокол, не только TCP/UDP). Альтернатива для лёгких клиентов — `CONNECT-UDP` (RFC 9298).
- **Rekey**: QUIC key-update по объёму/времени; полный рехендшейк по таймеру (ограничение окна HNDL даже при утечке).

## 5. Форматы пакетов (wire format)

### 5.1 Obfs-пакет (L1) — байт-точный формат

> **Актуальный нормативный формат, тест-векторы и KDF — в [docs/PHASE0-OBFS.md](PHASE0-OBFS.md).** Ниже — сводка; этот раздел не дублирует детали, чтобы не было двух источников правды.

Каждая UDP-датаграмма = один obfs-пакет (конструкция в стиле Shadowsocks-2022, симметричная, на PSK; **протокол v2**):
```
nonce_pkt(12, открыто) ‖ enc_header(24) ‖ aead_body(var)
  enc_header = (sid(16) ‖ packet_id(8 BE)) XOR ChaCha20(K_hdr, nonce_pkt)[0:24]
  aead_body  = ChaCha20Poly1305(K_sess(sid), body_nonce, AAD=nonce_pkt‖enc_header)(inner)
  inner      = type(1) ‖ [timestamp(8)|INIT] ‖ [echo_csid(16)|INIT_S] ‖ pad_len(2) ‖ pad ‖ quic_payload
```
- **v2 (M2-full):** `sid` — 16 байт, служит 128-битной per-session солью в `K_sess` (закрывает body-AEAD nonce-reuse под общим PSK: коллизия ключа 2⁻¹²⁸). KDF-контексты `obfs/v2/*`; wire несовместим с v1.
- Демультиплексирование — по зашифрованному `sid` (не по 4-tuple) → бесшовная миграция при смене сети.
- Probe-resistance: невалидный тег AEAD → молчание/decoy. Накладные расходы DATA: 55 Б + padding (было 47 в v1).
- **Ключ канала данных ротируется по эпохам** (H-3): exit принимает current и prev, абонент получает ключ у издателя после Layer-1 — см. [PHASE0-OBFS.md §2.1](PHASE0-OBFS.md) и §8.

### 5.2 QUIC (L0/L2) — стандарт
- Long header (Initial/Handshake) и short header (1-RTT) по RFC 9000; крипто по RFC 9001; DATAGRAM по RFC 9221. **Своего не изобретаем** — берём как есть (важно для неотличимости и для переиспользования аудированной реализации).
- На проводе поверх — обёртка §5.1, поэтому DPI видит не QUIC-инварианты, а псевдослучайный поток (режим fully-random) либо корректный QUIC к фронт-домену (режим mimicry, §7).

### 5.3 Полезная нагрузка CONNECT-IP (L3, RFC 9484)
```
QUIC DATAGRAM payload:
+----------------+-------------------------------------------+
| Context ID (i) |        Инкапсулированный IP-пакет          |
+----------------+-------------------------------------------+
```
- `Context ID` (QUIC varint) = 0 для «сырых» IP-пакетов (по умолчанию). Иные контексты — для будущих режимов (компрессия заголовков и т.п.).
- Внутренний IP-пакет — то, что сгенерировал стек ОС и перехватил TUN.

### 5.4 Контрольные сообщения (L4, поверх HTTP/3-стрима)
- Формат: CBOR (компактно, schema-evolution). Типы: `ServerInfo`, `RekeyHint`, `RouteUpdate`, `Disconnect{reason}`, `TokenRedeem`.

## 6. Data plane (L3)

- **TUN-устройство** на клиенте перехватывает весь исходящий IP-трафик (full-tunnel) или по split-tunnel политике.
- **Инкапсуляция:** IP-пакет → CONNECT-IP payload → QUIC DATAGRAM (ненадёжная доставка, как UDP внутри — правильно для VPN: не делаем TCP-over-TCP meltdown). Надёжные потоки — только для контрол-плейна.
- **MTU:** внешний оверхед = IP+UDP+QUIC-header+obfs+CONNECT-IP. Чтобы избежать IP-фрагментации:
  - **DPLPMTUD** (RFC 8899) для зондирования path MTU;
  - **MSS-clamping** для внутреннего TCP;
  - анонс внутреннего MTU клиенту в `ServerInfo`.
- **DNS:** резолвинг только через туннель, DoH/DoQ на доверенном резолвере; **анти-leak** (перехват :53, блок прямого DNS). 
- **Kill-switch:** при падении туннеля — fail-closed (фаервол-правило блокирует не-туннельный трафик).
- **NAT на сервере:** трансляция внутренних адресов пула в адрес exit; conntrack; политика выхода (порты/ASN) в L4.

### 6.1 Keep-alive и подсказка idle-таймаута (реализовано, 2026-08-14)

- **Свой keep-alive вместо периодического PING.** В простое клиент шлёт датаграмму `CTX_KEEPALIVE`
  (тело — 0…96 случайных байт, приёмник её отбрасывает: это не `CTX_RAW_IP`) со **случайным**
  интервалом; L1 паддит её до того же распределения длин, что и данные. Периодичности в потоке нет
  by-design — ровный маячок сам по себе признак (M-8). `keep_alive_interval` quinn (60 с) остаётся
  страховкой: его таймер сбрасывается на приёме, поэтому при живом маячке он не срабатывает.
- **Два режима интервала:** строгий 2–4 с (по умолчанию) и редкий 15–28 с. Редкий экономит радио
  мобильного устройства, но безопасен только если пир держит достаточный `max_idle_timeout`, а
  эффективное значение — минимум из объявленных сторонами, и наружу quinn его не отдаёт.
- **Поэтому exit называет своё значение сам** — необязательным хвостом капсулы `ADDRESS_ASSIGN`:
  после тела `varint(request_id) ‖ ver(1)=4 ‖ ip(4) ‖ prefix(1)` дописывается `varint(idle_ms)`.
  Пир прежней версии читает ровно свои шесть байт после `request_id` и хвост игнорирует; новый
  клиент без хвоста остаётся на строгом интервале. **Согласованный деплой не нужен: совместимы любые комбинации версий.**
- **Клиент не доверяет значению как числу:** подсказка влияет ровно на выбор одного из двух
  диапазонов (порог — 60 с), сами интервалы заданы константами. Враждебный exit не может ни
  выключить маячок, ни разогнать его.
- **На exit'е собственного маячка нет:** встречный маячок будил бы радио телефона на приём и
  вынуждал отвечать ACK'ом. Держать NAT-биндинг обязана сторона за NAT; мёртвого клиента exit
  убирает по idle-таймауту (`IDLE_TIMEOUT` = 90 с).

## 7. Обфускация и анти-DPI (L1) — первоклассный слой

Декомпозиция: **Pluggable Transport** — Rust-трейт, реализации сменяемы и согласуемы. Это даёт устойчивость к гонке вооружений с цензором без переписывания ядра.

```rust
// эскиз интерфейса
pub trait PluggableTransport: Send + Sync {
    /// Оборачивает соединение L0 (UDP/TCP) в обфусцированный дуплекс для QUIC.
    async fn wrap_client(&self, sock: Socket, params: &ObfsParams) -> Result<ObfStream>;
    async fn wrap_server(&self, sock: Socket, params: &ObfsParams) -> Result<ObfStream>;
    fn name(&self) -> &'static str;
}
```

### Стратегии (две школы, поддерживаем обе)
1. **Fully-random / «выглядит как ничто»** (default для UDP-разрешённых сетей) — поток без инвариантов (модель Shadowsocks-2022/obfs4). Probe-resistance обязательна (фаза 0).
2. **Mimicry / «выглядит как HTTP/3 к реальному домену»** — фронтинг через CDN/реальный TLS-фронт + ECH. Дороже, но переживает политику «блокировать всё неопознанное».
3. **Fallback-транспорты:**
   - **TCP/443**: QUIC-in-TCP (когда UDP/QUIC заблокирован целиком) — частый кейс цензуры.
   - **WebSocket+TLS / HTTPS-туннель** — last resort, максимально похоже на веб.

### Обязательные свойства
- **Probe-resistance:** без `K_obf` сервер неотличим от закрытого порта или decoy-сайта (защита A3).
- **Анти-fingerprint по размеру/таймингу:** рандомизированный padding, опц. константная скорость для чувствительных потоков.
- **ECH** в фазе 1 → скрытие SNI (защита A2).
- **Распространение `K_obf`** — часть подписки/конфига (вне области протокола), ротация ключей.

## 8. Control plane и приватность (L4)

- **Анонимная аутентификация** — токены **Privacy Pass** (RFC 9576/архитектура; слепые подписи). Биллинг выдаёт N unlinkable-токенов; при подключении клиент гасит токен — провайдер видит «валидный платящий пользователь», но **не может связать** сессию с аккаунтом/платежом (unlinkability у эмитента — безусловная).
  - **Схема (v2, с 2026-08):** VOPRF (2HashDH) над ristretto255 — та же конструкция, что в Privacy Pass / RFC 9497, в режиме с DLEQ-доказательством. До неё была blind RSA-2048 (RFC 9474); её сняли вместе с крейтом `rsa` и его незакрываемым тайминговым каналом (Marvin, RUSTSEC-2023-0071) — см. аудит-4, M-6/M-10.
  - **Токен не bearer.** У клиента после выдачи остаётся секрет `y`, который **не уходит на провод**; при подключении предъявляется `nonce ‖ MAC_y(домен ‖ TLS-exporter)`. Перехваченное предъявление бесполезно в чужой сессии. `cert_pin` в контекст намеренно НЕ входит: у клиента он нулевой в беспиновом dev-режиме, контексты сторон разошлись бы, а привязка к узлу и так есть — pin проверяется на TLS-слое (fail-closed), и сам exporter зависит от сертификата сервера. В blind RSA такая привязка недостижима в принципе (там на провод уходит сама подпись) — это и было остаточным пунктом находки H-2.
  - Заметка по PQ: **unlinkability информационно-теоретическая и от квантового противника не страдает** — ослеплённый элемент равномерен и статистически независим от nonce, поэтому HNDL к анонимности неприменим (то же было верно и для blind RSA). Классической остаётся только **неподделываемость**: CRQC, вычислив ключ ЭПОХИ, чеканит токены — но лишь онлайн (ключ живёт эпоху) и лишь будучи действующим абонентом (публичный элемент эпохи отдаётся только после Layer-1, который уже гибридный Ed25519+ML-DSA). PQ-anonymous-credentials (решёточные слепые подписи) незрелы → **future work**.
- **Выдача разнесена во времени с сессией (§7.1 аудита-4, заход 7).** Unlinkability скрывает, КАКОЙ
  токен предъявлен, но не скрывает от издателя, что абонент `client_id` с адреса *IP* обратился к
  нему в момент *t*; сессия на exit'е начиналась в *t + ε*, и корреляция была тривиальной — а при
  `--role all` издатель и exit ещё и одна машина. Поэтому клиент держит **кошелёк**: токены и ключ
  L1 берутся пачкой на эпоху (границы эпохи приезжают в кадре эпохи `0x02`), реконнекты внутри
  эпохи обращений к издателю не порождают, а дозаправка идёт фоном со случайной задержкой и —
  когда туннель поднят — **сквозь туннель**, то есть с адреса exit'а. Плата: отзыв абонента
  действует на честного клиента с задержкой ≤ эпохи. Остаток, неустранимый в коде: раз в эпоху
  издатель всё же видит `client_id`; лечится только разнесением ролей по администрациям.
  **Токен тратится только предъявлением.** Попытка подключения, не дошедшая до control-обмена
  (закрытый порт, нет сети, разошёлся ключ L1), токен не расходует: цикл реконнекта идёт с тем же
  токеном. Иначе шторм ретраев к недоступному exit'у выгребал квоту эпохи (A6) за считанные минуты,
  после чего издатель прекращал выдачу — и абонент оставался без связи до конца эпохи, с диагнозом
  «издатель не ответил на первый ослеплённый элемент» вместо настоящей причины.
- **Ссылка доступа — одноразовая и срочная (M-9, §18 аудита-4).** `citadel://` несёт секреты
  инлайн, поэтому бессрочная многоразовая ссылка = предъявительский секрет, который делится молча.
  Абонентская ссылка выпускается с окном активации (24 ч по умолчанию) и **активируется на одном
  устройстве**: клиент создаёт свой Layer-1 ключ, подписывает его ключом из ссылки (домен
  `pqid/enroll/v1` + EKM), подписка переезжает на устройство, запись ссылки становится `consumed`.
  Подмену при доставке ловят два независимых механизма: **отпечаток** канонической формы ссылки
  (издатель запоминает его при выдаче и сверяет при активации) и **код сверки** для передачи
  голосом. Подписи внутри ссылки нет намеренно: ML-DSA не помещается в QR, а классическая подпись
  защищала бы не от того противника (разбор — §18.2 аудита-4). **Код сверки СПРАШИВАЕТСЯ при
  импорте** (GUI — поле рядом с превью ссылки, CLI — `add --code`): показывать его «к сведению»
  бессмысленно, потому что сравнение по другому каналу — единственная проверка, которую подменивший
  ссылку не может подделать; без совпадения профиль не сохраняется. Требование действует для
  первичных (одноразовых) ссылок — у розданных раньше многоразовых кода нет.
- **No-logs:** не храним соответствие {внутренний IP ↔ источник ↔ время}; conntrack живёт в RAM, без персиста.
- **Минимизация метаданных:** разделение сервиса биллинга и серверов трафика; никаких аналитик на эндпоинтах.
- **Ротация ключа L1 — реализована (H-3, аудит-4).** Ключ канала данных выводится из серверного
  мастер-секрета на номер эпохи (`PSK_epoch(e) = KDF(MASTER_L1, e)`) и выдаётся абоненту издателем
  **после Layer-1**, тем же обменом, что и токены. Мастер в ссылки не попадает; PSK из `citadel://`
  остался бутстрапом канала к издателю. Следствие: `revoke` гасит и L1-доступ (со следующей эпохи),
  а утёкшая ссылка перестаёт быть бессрочным классификатором трафика деплоя. Нормативно —
  [PHASE0-OBFS.md §2.1](PHASE0-OBFS.md).
- **Выбор сервера и конфиги** — через L4.

### 8.1 Admin-плоскость (C7): управление реестром абонентов по туннелю

Выдача/отзыв доступа (Layer-1 реестр у issuer) управляется **in-band, из-под поднятого туннеля** — SSH-канал для этого не нужен и публичная поверхность сервера не растёт (наружу по-прежнему только порты туннеля, obfs-fallback и издателя; их номера задаются при установке, а по умолчанию порт туннеля и порт издателя **выбираются случайно** — прежние 4433/7000 были узнаваемой подписью деплоя, M-8; 443/tcp у obfs-fallback остаётся как камуфляж под HTTPS):

- **Транспорт:** TCP к `ADMIN_VIP:admin_port`, где `ADMIN_VIP` = шлюз туннеля (`Citadel_TUN_ADDR` exit'а; on-link для клиента и в split-tunnel). Data-plane exit'а пропускает этот поток точечно (после анти-спуфинга inner-src, мимо egress-фильтра F2) и DNAT'ит на issuer **только с туннельного интерфейса** — снаружи порт закрыт (проверяется харнесом, ТЕСТ 22).
- **Канал:** PQ-TLS с тем же `issuer_pin`, что у token-fetch (одна TLS-идентичность issuer'а). **Обе стороны аутентифицируются пост-квантово** (см. §8.2): издатель — первым кадром, админ — гибридной подписью в **отдельном домене** (`CitadelPQVPN/pqid/admin/v1`) с **привязкой к TLS-сессии через EKM** → Layer-1-подпись абонента не переиграть в admin-кадре и наоборот; релей между сессиями невозможен. Провал auth → пауза 1с и разрыв без ack (не оракул). Команды — CBOR (`list`/`add`/`revoke`).
- **Роли ссылок (креды v4):** **мастер-ссылка** несёт `admin_seed`+`admin_port` (только у админа; секрет уровня «управление доступом»); **клиентская** — те же exit/pin/obfs/issuer, но со своим `client_seed` и БЕЗ admin-полей. Выдача нового абонента идёт целиком на устройстве админа: свежий CSPRNG-seed → по каналу регистрируется только pub (client_id) → клиентская ссылка собирается локально. Issuer seed абонента не видит.
- **Приватность:** на сервере — только `pub + срок + статус`; человекочитаемые метки «кому выдано» живут исключительно в зашифрованном vault админа.
- **Одноразовость (M-9) и отзыв.** Ссылки выпускаются первичными: первое устройство активирует ссылку, подписка переезжает на его собственный Layer-1 ключ, а запись самой ссылки становится `consumed` c пометкой `dev=<device_id>`. Отсюда два следствия, которые обязаны выполняться вместе: **отзыв идёт по всей цепочке** «ссылка ⇄ устройство» (иначе админ гасит запись, которую видит с меткой, а доступ продолжает давать устройственная — так и было найдено вживую), и **в списке абонентов пара строк схлопывается в одну** (показывается устройственная, метка наследуется от ссылочной). По той же причине анти-self-lockout считается по цепочке, а не по равенству id: мастер-ссылка админа тоже одноразовая, и его собственный доступ живёт на устройственной записи.
- **Ссылки установщика.** Установщик печатает ТОЛЬКО мастер-ссылку, и та одноразовая (окно активации `--activate-secs`, по умолчанию 24 ч, заверение отпечатком `linkh` в реестре). Отдельной клиентской ссылки он больше не выпускает: она была бессрочной предъявительской и поднимала туннель с любого числа устройств. Практическое следствие принято сознательно: **у администратора одно устройство**.
- **Guard-rails:** отзыв client_id самого админа сервер отклоняет (анти-self-lockout); без файла `admin_id` на issuer канал никого не пускает (secure default).

### 8.2 PQ-идентичность сторон канала издателя (модуль `citadel_token::pqid`)

Конфиденциальность обоих каналов издателя (`:7000` выдача токенов и admin-канал) была
пост-квантовой с A1 — TLS 1.3 с единственной гибридной группой `X25519MLKEM768`. Аутентификация же
оставалась классической, и это давало квантовому противнику два входа:

* **издатель** предъявлял Ed25519-серт, а клиент верил ему по `pin = BLAKE3(DER)`. Pin привязывает к
  конкретному сертификату, но не к владению ключом: CRQC восстанавливает приватный ключ из
  публичного (он лежит в самом серте) и проходит пиннинг «легально» → полный MITM;
* **абонент и админ** доказывали владение ключом Ed25519-подписью, а их публичные данные
  (`admin_id` на сервере, реестр `client_id`) противнику доступны.

Схема после PQ-трека:

- **Одна пара из одного seed.** Из 32-байтного `client_seed`/`admin_seed` (те же поля ссылки)
  детерминированно выводятся **Ed25519 и ML-DSA-65** (FIPS 204 seed→keypair). Обе подписи ставятся
  на одно сообщение и обе обязательны при проверке: подделка требует сломать И классику, И PQ.
- **Идентификатор владельца** `client_id`/`admin_id` = `BLAKE3(ed_pub ‖ mldsa_pub)` — 32 байта,
  формат реестра и файлов прежний, но id теперь покрывает оба ключа (подменить один, сохранив id,
  нельзя).
- **Издатель представляется первым.** Кадр `IssuerHello` = челлендж + ML-DSA pub + подпись
  `DOMAIN_ISSUER ‖ challenge ‖ cert_pin ‖ EKM`; клиент сверяет `BLAKE3(mldsa_pub)` с обязательством
  `issuer_mldsa` из ссылки и только затем отправляет свою идентичность. Не сошлось — разрыв **до**
  раскрытия `client_id` (иначе PQ-MITM собирал бы идентификаторы абонентов = деанон подписки).
- **Постоянство.** Seed издателя (`issuer-mldsa.seed`, 600) переживает рестарт, обязательство
  публикуется в `issuer-mldsa.pin` — иначе рестарт контейнера инвалидировал бы розданные ссылки.
- **Совместимость:** ссылки версии ≤3 отвергаются на разборе с явной причиной («выпущена до
  перехода на пост-квантовую аутентификацию — запросите новую»), потому что их `client_id`
  вычислен по-старому и обновлённый сервер их всё равно не авторизует.

**Что осталось классическим (осознанно):** слепая выдача токенов Layer-2 — VOPRF над ristretto255
(с 2026-08; до этого blind RSA-2048). Практичной PQ-схемы слепой подписи с теми же свойствами
unlinkability по-прежнему нет: единственное семейство — решёточные слепые подписи — не
стандартизовано и не имеет проверенных реализаций. Последствие ограничено: CRQC, вычислив ключ
ЭПОХИ, сможет чеканить токены доступа этой эпохи (кража сервиса), но **не** деанонимизировать
абонентов (ослепление совершенное — задним числом связать выдачу с сессией нельзя никакой
вычислительной мощностью) и **не** расшифровать трафик.

Что изменилось в v2 по сравнению с blind RSA, кроме самого примитива:

- **ключ эпохи больше не публикуется.** Раньше RSA-pub лежал файлом и отдавался по запросу без
  аутентификации — то есть материал для будущей квантовой атаки собирался заранее и тривиально.
  Теперь публичный элемент эпохи уходит только абоненту, прошедшему Layer-1, а сам ключ — секрет
  (`issuer-<epoch>.key`, 0640) и на отдельный exit-узел едет по **двусторонне аутентифицированному**
  keysync-каналу (домен `CitadelPQVPN/pqid/keysync/v1`);
- **exit проверяет токен приватно** (тем же ключом эпохи). Следствие для мультиэкзитных установок:
  ключ обязан выводиться под каждый exit отдельно (`k_exit = KDF(мастер, epoch, exit_pin)`), иначе
  компрометация одного exit'а даёт чеканку токенов, годных на остальных;
- **ротация эпохи стала бесплатной** (генерация ключа — микросекунды вместо ~10 с RSA-keygen).

## 11. Критические инженерные риски (читать до кодинга)

1. **QUIC Initial + большой PQC ClientHello.** Гибридный ClientHello несёт ML-KEM ek (~1184 Б) → CH крупный.
   - *Хорошая новость:* анти-amplification QUIC (3× от полученного) НЕ страдает — наоборот, крупный CH **увеличивает** бюджет ответа сервера.
   - *Реальная забота:* CH может занять **несколько Initial-пакетов** (CRYPTO-фреймы режутся) → реализация должна корректно собирать/слать multi-packet Initial и **не допускать IP-фрагментации** (Initial ≥1200 Б по RFC, но это несколько UDP-датаграм, а не один фрагментированный). `quinn` это умеет — проверить на больших CH.
   - *Следствие для §3.2:* классический Ed25519-серт держит цепочку маленькой; ML-DSA-серт раздувает ответ → включать ML-DSA осознанно, тестировать MTU.
2. **Блокировка UDP/QUIC целиком.** Частый кейс цензуры → **обязателен** TCP/443-fallback (§7). Не опционально для consumer-анти-DPI.
3. **Оверхед инкапсуляции / MTU.** Двойной QUIC (наш + возможный QUIC приложения внутри) + obfs + CONNECT-IP → агрессивный path-MTU и MSS-clamp, иначе чёрные дыры PMTU.
4. **Probe-resistance ≠ опция.** Без фазы 0 сервер палится активным зондированием за часы. Это часть протокола, не «фича».
5. **Downgrade/мисконфиг.** Клиент обязан жёстко отвергать suite ниже политики; pin минимума; не доверять серверному предложению вслепую.
6. **0-RTT соблазн.** Не включать ради «скорости реконнекта» — для смены сети есть миграция QUIC (с PFS). 0-RTT = потеря PFS + replay.
7. **Side-channels PQC.** Только проверенные ML-KEM (aws-lc-rs/libcrux); помнить KyberSlash; не самопис.
