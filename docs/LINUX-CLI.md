# CitadelPQVPN — консольный клиент Linux (трек L)

Клиент для тех, у кого нет графической сессии: сервер, VPS, минималистичный десктоп, работа по
SSH. Настраивается в текстовом интерфейсе, живёт как служба systemd, профили хранит в том же
зашифрованном мастер-паролем хранилище, что и Flutter-клиент.

Документ описывает модель процессов, границы доверия и **модель угроз L1–L20** — что именно
защищается, чем и какой ценой. Смежные документы: `CLIENT-ARCH.md` (общая архитектура клиента),
`THREAT-MODEL-STRIDE.md` (сеть/протокол), `SECURITY-ROADMAP.md` (сквозной security-трек).

## 1. Модель процессов

```text
  ┌─────────────────────────────────────────────────────────────────────┐
  │ citadel-cli            обычный пользователь, без привилегий         │
  │   • TUI/подкоманды     • хранилище профилей + мастер-пароль          │
  └───────────────┬─────────────────────────────────────────────────────┘
                  │  AF_UNIX  /run/citadel-vpn/ctl.sock  (0660 root:citadel-vpn)
                  │  типизированные команды: status / connect / disconnect / disarm / events
  ┌───────────────▼─────────────────────────────────────────────────────┐
  │ citadel-vpnd           root, юнит systemd, песочница                │
  │   • TUN, маршруты, DNS, kill-switch, блок IPv6                      │
  │   • супервизор сессии; НЕ разбирает citadel://, НЕ ходит в сеть      │
  └───────────────┬─────────────────────────────────────────────────────┘
                  │  socketpair (fd 3) + SCM_RIGHTS для дескриптора туннеля
  ┌───────────────▼─────────────────────────────────────────────────────┐
  │ citadel-engine         uid citadel-vpn, без capabilities, NO_NEW_PRIVS │
  │   • QUIC/obfs/MASQUE, разбор ссылки, Layer-1 токены                 │
  │   • весь недоверенный ввод — здесь                                  │
  └─────────────────────────────────────────────────────────────────────┘
```

Три процесса — три разных набора прав. Это та же модель, что на Windows (служба `citadel-svc` +
приложение) и на сервере (`drop root → nobody`, F4), только канал передачи туннеля лучше: на Linux
дескриптор уходит через `SCM_RIGHTS`, поэтому пакеты **не копируются** через IPC — движок пишет в
TUN напрямую.

Ключевое свойство: код, который жуёт байты из сети (QUIC, обфускация, ответы exit'а и issuer'а),
не имеет привилегий вообще. Удалённое исполнение кода в парсере даёт атакующему непривилегированного
пользователя без capabilities — не root.

### Что где лежит

| Компонент | Путь | Владелец | Роль |
|---|---|---|---|
| `citadel-vpnd` | `/usr/lib/citadel-pqvpn/citadel-vpnd` | root:root 0755 | демон (systemd) |
| `citadel-engine` | `/usr/lib/citadel-pqvpn/citadel-engine` | root:root 0755 | движок (uid `citadel-vpn`) |
| `citadel-cli` | `/usr/bin/citadel-cli` | root:root 0755 | TUI/CLI пользователя |
| хранилище | `~/.config/citadel-pqvpn/vault.bin` | пользователь 0600 | профили (Argon2id) |
| настройки | `~/.config/citadel-pqvpn/{killswitch,split}` | пользователь 0600 | общие с GUI-клиентом |
| сокет | `/run/citadel-vpn/ctl.sock` | root:citadel-vpn 0660 | управление |

Ни один бинарь не setuid: привилегии даёт systemd, а не бит на файле.

## 2. Установка и работа

```bash
sudo ./tools/install-cli.sh              # бинари, пользователь citadel-vpn, юниты, старт демона
sudo usermod -aG citadel-vpn $USER       # право управлять туннелем (затем перелогиниться)
citadel-cli                              # текстовый интерфейс
```

Неинтерактивно: `citadel-cli status|connect|disconnect|profiles|add|remove|killswitch|split|passwd`.
Журнал демона — `journalctl -u citadel-vpnd -f`.

В интерфейсе клавиши подписаны в нижней строке, полный список — по **`?`** (или `h`); на экранах
ввода, где `?` — часть пароля или ссылки, справку открывает **F1**. Там же сказано главное, чего
по экрану не видно: выход из интерфейса **не** разрывает туннель — сессию держит демон, отключает
только `d` (или `citadel-cli disconnect`).

Секреты не принимаются аргументами: `citadel-cli add` спрашивает ссылку интерактивно (ввод скрыт),
для скриптов — `… | citadel-cli add --stdin`. Попытка передать `citadel://…` в argv отклоняется
с объяснением.

Мастер-ссылка может приехать **парольным блоком** (`-----BEGIN CITADEL MASTER LINK-----`, его
печатает установщик с `--master-password`). `add` узнаёт такой блок и спрашивает пароль отдельным
приглашением — блок и пароль по построению идут разными каналами, поэтому и вводятся раздельно.

## 3. Модель угроз (L1–L20)

Нумерация сквозная по треку; сюда же попадают решения, которые стоило зафиксировать явно.

### Граница привилегий и IPC

**L1 — confused deputy на управляющем сокете. HIGH.**
Локальный пользователь просит демон поднять туннель, поменять маршруты, снять защиту. Аналог W3
на Windows.
*Решение:* сокет `0660 root:citadel-vpn` в каталоге `0750` — право подключиться проверяет ядро по
правам файла. `SO_PEERCRED` используется дополнительно: uid владельца сессии запоминается, чужую
сессию рвать нельзя (кроме root). PID для авторизации **не используется** — он переиспользуется, и
проверка по нему гоночная. Набор операций типизирован: нет ни «выполни команду», ни «прочитай файл
по пути» — иначе член группы читал бы любой файл машины руками root'а.

**L2 — инъекция на границе привилегий. HIGH.**
Маршруты, DNS, CIDR, MTU приходят от непривилегированных процессов и попадают в аргументы
`ip`/`iptables` и в `resolv.conf`.
*Решение:* `crate::valid` — **parse, don't validate**: строки превращаются в `Ipv4Addr`/`u8`, а
аргументы собираются заново из типизированных значений; сырая строка до `Command` не доходит.
Плюс `env_clear()` (ни `PATH`, ни `LD_*`) и абсолютные пути к утилитам, найденные один раз на старте
с проверкой, что бинарь принадлежит root и не писабелен группой/миром.
Отдельная проверка охвата: «в обход» шире `/8` отвергается — иначе скомпрометированный движок
пробил бы дыру во весь kill-switch, а индикатор продолжал бы показывать «защита включена».

**L3 — группа `citadel-vpn` = «сетевой root». MED, принято осознанно.**
Её член может завернуть трафик машины в свой exit. Установщик создаёт группу, но **никого в неё не
добавляет**; в выводе и в этом документе сказано прямо: добавлять только тех, кому доверяете
администрирование сети.

**L4 — TOCTOU и симлинки. MED.**
`/etc/resolv.conf` под `systemd-resolved` — симлинк на stub. Запись «по ссылке» испортила бы сам
stub и после disconnect оставила бы систему без резолвера.
*Решение:* исходное состояние (симлинк/файл/отсутствие) запоминается и восстанавливается как было;
резервная копия — в `/run/citadel-vpn` с правами 0600. Каталог сокета root-only, поэтому подмены
файла сокета быть не может.
*Уточнено (2026-07-26):* новый резолвер ставится **атомарно** — временный файл рядом и `rename`
поверх. Так нет окна «резолвера нет вообще» (было `remove` + `write`) и заменяется сама ссылка, а
не её цель. Где `rename` невозможен — `/etc/resolv.conf` смонтирован bind-mount'ом (контейнеры,
LXC), и переименование поверх точки монтирования даёт `EBUSY` — используется запись «на месте»,
но **только для обычного файла**: писать «по ссылке» по-прежнему нельзя.

### Резолвер (F6): лестница способов

Записать `/etc/resolv.conf` можно не всегда, и раньше это валило сессию целиком: демон отвечал
движку `TunError`, туннель сворачивался, в журнале было «записать /etc/resolv.conf: Read-only file
system». Первым таким случаем оказался **сам юнит**: `ProtectSystem=full` делает read-only не
только `/usr` и `/boot`, но и `/etc` (комментарий в юните утверждал обратное). Исправлено
`ReadWritePaths=/etc`; точечный `ReadWritePaths=/etc/resolv.conf` не годится — systemd делает
bind-mount самого файла, после чего его нельзя ни заменить, ни удалить.

Одного этого мало: read-only `/etc` бывает и по другим причинам (контейнер, immutable-дистрибутив,
`chattr +i`). Поэтому способ настройки резолвера выбирается лестницей — от наименее инвазивного к
самому жёсткому, следующий пробуется только если предыдущий физически невозможен:

| # | Способ | Когда применяется | Как сворачивается |
|---|--------|-------------------|-------------------|
| 1 | запись `/etc/resolv.conf` | обычная система | восстановление сохранённого состояния |
| 2 | `resolvectl dns/domain ~.` | резолвер системы — systemd-resolved (проверяется, что `resolv.conf` смотрит на его stub) | `resolvectl revert <iface>` |
| 3 | `resolvconf -a <iface>.citadel` | есть openresolv/resolvconf | `resolvconf -d` |
| 4 | заворот всего `:53` в туннель (`iptables -t nat`, цепочка `CITADEL_DNS`) | резолвер системы настроить нечем | удаление цепочки и хуков |

Способ 4 делает содержимое `resolv.conf` неважным: куда бы приложение ни спросило, запрос уедет в
туннель. Исключения до DNAT — сам резолвер туннеля (иначе NAT зациклится) и `lo`: переписывать
адрес петлевого пакета нельзя (ядру пришлось бы менять и источник, пакет ушёл бы «марсианином»).
Локальный stub при этом продолжает работать — его собственный апстрим-запрос уже не петлевой и
заворачивается этими же правилами.

#### Почему способ 4 сначала не работал вовсе (два дефекта, найдены вживую)

Симптом у пользователя: консольный клиент подключается, локальные адреса пингуются по сплиту,
интернета нет; GUI-клиент **на той же машине с той же ссылкой работает**. Разница не в ядре, а в
том, что helper GUI запускается через polkit — **без песочницы**, поэтому у него способ 1 проходит,
и ступень 4 никогда не включалась. У демона `/etc` был read-only, включалась ступень 4 — и падала:

1. **`-o` в `filter OUTPUT` после DNAT врёт.** Для локально сгенерированного пакета netfilter
   вычисляет выходной интерфейс один раз, ДО прохода хуков `OUTPUT`. Заворот меняет назначение
   внутри этого прохода: ядро честно перемаршрутизирует пакет в туннель (`skb_dst` → `citadel0`),
   но `-o` для последующих правил **того же прохода** остаётся физическим. В итоге завёрнутый
   запрос не совпадал ни с `-o citadel0 -j RETURN` в `CITADEL_KS`, ни с F6-исключением, и умирал
   в нашем же финальном `DROP` (в счётчиках: сколько пакетов заDNATилось — столько же и дропнулось).
   *Решение:* рубеж для `:53` перенесён в **`mangle POSTROUTING`**, где интерфейс уже фактический,
   а `CITADEL_KS` выпускает `:53` без проверки интерфейса — но **только** когда этот рубеж стоит
   (`dns_guarded`, то есть в ссылке задан резолвер). Проверка стала строже: она ловит любой `:53`
   мимо туннеля, каким бы способом он там ни оказался.
2. **DNAT меняет назначение, но не источник.** Адрес источника выбран по маршруту к
   *первоначальному* резолверу, то есть это адрес локалки; `ip_route_me_harder` его сохраняет.
   Пакет уезжал в туннель с чужим src, и exit обязан был дропать его анти-спуфингом (S0.2/H3) —
   ответа не было бы никогда. *Решение:* цепочка `CITADEL_DNS_SNAT` (`MASQUERADE` на выходе в
   туннель для `:53` к резолверу туннеля) — источником становится адрес туннеля, а conntrack
   разворачивает и DNAT, и SNAT на ответе, поэтому приложение видит ответ от того резолвера, о
   котором спрашивало.

Обе ступени теперь проверяются e2e (`L-ТЕСТ 15`), включая негативный контроль: снятие SNAT обязано
возвращать дефект, а движок — назвать причину («пакеты с чужим адресом источника», см. ниже).
Ступень выбирается принудительно переменной `CITADEL_DNS_FORCE=file|resolved|resolvconf|redirect`
(её задаёт тот, кто пишет юнит): без неё нижние ступени в контейнере не воспроизвести, потому что
`/etc/resolv.conf` там пишется — ровно поэтому дефект и дожил до живой машины.

#### Диагностика на стороне движка

Exit принимает inner-пакет, только если его src равен назначенному адресу (S0.2/H3), поэтому пакет
с чужим src гибнет там **молча** — на клиенте это выглядит как «отправлено много, принято 0».
Теперь клиентский `pump` считает такие пакеты и в окне watchdog говорит вслух: сколько их, какой
был последний src и какой адрес назначен нам. По адресу сразу видна природа: адрес локалки — заворот
без SNAT, `127.0.0.1` — петлевой bind, адрес другого интерфейса — приложение прибито к нему явно.

> **Если EROFS на `/etc/resolv.conf` виден и после обновления — проверьте, что демон перезапущен.**
> Симптом: в журнале ровно старое сообщение `конфигурация туннеля отклонена: записать
> /etc/resolv.conf: Read-only file system`, без строки `[vpnd] … записать не удалось … ищу другой
> способ` (её печатает лестница). Значит работает демон прошлой версии. Причина была в самих
> установщиках: они заканчивались на `systemctl enable --now`, а `--now` на **уже активном** юните
> не делает ничего — `daemon-reload` тоже не перечитывает песочницу работающего процесса. Файлы на
> диске обновлялись, а в памяти оставался прежний демон со старым `ProtectSystem`. Теперь
> установщики делают безусловный `systemctl restart`, а `citadel-cli` (`status`, `version`, шапка
> TUI и перед `connect`) сравнивает mtime `/usr/lib/citadel-pqvpn/citadel-vpnd` со временем старта
> демона и говорит прямо: «работает УСТАРЕВШИЙ демон». Ручное лечение — `sudo systemctl restart
> citadel-vpnd`.

Fail-closed не ослаблен ни в одном варианте: F6-правила (`DROP` на `:53` мимо туннеля, `mangle
POSTROUTING`) ставятся всегда, а если не сработал **ни один** способ — `TunSetup` по-прежнему
отвергается, потому что иначе DNS-запросы ушли бы мимо туннеля. В способах 2 и 4 дополнительно
разрешён `:53` на `lo` — без этого локальный stub оказывался отрезан и DNS не работал вовсе.

Кроме того, если запись `/etc/resolv.conf` не удалась именно из-за read-only `/etc`, демон теперь
объясняет причину и даёт команду: когда юнит **на диске** разрешает запись (`ReadWritePaths=/etc`),
а у процесса `/etc` только для чтения — значит демон живёт со старой песочницей, лечится
`systemctl daemon-reload && systemctl restart citadel-vpnd`. Раньше это выглядело просто как «ушёл
на запасной способ» и не подсказывало, что обычный путь вернуть можно одной командой.

Попутно закрыт накопительный дефект: F6-правила добавлялись на **каждый** `TunSetup`, то есть на
каждый реконнект, а снималась одна копия. После сессии с реконнектами в `OUTPUT` оставались
висеть `DROP` на `:53` к уже мёртвому интерфейсу — DNS не работал и после отключения, причём
причина была неочевидна (тот же класс, что залипший kill-switch). Теперь перед установкой правила
снимаются, а e2e проверяет, что после disconnect в `OUTPUT` не осталось ни одного правила `:53`.

### Хранилище и мастер-пароль

**L5 — секреты в `argv`/`env`. HIGH.**
`/proc/<pid>/cmdline` читает любой локальный пользователь; ссылка `citadel://` — bearer-креды.
*Решение:* пароль и ссылка принимаются только с терминала (эхо снято через `termios`) или со stdin;
ссылка в argv отклоняется с объяснением. Конфиг движку передаётся **кадром по сокету**, не через
командную строку.

**L6 — секреты в памяти привилегированных процессов. HIGH.**
Core dump уезжает в `systemd-coredump` и лежит на диске; swap; `ptrace`.
*Решение:* `LimitCORE=0` в юните и `RLIMIT_CORE=0` + `PR_SET_DUMPABLE=0` для движка;
`ProtectProc=invisible`, `ProcSubset=pid`; ссылка затирается (`zeroize`) в демоне сразу после
передачи движку, пароль и поля ввода — в CLI.

**L7 — права и целостность файла хранилища. MED.**
`std::fs::write` создавал файл с `0644` — шифртекст мог унести любой пользователь машины на офлайн-
перебор.
*Решение (сделано в этой сессии, касается и GUI):* файл создаётся с `0600`, каталог `0700`; есть
тест, проверяющий это после создания и после каждой записи.
*Остаётся:* заголовок хранилища не аутентифицирован (AAD пустой) — подмена файла целиком (откат на
старую копию, подсовывание чужого профиля) не детектируется. Само по себе это не даёт читать чужие
секреты, но «злой профиль» уводит трафик на чужой exit. Пункт в бэклоге: AAD = заголовок +
монотонная ревизия, и показ отпечатка pin/ML-DSA при импорте ссылки.

**L8 — забытая разблокированная сессия. MED.**
TUI в detached-tmux держал бы хранилище открытым вечно.
*Решение:* автолок через 10 минут без нажатий, плюс `l` — закрыть немедленно.

**L9 — автостарт без человека. HIGH by design.**
Vault с паролем и старт до логина несовместимы: если машина открывает хранилище сама, ключ доступен
машине — а значит и тому, кто получил root или диск.
*Текущее решение:* демон **не хранит секретов на диске вообще**; сессию поднимает пользователь из
TUI. Сессия при этом переживает выход из TUI и логаут — она живёт в службе.
*Не сделано (осознанно):* `systemd-ask-password` при старте юнита и запечатывание профиля в TPM2
(`systemd-creds`) для unattended-режима. Оба варианта — следующий инкремент; выбор между ними
меняет свойства at-rest и должен быть явным, а не подразумеваемым.

### Служба

**L10 — окно утечки до подъёма туннеля. HIGH.**
Между загрузкой машины (или `systemctl restart`) и подключением трафик идёт открытым.
*Решение:* opt-in `citadel-lockdown.service` — fail-closed правила **до** поднятия сети
(`DefaultDependencies=no`, `Before=network-pre.target`). Цена названа в самом юните: до подключения
интернета нет вообще, а резолвер закрыт, поэтому в ссылке должен быть адрес exit'а, а не имя.
*Компромисс:* `systemctl stop citadel-vpnd` снимает защиту (иначе остановка службы оставляла бы
машину без сети без явного действия человека) — значит на время `restart` есть окно; кому это
неприемлемо, включают lockdown-юнит.

**L11 — залипшая защита. MED (ловили вживую на GUI-клиенте).**
После краха kill-switch остаётся — это правильно (утечки нет), но выглядит как «пропал интернет».
*Решение:* `citadel-cli killswitch --disarm` и `citadel-vpnd --disarm`; демон при старте громко
пишет в журнал, что защита армирована без сессии; `status` и статусная строка TUI показывают это
красным.

**L11-bis — залипание реконнекта (найдено при проектировании).**
Армированный kill-switch блокирует и сам движок: до `TunSetup` исключений для exit'а нет, значит
`establish` не проходит, `TunSetup` не приходит — и сессия не поднимется никогда.
*Решение:* сообщение `AllowExits`: движок до первой попытки просит открыть точечный доступ к
адресам exit'а и issuer'а; демон валидирует их как IPv4 (`0.0.0.0`/широковещалка отвергаются) и
вставляет `RETURN` в цепочку. Адреса живут всю сессию, поэтому пересборка цепочки на реконнекте не
отрезает issuer'а от добычи Layer-1 токена. Покрыто e2e-тестом L-11.

**L12 — журнал как канал утечки. MED.**
Всё, что демон пишет в stderr, попадает в journald (группа `adm`, ротация, пересылка на удалённый
syslog): адреса exit'ов, ошибки токенов.
*Решение:* секреты не логируются никогда; в журнал идут состояния и диагностика без кред. Ссылки,
токены и пароли не печатаются ни на одном уровне.

**L13 — компрометация парсера = root. HIGH.**
*Решение:* движок — отдельный процесс под `citadel-vpn`, без capabilities, `NO_NEW_PRIVS`,
`RLIMIT_CORE=0`, с единственным каналом к демону. Демон, в свою очередь, ограничен юнитом:
`CapabilityBoundingSet` из шести capability, `ProtectSystem=full` + `ReadWritePaths=/etc`
(без второго `/etc` только для чтения и резолвер не настроить — см. «Резолвер (F6)»), `ProtectHome=yes` (демон
физически не может читать домашние каталоги — хранилище не его дело), `SystemCallFilter=@system-service`,
`MemoryDenyWriteExecute`, `RestrictAddressFamilies`, `DevicePolicy=closed` + точечный
`DeviceAllow=/dev/net/tun rw`.
NB: `ProtectKernelModules=yes` намеренно **не** включён — `iptables` подгружает `ip_tables`/`xt_owner`
при первом применении правил, иначе kill-switch не встанет на свежезагруженной системе.

**L14 — NetworkManager/dhclient перетирают resolv.conf и маршруты. LOW–MED, частично.**
Штатный сценарий (смена сети во время сессии) может вернуть системный резолвер поверх нашего.
*Сделано:* резолвер **переприменяется на каждом реконнекте** (интерфейс после реконнекта новый, и
настройки на прежнем всё равно умерли вместе с ним), а на машинах с systemd-resolved/resolvconf
используются они, а не прямая запись файла (способы 2–3 лестницы) — там перетирание невозможно
конструктивно. *Остаётся:* между реконнектами файл всё ещё может перетереть NM; полноценная
интеграция через NM-dispatcher — в бэклоге.

**L15 — рестарт-шторм. LOW.**
`Restart=on-failure` при неустранимой ошибке = шторм к issuer/exit и характерный для DPI паттерн.
*Решение:* `StartLimitIntervalSec=60` / `StartLimitBurst=5` поверх backoff внутри движка.

### Терминал

**L16 — ANSI/OSC-инъекция. MED.**
Имя профиля из чужой ссылки, текст ошибки от сервера, метка абонента — недоверенные строки, которые
рисуются в терминале. Escape-последовательность в них перерисовывает экран, меняет заголовок окна,
подделывает подсказку.
*Решение:* `sanitize_text` (срезает C0/C1/ESC, ограничивает длину) применяется ко всему, что пришло
извне, и в CLI, и в TUI, и в статусах демона.

**L17 — скролбэк и запись сессии. LOW.**
`citadel://` на экране оседает в буфере терминала и в логе SSH-сессии.
*Решение:* ввод ссылки маскируется по умолчанию (Tab — показать), сохранённые ссылки в интерфейсе
не отображаются вообще.

**L18 — TTY-hijacking (`TIOCSTI`). LOW.**
Закрыто современными ядрами (`dev.tty.legacy_tiocsti=0` по умолчанию); отдельных мер не принимаем.

### Сеть

**L19 — резолв exit'а до туннеля. MED, частично.**
Имя сервера уходит на системный резолвер до подъёма туннеля — утечка метаданных и вектор для
DNS-poisoning (pin спасает от MITM, но не от выбора «удобного» адреса).
*Решение:* ссылка может содержать IP вместо имени — тогда резолв не нужен вовсе (и это единственный
рабочий вариант в lockdown-режиме). Кеширование последнего известного адреса между реконнектами —
в бэклоге.

**L20 — split-tunneling только по назначениям.**
Ось приложений (как на Android) требует cgroup v2 + `ip rule fwmark`; на Linux-десктопе пока
доступен фильтр по IP/CIDR/домену. Инвариант «подсеть туннеля всегда в туннеле» соблюдается общим
кодом `winnet::split_routes` (тот же, что у Windows и GUI).

## 4. Что проверено

Юнит-тесты (23 в `citadel-vpnd`): кадрирование IPC и отказ на кадр сверх лимита/мусор/обрыв;
разбор недоверенного `TunSetup` (инъекции, дегенеративные адреса, лимиты количества, «широкий
обход»); `AllowExits`; форма правил kill-switch и IPv6-блока с проверкой, что финальный `DROP`
идёт после всех `RETURN`; привязка исключения exit'а к uid движка; раскрытие full-tunnel в две
половинки `/1`; зеркальность установки и снятия правил DNS (снятие покрывает оба варианта — с
разрешённым loopback и без); порядок `ACCEPT lo` до `DROP`; форма заворота `:53` (исключения до
DNAT, цель — резолвер туннеля, всё в таблице `nat`) и его полное снятие; `sanitize_text`.

E2E в контейнерах (`bash docker/run-cli-tests.sh`) против настоящих exit и issuer:
прогон юнит-тестов всего воркспейса в чистом окружении (207 тестов) + 13 сценариев на живой
системе, 29 проверок — права сокета, отказ постороннему пользователю, отказ движка работать от
root, подъём туннеля с kill-switch, uid и `CapEff` движка, применённые маршруты и цепочки,
**настроенный резолвер** (любым способом лестницы), реальный трафик через туннель, блокировка
трафика мимо него, поведение при `kill -9` движка, реконнект поверх армированной защиты, чистое
отключение с восстановлением сети и резолвера, **отсутствие накопившихся правил `:53`** после
сессии с реконнектом, `--lockdown` и `--disarm`.
