## 0. Цели и не-цели

### Цели
- **Один UI-код на 5 целей** — Android, Windows (x86-64 + ARM64), macOS, Linux. Единая кодовая база интерфейса.
- **Два режима в одном приложении** — **User** (импорт конфига/ссылки/QR → подключение) и **Admin** (разворачивание сервера в Docker по SSH + выпуск кредов для новых клиентов).
- **Консьюмерское удобство** — выпуск нового клиента и отзыв (по времени/при компрометации) в один клик; авто-рефреш токенов невидим пользователю.
- **Переиспользование ядра** — никакого форка протокола: GUI оборачивает существующие крейты `citadel-*` как библиотеку.
- **Приватность по умолчанию** — exit не линкует сессии с личностью (наследуем модель токенов M5, см. §10).

### Не-цели (явно вне области)
- Переписывание протокола/крипты — фиксировано в `SPEC.md`.
- iOS как обязательная цель этапа 1 (Flutter её поддержит, но в roadmap C* не закладываем как блокирующую — NetworkExtension-нюансы те же, что у macOS).
- Web-клиент (браузер не даёт TUN).
- Самостоятельная установка Docker на сервер без участия админа (детектируем и подсказываем, но не автоустанавливаем молча).

## 1. Контекст: что уже готово и что строим

**Готово (PoC-уровень, M0–M7 ✅):** Rust-воркспейс `citadel-{obfs,masque,tun,token,quic}`; бинарь `citadel-m1` (роли `server|client|probe|auth-probe`, конфиг через `Citadel_*` env, сам открывает TUN через ioctl); `citadel-token` (issuer/client/keysync/batch, анонимные токены VOPRF — до 2026-08 blind-RSA RFC 9474); `docker/` демка (issuer :7000 → exit :4433 + TCP-fallback :443 → client). Гибрид X25519+ML-KEM-768, obfs L1, миграция, multi-server, ML-DSA-65 PQ-auth.

**Строим (трек C*):** клиентское приложение, которое:
1. оборачивает движок как **встраиваемую библиотеку** `citadel-client`;
2. даёт **Flutter-GUI** с режимами User/Admin;
3. в Admin-режиме **разворачивает серверный стек по SSH** и **выпускает креды** (конфиг/ссылка/QR);
4. интегрируется с **платформенными TUN-API** каждой ОС.

## 2. Ключевое архитектурное решение: ядро-как-библиотека

Текущий движок зашит в `bin/citadel-m1.rs`: читает `Citadel_*` env → `open_tun()` (ioctl) → `run_client`. **В таком виде он непригоден для GUI-клиента**, потому что:

- На **Android/iOS** нельзя форкнуть привилегированный процесс и самому создать TUN: ОС отдаёт **файловый дескриптор** туннеля через `VpnService`/`NetworkExtension`, и пакеты гоняются **внутри** процесса приложения.
- GUI должен управлять движком по API (статус, события, переподключение), а не парсить stdout стороннего процесса.

> **Решение:** выделяем крейт **`citadel-client`** — библиотека-«мозг», собираемая как `cdylib`/`staticlib` и линкуемая во все GUI. Бинарь `citadel-m1` остаётся, но обслуживает **только серверную сторону** (в Docker). Движок клиента выносится из бинаря в библиотеку.

Это критический путь всего трека — этап **C0**.

## 4. Ядро `citadel-client` (Rust lib-API)

### 4.1 `TunIo` — абстракция туннеля
Движок больше не открывает TUN сам. Вместо этого работает поверх трейта (живёт в `citadel-tun`; **блокирующий** — `pump` уже изолирует чтение TUN в `std::thread`+mpsc, async тут лишний):

```rust
// crates/citadel-tun/src/lib.rs
pub trait TunIo: Send + Sync + 'static {
    fn recv(&self, buf: &mut [u8]) -> io::Result<usize>;
    fn send(&self, pkt: &[u8]) -> io::Result<usize>;
}
impl TunIo for Tun { /* делегирует к существующим recv/send */ }
```
Реализации: Linux `/dev/net/tun` (текущий `citadel-tun::Tun`); мобилки/десктоп — обёртка над **внешним fd** от ОС (`Tun::from_raw_fd(fd)`). Платформенные обёртки (Android и т.д.) живут в `citadel-client` — orphan-rule соблюдён (тип локальный, трейт чужой).

### 4.2 `ClientConfig` — конфиг-структура вместо env
Все текущие `Citadel_*` становятся полями (env-парсинг остаётся тонкой обёрткой только для бинаря):

| Поле | Источник сейчас | Назначение |
|---|---|---|
| `servers: Vec<Endpoint>` | `Citadel_SERVERS`/`Citadel_CONNECT` | multi-server + failover (M5) |
| `server_name` | `Citadel_SERVER_NAME` | SNI |
| `cert_pin` | `Citadel_PIN`/`PIN_DIR`/`PIN_FILE` | pinning (F1) |
| `mldsa_pub` | `Citadel_MLDSA_PUB`/`_FILE` | PQ-auth (M7) |
| `obfs_psk` | `Citadel_OBFS_PSK` | obfs L1 PSK |
| `kx_suite` | `Citadel_KX` | crypto-agility (M6) |
| `tcp_fallback_port` | `Citadel_TCP_PORT`/`TCP_CONNECT` | :443 fallback (M4) |
| `issuer` + endpoint | `Citadel_ISSUER_KEY` (на exit'е — ключ эпохи) | минт токенов (M5) |
| `routes`, `dns`, `mtu` | `Citadel_ROUTES`/`DNS`/`MTU` | split-tunnel, DoH (F6) |

### 4.3 `VpnController` — управление сессией
```rust
pub struct VpnController { /* … */ }
impl VpnController {
    pub async fn connect(&self, cfg: ClientConfig, tun: Arc<dyn TunIo>) -> Result<SessionHandle>;
    pub fn status_stream(&self) -> impl Stream<Item = VpnEvent>; // Connecting/Up/Migrating/Down + байты, текущий exit
    pub async fn disconnect(&self) -> Result<()>;
}
```
Внутри — уже готовое: `enum Tunnel{Quic,Tcp}`, миграция, multi-server failover, PQ-auth, rate-limit на приёме.

## 5. FFI-граница

## 6. GUI (Flutter)

**User-режим:**
- Импорт: вставить `citadel://`-ссылку, открыть `.citadelconf`-файл, **сканировать QR** (камера на мобилке / из файла на десктопе).
- Большая кнопка Connect/Disconnect, индикатор статуса (поток из `VpnController`), выбор exit, split-tunnel/DNS, kill-switch.

**Что главный экран показывает и чего НЕ показывает (2026-07-31).** Карточка статуса — «Защищено /
Подключение… / Не защищено», узел выхода и транспорт; список профилей — имя, адреса серверов и
чипы возможностей. Ни номеров портов, ни назначенного нам адреса туннеля с маской там нет: человеку
они ничего не объясняют, а скриншот или демонстрация экрана выдают конфигурацию exit'а и адрес
клиента. Всё это осталось там, где нужно для разбора — журнал ядра и «Диагностика подключения»
(режим отладки). Ровно по той же причине из журнала убран hex серт-pin'а: pin — стабильный
идентификатор сертификата конкретного сервера, а журнал уезжает в поддержку целиком (в логе
остаётся факт «серт-pin активен»; несовпадение и так видно по отказу TLS).

**Профили (2026-07-31).** Имя профиля — вывеска, не ключ: ссылка и порядок от него не зависят.
Если пользователь имя не задал, ядро выдаёт `Citadel001`, `Citadel002`, … — первый СВОБОДНЫЙ номер
по именам существующих профилей (после удаления номер переиспользуется, вручную заданное имя не
подменяется). Меню профиля: «Переименовать» и «Удалить». Порядок списка меняется **перетаскиванием**
(долгое нажатие на плитке → плитка «отрывается»: подъём + лёгкое увеличение, `proxyDecorator`), и
он же — порядок записей в vault, поэтому переживает перезапуск и переносится вместе с хранилищем.
Всё это в ядре (`Vault::add|rename|move_to`), так что консольный клиент получает то же поведение.
Пунктов «переместить выше/ниже» больше нет: перенос на нужное место одним жестом — одна запись
файла вместо N, а на списке из нескольких профилей кнопками пришлось бы бить по позиции.

**Индикация трафика (по умолчанию выключена).** Тумблер «Показывать индикацию трафика» добавляет на
плашку подключения текущую скорость приёма/передачи (`↓`/`↑`, обновление раз в секунду). Считает её
UI по дельте **монотонных** счётчиков ядра (`citadel_quic::dataplane::traffic_bytes` → FFI
`traffic_counters`), деля на фактически прошедшее время; итогов за сессию/сутки нет намеренно —
накапливать историю трафика пользователя клиенту незачем, а «скорость сейчас» отвечает на
единственный практический вопрос «туннель вообще возит данные?». Счётчики считают inner-байты
(полезную нагрузку) и ведутся **только на клиенте**: на exit'е это был бы учёт чужого трафика в
общей на процесс переменной — против no-logs.

**Язык интерфейса (2026-08-05).** Девять языков: русский (по умолчанию), английский, немецкий,
французский, испанский, итальянский, чешский, хинди, бирманский. Строки — плоские карты
`ключ → строка` в `app/lib/l10n/lang_*.dart` (русский — эталон набора ключей), доступ через
`Strings.of(context)`; `flutter_localizations` добавлен ради переводов самих Material-виджетов.
ARB/gen_l10n не используется сознательно: второй кодогенератор в релизном конвейере (там уже
FRB-codegen) дороже, чем тест на полноту ключей (`app/test/l10n_test.dart` — паритет наборов,
сохранность плейсхолдеров и проверка, что каждый запрошенный из кода ключ существует). Выбор языка
хранит **ядро** (файл `language` рядом с vault, как kill-switch/debug): язык нужен ДО открытия
хранилища — экран разблокировки уже говорит с человеком. Заголовки отказов подключения хранятся в
состоянии как **ключи**, а не готовый текст, поэтому смена языка перерисовывает и уже показанную
ошибку.

Нативные поверхности берут строки оттуда же, а не из системной локали: постоянная нотификация
Android (`CitadelVpnService`) и меню значка в трее Windows получают их из Dart по MethodChannel
(`setNotifStrings` / `init`) при старте и при смене языка. Иначе приложение говорило бы на одном
языке, а шторка уведомлений — на другом; для нотификации это особенно важно, потому что при
закрытом окне она единственная показывает состояние VPN. Тексты, которые формулирует ядро (ошибки
vault/движка), пока приходят по-русски — их локализация потребует пройти по всем
`anyhow`-сообщениям крейтов и здесь не делалась.

**Admin-режим (реализовано в C7 — по туннелю, без SSH):**
- Admin-профиль = профиль, чья ссылка — **мастер** (несёт `admin_seed`; в UI — чип `admin`, предупреждение «не передавайте её никому» при добавлении).
- Меню admin-профиля → **«Абоненты»** (требует активной сессии этого профиля — канал живёт за туннелем): список реестра с локальными метками, «Выдать доступ» (метка + срок → регистрация pub по каналу → клиентская ссылка + QR, показывается **один раз** — seed абонента у админа не хранится), «Отозвать» (с guard-rail: self-revoke отклоняет сервер). **M-9:** выдаваемая ссылка — ОДНОРАЗОВАЯ и срочная (окно активации 24 ч): она активируется на первом устройстве и после этого мертва, а рядом со ссылкой показывается **код сверки** — его называют абоненту отдельно от самой ссылки (он же ловит подмену при доставке).
  - **Один абонент — одна строка.** После активации в реестре сервера появляются ДВЕ записи (ссылка `consumed` + устройство, которое и даёт доступ); экран показывает устройственную, а метку берёт от ссылочной. Иначе админ отзывал строку, которую узнаёт по метке, и ничего не происходило — доступ жил на второй. Отзыв на сервере гасит обе (см. SPEC §8.1).
  - **Импорт ссылки спрашивает код сверки** (лист «Новый профиль»): для первичных ссылок поле обязательно, несовпадение — отказ сохранить профиль. Правила сравнения (регистр, разделители, `O→0`, `I/L→1`) — `app/lib/verify_code.dart`, у консольного клиента то же самое в `add --code`.
  - **Ожидание ограничено.** Каждая admin-операция имеет потолок 30 с (плюс до трёх повторов при авто-загрузке): раньше не проложенный маршрут к VIP или зависший TLS-хендшейк давали экран, который «крутится вечно». Этапы канала (TCP → PQ-TLS → аутентификация) пишутся в журнал ядра строками `[admin]` — это единственный способ разобрать жалобу на устройстве.
- Разворачивание сервера — bootstrap-скриптом на самом сервере (`tools/install-citadel-server.sh`, C4): печатает мастер- и клиентскую ссылки. SSH-управление реестром из клиента (страница C5.5) **удалено** — заменено туннельным каналом (§10).

## 7. Платформенная TUN-интеграция

Единственный неустранимо-нативный слой — по тонкому плагину на ОС, каждый отдаёт `TunIo` в ядро:

| ОС | Механизм | Привилегии | Заметки |
|---|---|---|---|
| **Linux** | `/dev/net/tun` (есть `citadel-tun`) | `CAP_NET_ADMIN` | privileged helper / polkit / systemd |
| **Android** | `VpnService.establish()` → fd | нет root | маршруты/DNS через `Builder`; ядро берёт fd |
| **Windows** | **WinTUN** (`wintun.dll`, от WireGuard) | elevation | userspace-адаптер; создание через службу |
| **macOS** | `NEPacketTunnelProvider` или `utun` | entitlement / привилегии | App Store ⇒ NetworkExtension + provisioning |

## 8. Admin-режим: разворачивание сервера

> **Статус (2026-07):** актуальный путь деплоя — **bootstrap-скрипт на сервере** (`tools/install-citadel-server.sh`: Docker, keygen на сервере, issuer+exit, мастер-/клиентская ссылки; см. C4). SSH-деплой из GUI ниже — дизайн на будущее; `AdminDeployer` (russh) остаётся библиотечным. **Управление абонентами больше не SSH-операция** — оно ушло в admin-плоскость по туннелю (§10, C7).

### 8.1 Доставка бинаря — из GitHub Release
- **CI** (`.github/workflows/release.yml`): матрица `amd64 + aarch64` (нативные arm64-раннеры — `aws-lc-rs` тянет cmake/C, под QEMU медленно/хрупко). Артефакты: `citadel-m1-{x86_64,aarch64}.zst` (стрип + zstd; сейчас бинарь ~72 МБ), `citadel-token-*`, `sha256sums`, подпись (minisign/cosign).

### 8.2 Деплой по SSH (`russh`)
> SSH-клиент — **`russh`** (чистый Rust, async, без OpenSSL-C). `ssh2`/libssh2 отвергнут: C-зависимость не соберётся под Android/ARM-цели единым ядром.

Поток:
1. SSH-коннект (пароль или ключ), TOFU по host-key.
2. `uname -m` → выбор арки; проверка Docker — **нет → авто-установка** (официальный `get.docker.com` под root; Debian/Ubuntu — наша база, надёжно; RHEL/прочие — best-effort + внятный фолбэк, не молчим).
3. **Сервер сам тянет бинарь** с GitHub Release (`curl` на хосте — не льём 70 МБ через SSH). Фолбэк без egress: админ-приложение качает один раз, кэширует, стримит через sftp.
4. Проверка `sha256` + подписи → `/opt/citadel/bin/citadel-m1`.
5. **Генерация серверных ключей** (на хосте или локально с заливкой): self-signed cert + pin (F1), ML-DSA-65 keypair (M7), ключ эпохи Layer-2 (M5, генерируется мгновенно и ротируется каждую эпоху), obfs PSK.
6. Рендер `compose.yml` + entrypoints → `docker compose up -d`.
7. **Чтение обратно** pin/pubkeys → сборка клиентского бандла (§9).

### 8.3 Dev vs Prod
- **Dev (оптимум итераций):** базовый образ **пинуется один раз** (`debian:trixie-slim` + рантайм-deps), бинарь и ключи идут **bind-mount’ом** (volume). Обновление = заменить файл + `docker compose up -d --force-recreate` — **без `docker build`**. Версия в лейбле `citadel.release=<tag>+<sha>`.
- **Prod:** бинарь **запечён** в образ (воспроизводимость), опционально пуш в GHCR. Переключатель `CITADEL_BINARY_MODE=mount|baked`, единый `compose.yml`.

## 9. Формат кредов: конфиг ↔ ссылка ↔ QR

### 9.1 Две формы
- **Полный бандл `.citadelconf`** (CBOR, либо человекочитаемый TOML) — все ключи инлайн; для импорта файлом / air-gapped.
- **Компактная ссылка/QR `citadel://`** — только **обязательства (хэши)**, полные публичные ключи дотягиваются in-band и проверяются против хэшей (см. 9.3).

### 9.2 Содержимое бандла
endpoints (+TCP/443 fallback), **cert pin** (BLAKE3 DER, 32 B), **ML-DSA-65 pub** (1952 B), **obfs PSK** (32 B), `kx_suite`, **issuer endpoint** (ключ эпохи в ссылку не кладётся — он ротируется), **issuer TLS-pin** (BLAKE3 DER, 32 B — PQ-TLS канал к издателю, S2.1/A1), **обязательство PQ-идентичности издателя** (`issuer_mldsa`, BLAKE3 ML-DSA pub, 32 B — C9), **client-seed** (Слой-1, 32 B, §10; из него выводится гибридная пара Ed25519+ML-DSA-65), routes/DNS/SNI.

### 9.3 QR-ёмкость — узкое место и решение
ML-DSA pub (1952 B) доминирует. Прикидка сырья ≈ 2.5 КБ; QR version 40 byte-mode даёт ~2953 B только на **низшем** уровне коррекции (хрупко), base64url (×1.33) уже **не влезает**. Ключи высокоэнтропийны — сжатие не помогает.

> **Решение (рекомендуется): QR несёт обязательства, не ключи.** В `citadel://` кладём endpoints + `pin(32)` + `H(mldsa_pub)(32)` + `H(issuer_pub)(32)` + `issuer_pin(32)` + `obfs_psk(32)` + `ed25519_seed(32)` + мета ⇒ **~330 B** → влезает даже на высоком уровне коррекции QR. Полные публичные ключи клиент дотягивает при первом коннекте и **сверяет с хэшами из QR**.

**Бонус-свойство (CRQC-safe bootstrap):** обязательство `H(mldsa_pub)` пришло **вне канала** (QR/ссылка). Даже если будущий CRQC сломает классический pin и устроит MITM на дотягивании ключей — он не подберёт ML-DSA pub под заданный SHA-256-хэш (стойкость к прообразу). Out-of-band-обязательство **связывает** PQ-ключ независимо от стойкости транспортного pin.

`.citadelconf` (не-QR) несёт ключи инлайн — для оффлайна/air-gapped.

## 10. Модель идентичности (двухслойная, Privacy Pass production pattern)

**Противоречие:** анонимные токены (M5) **unlinkable** — exit не знает, чей токен, и не может отозвать конкретного юзера. Это максимум приватности, но «отозвать при компрометации» так невозможно. Консьюмерское «создать/отозвать удобно» требует идентичности. Развязка — разнести идентичность и анонимность по слоям.

### Слой 1 — клиентский «абонемент» (отзываемый; на exit НЕ виден)
При «создании клиента» генерим 32-байтный seed, из которого детерминированно выводится **гибридная пара Ed25519 + ML-DSA-65** (C9), используемая **только против issuer’а** — на exit она не уходит; `client_id = BLAKE3(ed_pub ‖ mldsa_pub)`. Issuer держит реестр: `client_id → valid_until, status(active|revoked)`. Здесь вся подотчётность.

### Слой 2 — короткоживущие анонимные токены (unlinkable на exit)
Клиент раз в эпоху (1–24 ч, конфиг) аутентифицируется в issuer по Слою-1 (Ed25519 challenge-response) и получает пачку **blind-подписанных epoch-токенов** (механизм `citadel-token`, но issuer подписывает **ключом эпохи**; epoch_id зашит в подписываемое сообщение). Exit принимает токен только текущей эпохи.

**Канал к issuer'у — PQ-TLS с пиннингом (S2.1/A1).** Весь Слой-1 обмен и слепая выдача идут поверх TLS 1.3 с гибридной группой `X25519MLKEM768` и **пиннингом серта издателя** (`issuer_pin` из ссылки). Это закрыло аудит-2/A1: (a) активный MITM не подставит свои `blind_msg` под чужую Layer-1-авторизацию (кража токенов), (b) `client_id` не светится в открытом виде (деанон подписчика), (c) издатель аутентифицируется клиентом (анти-импёрсонация). Идентичность издателя (TLS-серт) постоянна (переживает рестарт → розданные ссылки не ломаются). **C9:** пиннинг серта дополнен ML-DSA-доказательством владения ключом (первый кадр канала) — против квантового противника один pin не держит, см. SPEC §8.2.

### Свойства
| Требование | Как достигается |
|---|---|
| **Приватность data-path** | exit видит только unlinkable-токены — не линкует сессии к юзеру (даже при сговоре issuer+exit на уровне сессии) ✓ |
| **Отзыв по времени** | нет рефреша (истёк `valid_until`) → токены гаснут к концу текущей эпохи, автоматически ✓ |
| **Отзыв при компрометации** | admin → `status=revoked` → нет новых токенов; немедленность ≤ длины эпохи (берём эпоху короче для жёсткого отзыва) ✓ — и это верхняя граница честного клиента: пачка, взятая до отзыва, догорает до конца эпохи (§17.1) |
| **Удобство** | один QR бутстрапит Слой-1; рефреш токенов невидим (`TokenAgent`, кошелёк на эпоху); «создать»/«отозвать» = клик ✓ |

### Честный трейдофф
Появляется точка линковки **на issuer’е**: он знает «абонент X активен в эпоху N» (но НЕ его сессии/назначения — это видит только обфусцированный data-path, там анонимно). Это неустранимо для любой revocable-by-identity схемы. Ровно так работают боевые Privacy Pass / Apple Private Access Tokens: issuer аутентифицирует личность, redeemer (exit) — только unlinkable-токены.

### Admin-плоскость (C7): «выдать/отозвать» по туннелю — реализовано
Управление Слоем-1 (реестром) идёт **in-band, из-под поднятого туннеля** — публичная поверхность сервера не растёт:

- **Канал:** TCP к `ADMIN_VIP:admin_port` (`ADMIN_VIP` = шлюз туннеля, on-link и в split-tunnel) → data-plane exit'а пропускает точечно (после анти-спуфинга src) и DNAT'ит на issuer **только с туннельного интерфейса**; снаружи порт закрыт. Это **единственный** путь: прямой ход абонента на `ISSUER_IP:admin_port` сквозь туннель закрыт `EgressPolicy.deny_dsts` (G2 — SNAT exit'а иначе выдавал абонента за саму exit-машину и обходил allowlist `Citadel_ADMIN_PEER`). Поверх — PQ-TLS с тем же `issuer_pin`, что token-fetch; аутентификация админа — Ed25519 в отдельном домене (`citadel-admin/v1`) + EKM channel-binding (кросс-протокольный replay и релей исключены). Каждая операция самодостаточна: connect → op → close.
- **Роли ссылок (креды v4):** **мастер-ссылка** = клиентская + `admin_seed`/`admin_port` — только у админа; **клиентская** — свой `client_seed`, admin-полей нет. Выдача абонента целиком на устройстве админа: свежий CSPRNG-seed → по каналу уходит только pub (client_id) → ссылка минтится локально. Issuer seed абонента не видит (модель C5.4b сохранена).
- **Приватность и метки:** на сервере — только `pub + срок + статус`; человекочитаемые метки («телефон Али») — исключительно в зашифрованном vault админа (`IssuedRecord`).
- **Guard-rails:** `admin_id` отсутствует → канал никого не пускает (secure default); отзыв client_id самого админа отклоняется (анти-self-lockout, R6 — восстановления на сервере НЕТ, только реинсталл); провал auth → throttle 1с + разрыв без ack (не оракул).
- **Поверхности:** GUI «Абоненты» (все платформы, включая мобильные — russh не нужен) и CLI `citadel-token admin <list|add|revoke>` (ops с любой машины, где есть мастер-креды и туннель). **На сервере управляющих операций нет:** `citadel-token registry` оставлен только для провижининга (`add`/`add-seed`, зовёт установщик), а `revoke`/`list` с бокса убраны — тот же принцип, что и отсутствие `citadel-linkgen` (Q4): компрометация сервера не должна давать готовый инструмент перечисления базы и массового отзыва. Мера снимает инструмент, а не полномочия root'а (файл реестра он читает и правит и так).

### Дельты по коду
- `citadel-token`: **epoch-ключи** (per-epoch скаляр VOPRF; exit проверяет ключами current±prev); предъявление токена проверяется только вместе с контекстом сессии.
- Issuer: **client-registry** + Ed25519-аутентификация перед blind-signing; `revoke` = флип статуса; **admin-listener** (`Citadel_ADMIN_LISTEN`) — управление реестром по каналу (C7.1).
- Клиент: `enroll` — **активация первичной ссылки** (M-9): ключ устройства рождается локально,
  сохраняется в хранилище ДО обращения к издателю (оборванная активация продолжается тем же
  ключом), подтверждается отдельным флагом профиля; `effective_seed` — единая точка выбора «ключ
  ссылки или ключ устройства» для всех клиентов. `TokenAgent` — **кошелёк** (`TokenPouch`): пачка токенов + ключ L1 на эпоху в памяти процесса, фоновая дозаправка со случайной задержкой и **через сам туннель**, пока он поднят (§7.1/§17.1 аудита-4). До захода 7 клиент ходил к издателю перед КАЖДЫМ establish — то есть проектное «раз в эпоху» из этой же главы в коде не выполнялось, и издатель видел момент каждого подключения. `citadel_client::admin` — admin-операции + минт клиентских ссылок (C7.3); FFI/GUI «Абоненты» (C7.4).

## 11. Безопасность клиента

- **`SecretStore` = собственное зашифрованное хранилище**, а не обёртка OS-keychain (так задумывалось изначально; от keychain отказались ради единого кроссплатформенного формата и независимости от демонов вроде Secret Service). Один файл, крипта в Rust-ядре на `aws-lc-rs`: **v4 — мастер-ключ `MK` в слотах** (`password` под Argon2id-KEK, `platform` — блоб Android Keystore), полезная нагрузка под AES-256-GCM с заголовком И таблицей слотов в AAD. Детали формата и разбор остаточных рисков — §16.6. Хранит профили (`citadel://` со всеми инлайн-секретами: pin, PSK, seed), `device_seed` после активации и метки выданных ссылок. **Никаких секретов в plain-конфиге на диске.** Токены и ключ L1 эпохи в хранилище НЕ ложатся — кошелёк (`TokenPouch`) живёт только в памяти процесса (§10).
- **Admin-режим = высокая привилегия:** мастер-ссылка (в ней `admin_seed`) даёт выдачу и отзыв абонентов. Канал — тот же PQ-TLS к издателю с пином и ML-DSA-доказательством, доступный **только из-под поднятого туннеля** (ADMIN_VIP + DNAT), команды подписываются в отдельном домене с привязкой к TLS-сессии (C7, §14). SSH-путь деплоя и TOFU по host-key **удалены** (аудит-4, L-7/L-8): на сервере управляющих операций нет вовсе, break-glass — переустановка. Метки «кому выдано» — только в хранилище админа, на сервере их нет.
- **Kill-switch** — fail-closed маршрутизация (наследует F6 DNS-leak-protection); при разрыве туннеля трафик не утекает в открытую сеть. Платформы: Linux — `citadel-vpnd` + iptables/ip6tables, Windows — WFP (ограничение L-12: уже установленные потоки армирование не рвёт), Android — системный always-on + «блокировать без VPN» (приложение его выставить не может, только объяснить и увести в настройки).
- **Автозамок хранилища** (N-2, заход 12): логика — `app/lib/autolock.dart` (простой + уход в фон/погашение экрана; на десктопе им же считается сворачивание в трей), настройка «выкл / 1 / 5 / 15 мин» с **дефолтом 5 минут** живёт в ядре рядом с vault. Мусор в файле настройки читается как дефолт, а не как «выключено». Замок зовёт тот же `vault_lock`, что и кнопка, — туннель он не трогает.
- **Парольный конверт мастер-ссылки** (B-2, заход 13): вставленный текст, начинающийся с
  `-----BEGIN CITADEL MASTER LINK-----`, распознаётся в листе «Новый профиль»
  (`link_is_wrapped` — синхронно, дёшево) и вместо превью показывает поле пароля; разворачивание
  (`link_unwrap`) идёт **не** sync — внутри Argon2id на 256 MiB, на UI-потоке это заморозка кадра.
  Дальше ссылка идёт обычным путём (превью → код сверки → сохранение). Ошибка одна на все случаи
  («неверный пароль или повреждённый блок»): различать их — значит подсказывать подбирающему, что
  пароль он уже угадал. У консольного клиента то же в `citadel-cli add` (пароль спрашивается с
  терминала, ссылка и пароль не принимаются аргументами — они видны в `ps`).
- **Чувствительное в буфере обмена** (N-3, заход 12): ссылка абонента и `client_id` копируются через `app/lib/sensitive_clipboard.dart` → `SensitiveClipboard.kt` (метка `EXTRA_IS_SENSITIVE` для системного превью на Android 13+, очистка через 90 с, и только СВОЕГО содержимого). Граница: с Android 10 система не даёт менять буфер приложению без фокуса, поэтому очистка из фона может не сработать — она повторяется на возврате в приложение.
- **Захват IPv6 виден человеку** (N-1, заход 12): если устройство отвергло IPv6-blackhole, ядро пишет строку в журнал и шлёт в UI событие `kind=ipv6` (состояние держится и в снимке сессии — переживает перезапуск окна), на плашке статуса появляется «IPv6 идёт мимо туннеля» с разбором. Настройка «Строгий IPv6» (дефолт ВЫКЛ) запрещает поднимать туннель без захвата.
- **Известные остатки клиентской части** (реестр — `docs/SECURITY-AUDIT-4-2026-08.md §20.4`): платформенного слота хранилища нет на Windows/macOS (паритет с Android — R1.4); ручная проверка N-1 на устройстве, отвергающем v6-адрес, ещё не проводилась.
- **Угрозы вне области:** компрометация эндпоинта пользователя (см. `SPEC.md §0`).

## 14.1 Трек C8 — сетевой контроль (детальный план, 2026-07-21)

Порядок реализации: **C8.0 → C8.1 → C8.2 → C8.3** (по возрастанию сложности и платформенной специфики). Каждый пункт — компилируемый+рецензируемый инкремент; поведение сети верифицируется на Linux-VM и Android-устройстве (см. [[testing-interactive-ui]]).

### C8.0 — Хард-делит абонента (из support-вопроса про «зависший SSH-токен»)
**Проблема:** admin-плоскость умеет только `Revoke` (мягкий: `status=revoked`, строка остаётся в реестре навсегда) — стары́е записи «висят» в «Абонентах» и не удаляются; `Revoke` собственного admin client_id отбивается анти-self-lockout (R6). Хард-делита нет.
- `admin::AdminRequest::Remove { client_id }` (новый CBOR-вариант) + `registry_apply_remove(existing, pk) -> Result<String>` (удаляет строку целиком; `bail!` если не найдена). Анти-self-lockout как в `Revoke` (отказ на `admin_client_id`).
- `serve_admin` → `atomic_write`; CLI `citadel-token admin remove <pub>` (по каналу — **не** серверный `registry`: управляющих операций на боксе не заводим, см. §admin-плоскость); FFI `admin_remove_subscriber`; GUI — кнопка «Удалить» рядом с «Отозвать» (подтверждение; акцент для `revoked`/`истёк`).
- Тесты: `registry_apply_remove_{ok,missing,self_lockout}`. Формат реестра НЕ меняется (backward-compat), но новый enum-вариант → согласованное обновление сервер+клиент.
- **До C8.0** хард-делита нет вовсе: `Revoke` по каналу гасит доступ, строка остаётся. Ручная правка файла на VPS штатным путём не считается и в инструкции оператора не входит — сервер по модели управляющих полномочий не имеет (см. §admin-плоскость, guard-rails).

### C8.2 — Linux: при закрытии окна спросить «фон / разорвать» ✅ реализован (2026-07-21)
Закрытие окна (X) при живом туннеле больше не рвёт его молча — диалог «Оставить в фоне» / «Отключить и выйти».
- `window_manager ^0.4.3`: `main()` на desktop → `ensureInitialized`+`setPreventClose(true)`; `_CitadelAppState with WindowListener`, `onWindowClose` через `navigatorKey`-контекст.
  - Туннель неактивен (`!state.isBusy`) → `windowManager.destroy()` сразу.
  - «Оставить в фоне» → `windowManager.minimize()` (окно в трее задач, сессия+реконнект живы; процесс жив).
  - «Отключить и выйти» → `state.disconnect()` (`vpnDisconnect`→clean_shutdown, 'Q'→helper снимает KS) + пауза 700 мс на teardown → `windowManager.destroy()`.
- Только desktop (`_isDesktop = Linux|Windows|macOS`); Android не затронут (S3 держит сессию через сервис). NB: при SIGKILL процесса в фоне KS остаётся (helper fail-closed на EOF без 'Q'). **Фон = свернуть** (не hide): без системного трея скрытое окно нечем вернуть; трей-иконка — future-улучшение. Гейт: `flutter analyze` 0 + `flutter build linux`.
- **Скрытое окно не должно стоить процессорного времени (2026-08-11).** Flutter не знает, что окно спрятано: скрытое окно продолжает получать такты вертикальной синхронизации, поэтому бесконечная анимация в дереве планирует кадр за кадром и без окна на экране. У нас такая анимация ровно там, где она дороже всего: индикатор «Подключение…» крутится столько же, сколько движок ретраит недоступный сервер, — то есть часами. Живой симптом: свернули в трей при неподнимающемся туннеле, процессор занят и не освобождается. Решение — флаг видимости (`app/lib/window_visibility.dart`), который ставит `main.dart` (мы сами зовём `hide()`/`show()`, плюс `onWindowMinimize/Restore/Event`), и три потребителя: `TickerMode(enabled: …)` над всем `MaterialApp` (гасит Ticker'ы), таймеры индикации трафика и поток журнала ядра не зовут `setState`, пока окна не видно. Работа движка (сессия, реконнект, kill-switch) не затрагивается — гасится только отрисовка; при возврате окна потребители догоняют состояние одним обновлением.
- **Уточнено 2026-07-26 (Windows).** Там, где есть трей (Windows, `WindowsTray.supported`), диалога больше НЕТ: закрытие окна при живом туннеле — это «убрать с глаз», а не «отключить», поэтому окно молча уходит в трей, а сессия продолжает работать. Выйти по-настоящему — пункт «Выход» в меню трея (он делает чистый disconnect со снятием KS и гасит службу). Диалог остался только там, где трея нет (Linux/macOS): скрытое окно вернуть было бы нечем, поэтому «в фоне» = `minimize()` и спросить уместно. Заодно у окна убрана кнопка «развернуть» (`setMaximizable(false)`): размер фиксирован (400×680), разворачивать некуда.

### C8.3 — Split-tunneling (Android ✅ реализован 2026-07-21; Linux/Win/macOS — позже)
**Две независимые оси** (компонуются — Android разрешает фильтр приложений И набор маршрутов одновременно):
- **Ось приложений:** `app_mode: Off | Include | Exclude` + `apps: Vec<String>` (package-имена). Include = только выбранные через туннель; Exclude = все, кроме выбранных.
- **Ось назначений:** `dest_mode: Off | Include | Exclude` + `dests: Vec<String>` (запись = **домен | IP | CIDR**, в т.ч. локальная подсеть). Include = только эти назначения в туннель; Exclude = full-tunnel минус эти (в обход, напр. локальная сеть).

**Реализация (Android, `SplitTunnel` в `citadel-quic::config`):**
- Ядро: `SplitMode`{Off,Include,Exclude} + `SplitTunnel`{app_mode,apps,dest_mode,dests} в `ClientConfig`; `vpn::resolve_dests` раскрывает домены→A-записи→`/32`, IP→`/32`, CIDR как есть (IPv4; v6 — future), на каждый establish (реконнект перерезолвит CDN). `TunParams` несёт split-поля.
- FFI: `SplitTunnelDto` + `set_split_config`/`split_config`, персист текстовым файлом `split` рядом с vault (как kill-switch), накат в `spawn_controller`.
- JNI→Kotlin `establishTun(...appMode,apps,destMode,destRoutes)`: приложения — `addAllowedApplication`(Include)/`addDisallowedApplication`(Exclude), несуществующий пакет ловится пер-пакет; назначения — Include → `addRoute` только их (не full, без IPv6-blackhole), Exclude → full-tunnel + `excludeRoute` (Android 13+/API33; ниже — лог, назначение остаётся в туннеле).
- UI: `split_tunnel_page.dart` (две секции с `SegmentedButton`, app-picker из `MainActivity.listInstalledApps` через `<queries>` LAUNCHER, редактор назначений + «Добавить локальную подсеть» из `NetworkInterface`). Гейт: `cargo ndk check aarch64` + `flutter analyze` + unit-тесты + `flutter build apk`. **Device-тест за пользователем.**
- **Linux — ось назначений ✅ реализована (2026-07-21):** `gui_tun::split_routes(dest_mode, link_routes, dest_routes)` → helper. Include → `--routes <dest_routes>` (в туннель только они, default физический, без IPv6-блока); Exclude → `--routes <link>` + новый `--bypass <dest_routes>` (helper `ip route replace <cidr> via <phys-gw>`, тем же путём, что exit-IP bypass; teardown на выходе); Off → как раньше. `resolve_dests` (ядро) раскрывает домены→CIDR. Тест `split_routes_by_dest_mode`. UI: секция «Адреса назначения» показывается и на Linux (секция «Приложения» — только Android).
- **Linux — ось приложений (per-app): отложена** (решение пользователя 2026-07-21 — «пока только по назначению»). План при возврате: **cgroup v2 + fwmark + policy routing** через launcher-обёртку `citadel-run <app>` (PID→cgroup, `iptables -t mangle -m cgroup … MARK`, `ip rule fwmark → bypass/tunnel table`) — как `mullvad-exclude`.
- **Windows/macOS:** WFP по AppID / NE `NEAppProxyProvider` — отдельный трек.
- Red-team: split — поверхность деанона (выбранное «в обход» светит реальный IP); домены у CDN с меняющимися IP могут «протекать» между реконнектами. UI-предупреждение добавлено.
- **DNS при сплите (разобрано 2026-07-26).** Ось приложений и ось назначений делят DNS по-разному, и это неочевидно:
  - **app-Include («только эти приложения через туннель»):** Android выбирает резолвер **по приложению**, а не по адресу — per-UID сетевые правила netd. Приложения в туннеле резолвят через `addDnsServer` (резолвер туннеля, запрос идёт внутри туннеля); все остальные — через DNS физической сети (Wi-Fi/оператор), то есть провайдер видит их домены. Это ожидаемое свойство сплита (их трафик и так идёт мимо туннеля), но пользователю о нём надо сказать — подсказка добавлена в UI сплита.
  - **Системный «Личный DNS» (DNS-over-TLS, Android 9+)** применяется и к VPN-сети: при strict-режиме резолвинг пойдёт на заданный DoT-хост (через туннель), а не на наш резолвер. Если DoT-хост недоступен, DNS не работает — типовая жалоба на все VPN-клиенты; тоже названо в подсказке.
  - **Найден и исправлен дефект:** маршрута к самому резолверу на Android не добавлялось. При dest-Include (в туннель только выбранные адреса) или при exclude, накрывающем резолвер, DNS-сервер оказывался вне туннеля — приложения под VPN не резолвили ничего. Теперь Kotlin добавляет `addRoute(<dns>/32)` на каждый сервер имён (IPv4; `/32` специфичнее любого exclude-префикса, поэтому исключения его не отменяют) — тот же инвариант, что host-route на DNS в `citadel-vpnd` (`plan::tunnel_route_cmds`).
- **Инвариант «подсеть туннеля не выносится из туннеля» (фикс 2026-07-25).** В подсети назначенного адреса живёт шлюз exit'а = `ADMIN_VIP` (C7.2) — по нему идёт admin-канал «Абоненты». На Linux/Windows маршрут в неё появляется сам (адрес на интерфейсе → on-link), а у VPN-сети Android маршрутов ровно столько, сколько добавлено в `Builder` ⇒ любой split уносил её мимо VPN, и `connect()` к `10.7.0.1` падал в `EHOSTUNREACH` («No route to host»: для UID под VPN Android ставит fallthrough-правило `unreachable`), хотя туннель работал. Теперь: (1) Kotlin ВСЕГДА добавляет `addRoute(<подсеть туннеля>)`; (2) из `excludeRoute` вырезается всё, что её накрывает; (3) при app-Include приложение добавляет САМО СЕБЯ в разрешённые, при app-Exclude — никогда себя не исключает; (4) `winnet::split_routes(..., tun_net)` держит тот же инвариант для Linux/Windows (bypass-список фильтруется — тест `split_routes_never_bypasses_tunnel_subnet`); (5) «Добавить локальную подсеть» в UI пропускает интерфейс туннеля.

## 15. Data-plane: MTU-бюджет, живость пути и IPv6 (2026-07-25, разбор «мобильного» реконнект-шторма)

Три инварианта, которые обязаны выполняться одновременно, иначе туннель ведёт себя «загадочно»:
хендшейк проходит, а данные не идут, либо клиент бесконечно переподключается.

### 15.1 MTU: один бюджет на всю цепочку
```
IPv4(20) + UDP(8) + [ obfs: FRAMING_OVERHEAD(55) + padding ] + QUIC-пакет(≤1200)
                                     ↑ потолок провода = citadel_obfs::WIRE_CAP = 1255
inner-IP-пакет ≤ citadel_quic::INNER_MTU (1161) = max_datagram_size(1162) − 1 байт context-varint
```
- **QUIC не знает про obfs.** `initial_mtu = MAX_QUIC_PACKET` (1200, discovery выключен), а на провод
  уходит ещё +55 фрейминга и +паддинг. Паддинг C2 **не имеет права раздувать** пакет выше `WIRE_CAP`
  — иначе полноразмерные пакеты (и только они) чёрнодырятся там, где MTU впритык: мобильные сети,
  NAT64/CLAT (+20 б на трансляцию), GTP, туннель-в-туннеле. Симптом коварный: мелкие пакеты и
  хендшейк живут, данные — нет. Держится тестами `obfs_wire_cap_matches_quic_mtu` (citadel-quic) и
  `default_padding_never_exceeds_quic_mtu_on_wire` (citadel-obfs).
- **TUN обеих сторон = `INNER_MTU`.** Клиент клампит свой TUN под фактический
  `Session::quic_datagram_mtu()`; exit конфигурирует общий TUN до появления соединений, поэтому
  берёт константу (`Citadel_MTU`, дефолт `INNER_MTU`). Больше — пакет из интернета не влезет в
  датаграмму (тихий дроп; для TCP маскируется MSS-clamp'ом, крупный UDP — QUIC/HTTP3, видео, игры —
  просто пропадает). Меньше — крупные пакеты КЛИЕНТА не влезут в TUN exit'а и умрут при записи.
  Тест `inner_mtu_fits_real_datagram_budget` проверяет константу против живого quinn.

### 15.2 Живость пути ≠ наличие обратных датаграмм
`pump`-watchdog рвёт транспорт сразу, только если за окно (8с) мы слали ≥12 датаграмм И не приняли
**ни одной датаграммы, ни одного QUIC-пакета** (`stats().udp_rx`). Пока идут ACK'и/keep-alive пира —
путь ЖИВ, и разрыв «за тишину в туннеле» лечить нечего: новая сессия упрётся в то же самое
(ровно этот реконнект-шторм ловился на cellular).

Но «путь жив» ≠ «наши пакеты доезжают», и раньше эти два случая сливались в один вердикт «похоже,
пакеты дропает exit» — неверный ровно в самом частом мобильном случае и уводивший разбор на сервер.
Окно разбирается по счётчикам транспорта (`dataplane::uplink_is_dead`):

Решающая улика — **ACK-фреймы** (`frame_rx.acks`), а не соотношение отданного и ушедшего: пир шлёт
ACK только за то, что до него ДОЕХАЛО. Ноль ACK'ов за окно активной отправки означает, что канал не
несёт наши пакеты (или их подтверждения); поток ACK'ов, наоборот, доказывает, что пакеты у exit'а.

| что видно за окно | вердикт | реакция |
|---|---|---|
| ушло на провод, ACK'ов 0 | путь не несёт наши пакеты (или их ответы) | `DataPath::UplinkDead` |
| отдано N, `frame_tx.datagram` ≪ N, ACK'ов 0 | очередь встала намертво — quinn **молча вытесняет** старые датаграммы из `datagram_send_buffer_size`, поэтому успешный `send_datagram` ничего не обещает | `DataPath::UplinkDead` |
| ушло на провод, но `path.lost_packets` ≥ половины | путь глотает наши пакеты (потери / узкий MTU) | `DataPath::UplinkDead` |
| ушло и подтверждено, обратно 0 | пакеты у exit'а: дроп на нём (F2/анти-спуфинг/F7) либо молчит назначение | `DataPath::ExitSilent`, сессию НЕ рвём |

**Быстрый детектор (тик 2с).** Полевой лог Android: за тик отдано 113 датаграмм, на провод ушло 2,
потеряно 0. Ждать полных двух окон (16с) в таком состоянии нечего — сигнатура `uplink_is_stalled`
(отдано ≥12, потерь 0, **ACK'ов 0**, на провод ушло на порядок меньше) рвёт транспорт через
**2 тика (4с)**. Условие про ACK'и здесь не украшение, а единственное, что отличает мёртвый канал
от УЗКОГО: на 2G/перегруженном Wi-Fi «отдано 113, ушло 2, потерь 0» — совершенно нормальная
картина, туда просто не влезает больше, и рвать такую сессию нельзя (симптом «каждое подключение
обрывается и уходит на 443»).

Две локальные причины остановки отправки по счётчикам неотличимы и лечатся одинаково (сменить
транспорт), но в журнале называются по-разному — по `udp_tx` за тик: ноль = сокет не взял ни одного
пакета (очередь устройства/`ENOBUFS`/нет маршрута), не ноль = пакеты уходят, но не подтверждаются.
Туда же печатается счётчик петли (§15.7) — при завороте собственного транспорта в собственный
туннель картина ровно та же, а причина совсем другая. Средний размер ушедшего пакета печатается в
окне: сотни байт = путь не несёт крупные (полноразмерный пакет провода = `WIRE_CAP`(1255) + 28 =
**1283 б** против типового мобильного потолка 1280; ниже 1200 quinn `initial_mtu` не опустить),
~1250 = уходит всё, просто редко.

`UplinkDead` два окна подряд (16с) → транспорт рвётся с `PumpExit::uplink_dead`, и цикл реконнекта
поднимает следующую сессию **сразу obfs-TCP** (§15.4): сегментация переживает узкий MTU и потери
там, где QUIC/UDP чёрнодырится. Если односторонним оказался уже obfs-TCP — дело не в транспорте,
предпочтение снимается (иначе застряли бы на TCP навсегда); если obfs-TCP просто не поднялся —
тоже, чтобы не биться в закрытый 443.

Вердикт **переживает контроллер**: приложение создаёт новый `VpnController` на каждое нажатие
«Подключить», поэтому «QUIC/UDP здесь не работает» хранится процессным флагом с TTL 15 минут
(`vpn::udp_unusable_recent`) и сбрасывается сменой сети. Иначе каждое подключение на такой сети
начиналось бы одинаково: 4с мёртвого туннеля, обрыв, переустановка — и второй токен из кошелька за
одно подключение.

Вердикт пишется в ДВУХ местах, потому что негодность UDP бывает двух видов:

| что случилось | где отмечается | цена без вердикта |
|---|---|---|
| хендшейк QUIC/UDP не прошёл, сессия поднялась поверх obfs-TCP | сразу после `Connected` (`session.over_tcp() && !prefer_tcp`) | 5 попыток × 3с = **15с ожидания на каждое подключение** |
| сессия поднялась, но канал односторонний | по `PumpExit::uplink_dead` после pump | 4с мёртвого туннеля + второй токен |

Исключение общее: если obfs-TCP мы навязали сами (`prefer_tcp`), про UDP вердикт не выносится — его
в этой попытке не пробовали. И если односторонним оказался сам obfs-TCP или он не поднялся —
вердикт снимается (см. выше).

Последний вердикт виден процессу как `dataplane::data_path()` и приклеивается к отказам
admin-плоскости (§15.5): «Абоненты» ходят ВНУТРИ туннеля и молчат по той же причине, что и
интернет, — экран обязан назвать её, а не показывать «канал недоступен (туннель поднят?)».

### 15.3 IPv6 в IPv4-туннеле
Туннель IPv4-only, на Android в TUN намеренно заведён blackhole `::/0` (S2.2/A2, анти-leak).
Клиентский `pump` **дропает не-IPv4 локально** (exit всё равно ответит default-deny) и раз в окно
пишет об этом строку: иначе v6-трафик приложений выглядит как «шлём и не получаем» → ложная
смерть пути, и это же маскирует «часть сайтов не открывается».

### 15.4 Эскалация QUIC→obfs-TCP и экономика токенов
Эскалация (`VpnController`) лечит **ровно один** класс отказов: транспорт поднялся, а крупный
control-обмен не прошёл (MTU/NAT64). Раньше она срабатывала на ЛЮБУЮ ошибку establish, и это било
дважды: вторая попытка предъявляла **ещё один** Layer-1 токен (issuer выдаёт их под single-session
аренду 4/B), а в UI уезжала последняя причина — «auth-failed» вместо настоящей (например, «ML-DSA
подпись не сошлась»). Теперь: `should_escalate_to_tcp` пропускает только транспортные отказы,
причина QUIC-попытки доклеивается к итоговой ошибке, а если issuer не дал свежий токен — попытка
**не делается вовсе** (потраченный токен = гарантированный `auth-failed`), клиент ждёт с backoff и
показывает честную причину. Регрессия ловится docker-негативами ТЕСТ 15 / ТЕСТ 19.

### 15.5 Диагностика (чтобы не гадать)
- `citadel_quic::diag` печатает причины через `{e:#}` — цепочка `source` (иначе от quinn видно лишь
  бесполезное «read error: connection lost» вместо «timed out» / «closed by peer: code 1»).
- Шаг **«Admin-канал»** — сырой TCP-SYN на `ADMIN_VIP:порт` прямо в туннель, мимо ОС-роутинга:
  делит жалобу «не открывается список абонентов» на «сломано на exit'е» (нет SYN-ACK) и «сломан
  маршрут/split на устройстве» (SYN-ACK есть). Только для мастер-профиля.
- Отказ любой admin-операции дополняется состоянием канала (`citadel_client::admin::explain_path`
  поверх `dataplane::data_path()`, §15.2). Без этого экран показывал «admin-канал 10.7.0.1:7001
  недоступен (туннель поднят?)» — вопрос, на который у человека нет способа ответить, хотя движок
  ответ уже знал.
- При вердикте `UplinkDead` admin-операция отказывает **сразу** (`refuse_if_path_dead`), не тратя
  10с `CONNECT_TIMEOUT` на SYN в мёртвый туннель: за это время движок как раз успевает сменить
  транспорт, и повтор попадает на живую сессию.
- Экран «Абоненты» пробует загрузиться сам не более двух раз (потолок в `subscribers_page`). Без
  потолка выходил вечный круг: неудачная попытка оставляет список пустым, авто-загрузка висит на
  событии «сессия поднялась», и каждый реконнект запускал её заново — «висит, потом всё заново».
  Номер попытки показан рядом с надписью, дальше — только явное «Обновить».

### 15.6 «Сети нет вовсе» — кто это замечает (2026-07-31)
Пропажа ВСЕЙ сети (авиарежим, ушли из зоны) — не то же самое, что смена сети, и раньше её никто не
ловил сразу: `onLost` только обнулял `currentNetworkId`, обратных датаграмм нет и при простое,
watchdog (§15.2) срабатывает лишь под нагрузкой. Туннель оставался «поднятым» в UI и в постоянной
нотификации, пока не истечёт QUIC-idle (15с) — а на obfs-TCP и того дольше. Теперь три звена:

1. **`CitadelVpnService.onLost`** — если упала сеть, поверх которой шёл туннель: осталась другая
   (выключили WiFi при живом LTE) → переезжаем на неё сразу (её `onAvailable` уже был и повторно не
   придёт); не осталось ничего → `setUnderlyingNetworks(null)`. В обоих случаях будим ядро
   (`nativeNetworkChanged`) — оно рвёт мёртвый pump и уходит в переподключение (`Migrating`).
2. **`VpnController::backoff_wait`** — пауза между попытками просыпается не только на `disconnect`,
   но и на смену сети, со сбросом backoff. Иначе вернувшийся интернет ждал бы до 30с уже
   доступным.
3. **Постоянная нотификация Android** — текст идёт из состояния движка (`setStatus` по JNI):
   «Подключение…» / «Нет соединения — восстанавливаю» / «Постквантовый туннель активен». При
   закрытом окне это единственный индикатор, и он обязан не врать.

QUIC-idle остаётся backstop'ом для случая, когда ОС о потере не сообщает (мёртвая зона, captive
portal). С заходом «маскировка/батарея» (§17.3) он стал ленивее: idle 90 с, собственный маячок
15–28 с при подтверждении со стороны exit'а. Это осознанно — мёртвый путь ловят не он, а data-path
watchdog (затор 4 с, односторонний путь 16 с) и Android-watchdog смены сети, и ловят раньше; а
плата за короткий idle была велика — маячок раз в 2–4 с не давал LTE-модему уйти в idle **никогда**.

### 15.7 Анти-петля: сокеты движка мимо собственного туннеля (2026-08-06)

Приложение-владелец VPN **не исключено** из своих же маршрутов: на Android весь трафик процесса
идёт в TUN, на desktop `0.0.0.0/0` накрывает и адрес exit'а. Значит, у каждого исходящего сокета
движка должен быть явный обход, иначе транспорт заворачивается сам в себя.

| Платформа | Механизм обхода | Кто ставит |
|---|---|---|
| **Android** | `VpnService.protect(fd)` | `citadel-protect` → JNI (`protectFd`) |
| **Linux/Windows** | bypass-маршрут к `exit_ips` (+ WFP-исключение) | `TunProvider` при конфигурации TUN |

**Инвариант:** каждый сокет к ПУБЛИЧНОМУ адресу (QUIC/UDP к exit, obfs-TCP к exit, канал к
издателю за Layer-1 токеном, TCP-пробы диагностики) создаётся несоединённым, проходит через
`citadel_protect::protect_socket` и только потом соединяется. Реестр протектора живёт в отдельном
крейте `citadel-protect` именно потому, что нужен и `citadel-quic`, и `citadel-token` (зависеть
друг от друга они не могут). Порядок «protect → connect», а не наоборот: с системным always-on +
«блокировать без VPN» незащищённый сокет вообще не выпускается ОС; TCP выбирает исходящий адрес и
маршрут в момент connect; при поднятии туннеля система рвёт незащищённые сокеты процесса.

**Исключения — два, и оба выражены типом** `citadel_protect::Route`{`Bypass`,`Tunnel`}, а не
умолчанием, чтобы новый сетевой путь обязан был выбрать сторону сознательно:

1. **admin-плоскость** (`citadel_token::admin`, «Абоненты») идёт к ADMIN_VIP *внутри* туннеля
   (C7.2); пометка «мимо туннеля» увела бы её в сеть, где такого адреса нет;
2. **фоновая дозаправка кошелька токенов при поднятом туннеле** (§7.1(в) аудита-4): она
   сознательно идёт СКВОЗЬ туннель, чтобы издатель видел адрес exit'а, а не абонента. Перед
   `establish` и при опущенном туннеле кошелёк ходит `Bypass` — иначе токен не добыть вовсе.

Цена нарушения (живой случай 2026-08-06, Android): UDP/4433 в сети недоступен → obfs-TCP поднимался
до создания TUN и потому соединялся, а после `establish()` его сегменты уходили в наш же туннель,
приходили на exit с адресом источника локальной сети и дропались анти-спуфингом (S0.2). Внешне —
«подключается и сразу переподключается» по кругу; в журнале — «пакеты ушли в туннель с ЧУЖИМ
адресом источника». Теперь такой пакет (dst == адрес exit'а) в журнале называется петлёй прямо,
отдельной строкой — «чужой src» слишком мягкая формулировка для этого случая.

**Повтор той же беды на UDP-транспорте (2026-08-12).** Строку `protect_socket` в `build_endpoint`
удалили при рефакторинге (перенос `pacing` в параметр, заход 7 аудита-4), и клиентский QUIC/UDP
сокет перестал исключаться из туннеля. Проявление коварнее, чем в случае с TCP: **хендшейк
проходит** (он идёт до `VpnService.Builder.establish()`, туннеля ещё нет и маршрут настоящий), а
data-plane встаёт ровно в момент подъёма TUN. Счётчики при этом выглядят как «плохая сеть»: отдано
113 датаграмм, на провод ушло 2, потерь 0, ACK'ов 0 — то есть cwnd не открывается, потому что
подтверждать нечего. Разбор из-за этого дважды уезжал в MTU и в оператора связи. Выводы, которые
удерживаются кодом:

* инвариант «сокет к публичному адресу проходит через протектор» закреплён тестом
  `protect::tests::transport_sockets_go_through_protector` — он проверяет ОБА транспорта и путь
  без обфускации (`client_endpoint_plain`; `quinn::Endpoint::client` использовать нельзя — он
  создаёт сокет внутри себя, и вклиниться с `protect` между bind и connect негде);
* `protect_socket` возвращает **признак успеха**, и клиент печатает его при создании QUIC/UDP
  сокета. Без этого «протектора нет» было неотличимо от «защищено»: хендшейк в обоих случаях
  проходит (туннеля ещё нет), и расходятся они только на данных;
* **владение моментом**: протектор обязан стоять ДО первого транспортного сокета. Это держат три
  вещи сразу, потому что одной мало: `startService` из Dart ждёт `onServiceReady`; служба,
  получившая `stopSelf`, считается неготовой (`CitadelVpnService.ready()`) — иначе быстрое
  «Отключить → Подключить» стартовало сессию поверх умирающего экземпляра, чей `onDestroy` затем
  снимал протектор уже из-под работающего движка; `nativeUnregister` снимает протектор, только
  если умирает ТОТ ЖЕ экземпляр, который зарегистрирован (`is_same_object`). Плюс движок на
  Android коротко (≤1с) ждёт `protector_active()` перед первым establish;
* признак петли — **только `dst == адрес exit'а`**, без условия «чужой src»: когда маршрут к
  exit'у уходит в TUN, ядро берёт адресом источника адрес самого TUN, то есть назначенный нам, и
  прежняя проверка (петля искалась внутри ветки «чужой src») не срабатывала вовсе;
* счётчик петли печатается и в вердикте быстрого детектора (§15.2), а не только в оконной
  диагностике: тик рвёт транспорт на 4-й секунде, до окна (8с) дело не доходит.

### 15.8 Отмена подключения: «Отключить» обязано прерывать фазу, а не ждать её конца

`VpnController::connect` — цикл длинных фаз: добыча Layer-1 токена (кошелёк обычно отдаёт его
мгновенно, но на холодном старте это заход к издателю с его таймаутами), establish
(до 5 попыток QUIC + obfs-TCP), конфигурация TUN. Запрос на разрыв — персистентный флаг `stopped`
плюс `Notify`; проверять его между итерациями недостаточно: нажатие в середине фазы раньше не
прерывало её. Наблюдалось это так: пользователь жмёт «Отключить» во время переподключения, а в
журнале продолжаются попытки, после чего — «TUN не удался: CitadelVpnService не зарегистрирован»
(цикл дошёл до конфигурации туннеля уже поверх погашенного сервиса). На desktop тот же путь мог
поднять туннель и kill-switch заново после того, как пользователь их снял.

Правила теперь такие:

1. Каждая длинная фаза идёт через `until_stop(fut)` — `select!` с приоритетом отмены (`biased`).
2. Перед привилегированным шагом (`provider.configure`) и сразу после успешного establish —
   повторная проверка флага; поднявшаяся «лишняя» сессия гасится дропом, `Connected` не эмитится.
3. Ожидание отмены (`cancelled`) сначала **подписывается**, затем читает флаг. Обратный порядок —
   гонка: `disconnect`, прошедший между проверкой и подпиской, терялся (`notify_waiters` помнит
   только уже зарегистрированных), и туннель продолжал жить.

### 15.9 F8: что клиент принимает ИЗ туннеля (аудит-4, находка H-4, 2026-08-08)

Долгое время фильтрация трафика считалась заботой exit'а: у него `Inbound` с анти-спуфингом,
egress-политикой F2 и rate-limit F7, а на клиенте тот же объект создавался с `egress = None`, то
есть **не проверял ничего**. Это ошибка асимметрии: туннель — двусторонний канал, и его дальний
конец — это запись в TUN нашего устройства. Всё, что exit положит в датаграмму, ядро клиента
обработает как обычный входящий пакет. Скомпрометированный exit получал этим не только чтение
трафика (что неизбежно — он NAT-эндпоинт), но и **инициативу**: SYN на любой слушающий порт
устройства (`adb tcpip` 5555 на Android, sshd/SMB/dev-серверы на десктопе), доступ к сервисам,
привязанным к адресу локалки (Linux принимает пакет к любому своему адресу с любого интерфейса),
маршрут в LAN при `ip_forward=1`, ICMP redirect. Kill-switch этого не ловит по построению: и
`CITADEL_KS`, и WFP-план сидят на исходящем направлении.

Инвариант: **из туннеля принимается только то, что может быть ответом на наш собственный
исходящий трафик**. Реализация — `citadel_quic::clientfw` (F8), включается в `pump`, когда
`ClientPath` задан (то есть на клиенте, взаимоисключимо с exit-режимом):

1. `dst` == назначенный адрес — иначе дроп (это же закрывает weak host model и пивот в LAN);
2. TCP/UDP: порт назначения обязан быть портом, с которого мы отправляли в этой сессии;
3. TCP `SYN` без `ACK` — дроп всегда (сервер не открывает нам соединений);
4. ICMP: только 0/3/11; `3` обязателен — на нём держится PMTU внутри туннеля (см. §15.1);
5. прочие протоколы — только после нашего исходящего этим протоколом;
6. не-IPv4 — default-deny (§15.3).

Почему записи не стареют: старение рвало бы живое, но молчащее соединение (idle-SSH, где сервер
пишет первым после паузы) — мы бы дропнули его пакет, а сами ничего не шлём, и получился бы дедлок
до keep-alive. Порт, которым мы пользовались, остаётся открытым до конца сессии; «постоянные»
слушатели (22/445/5555/8080) не проходят никогда, потому что исходящих пакетов с таких портов нет.

Дропы считаются по причинам и печатаются агрегированно в окне watchdog: попытка сервера достучаться
до устройства — это диагностический факт, который пользователь обязан увидеть, а не тишина.
`Citadel_INBOUND_OPEN=1` переводит фильтр в режим наблюдения (аварийный рубильник для поля).

## 16. Windows (модель W2): жизненный цикл службы `citadel-svc` (2026-07-30)

Разбор двух живых жалоб: «через ~20 минут туннель начал переподключаться и больше не поднялся —
*Все копии канала заняты (os error 231)*, а после выхода из приложения `citadel-svc.exe` остался
висеть» и «без прав администратора туннель не поднимается — *OpenService: Отказано в доступе*».

### 16.1 Инвариант «подключиться к службе можно всегда»
Служба владеет ОДНИМ WinTUN-адаптером, и раньше из этого молча следовало «и одним соединением»:
serve-цикл создавал единственный инстанс named pipe и занимал его на всю сессию. Отсюда весь класс
отказов реконнекта — во время сессии `CreateFileW` получал `ERROR_PIPE_BUSY` (231), а в окне между
инстансами (teardown маршрутов + удаление адаптера — единицы секунд) `ERROR_FILE_NOT_FOUND` (2).

Теперь эти две сущности разведены:
- **акцептор** всегда держит СВОБОДНЫЙ слушающий инстанс и отдаёт соединение рабочему потоку;
- **сессия** — ровно одна, в глобальном слоте; новый аутентифицированный (W3) клиент **вытесняет**
  прежнюю и дожидается её полного сворачивания, прежде чем поднимать свою (иначе получили бы второй
  WinTUN с тем же именем и неоднозначный `netsh name=Citadel`).

Вытеснение — не ослабление модели: пройти к слоту может только образ из install-dir (W3), т.е. само
приложение. Вытесненная сессия сворачивается как аварийная ⇒ WFP-kill-switch остаётся армированным
до тех пор, пока новая сессия не переармирует его (fail-closed не рвётся).

### 16.2 Почему служба залипала навсегда
Поток «WinTUN → пайп» будился только `session.shutdown()`. Если он стоял в overlapped-`WriteFile`
(клиент перестал читать пайп, но хэндл ещё держит ⇒ 64 КБ буфера канала заполнены и запись висит
«в ожидании»), `join` не возвращался НИКОГДА. Служба оставалась занятой: туннель не поднимался ни по
одной ссылке, `TAG_QUIT` не доходил — отсюда и «остался висеть процесс». Теперь поток будится
обоими способами (`shutdown` + `CancelIoEx`), а ожидание вытеснения ограничено по времени.

### 16.3 Право `SERVICE_START` — почему ломалось отложенно
Приложение неприв., поэтому при выходе оно гасит службу (`TAG_QUIT`), а на следующем подключении
поднимает её через SCM. Это работает, только если у интерактивного пользователя есть `SERVICE_START`
(его выдаёт `citadel-svc install` → `sc sdset`). Дефект был двойной: право выдавалось последним
шагом за двумя `?` (осечка любого предыдущего — и служба молча оставалась с дефолтным дескриптором,
а инсталлятор код возврата не проверяет), а клиент открывал службу сразу с `SERVICE_START`, и
нехватка права выглядела как отказ даже там, где служба УЖЕ работала и делать было нечего.

Правила теперь такие:
1. право выдаётся ПЕРВЫМ делом при установке **и** на каждом старте службы (LocalSystem имеет
   `WRITE_DAC` на свою запись в SCM) — установка чинит себя сама, `AutoStart` доносит это до
   старых установок после ближайшей перезагрузки;
2. статус спрашивается минимальным доступом (`SERVICE_QUERY_STATUS`), стартовые права — только
   когда служба реально остановлена;
3. приложение НЕ гасит службу при выходе, если поднять её обратно не сможет (лишний процесс в
   задачах — меньшее зло, чем неработающий VPN);
4. `SERVICE_STOP` пользователю по-прежнему не выдаётся: остановка идёт только по пайпу и только без
   активной сессии, иначе снятие службы уносило бы вместе с ней kill-switch (fail-open = деанон).

**Запуск «от имени администратора» — не решение, а обходной путь** (у администратора `OpenService`
проходит по ACE `BA`): GUI-приложение с движком и разбором недоверенного ввода не должно ходить
elevated — ради этого модель W2 и разделена на неприв. приложение и службу-плумбер.

### 16.4 Где лежит хранилище на Windows (2026-07-30)

`%LOCALAPPDATA%\CitadelPQVPN\vault.bin` (рядом — `killswitch`, `debug`, `split`,
`screenshot_block`). Именно `Local`, а не `Roaming`: хранилище несёт bearer-креды, синхронизировать
их по доменному профилю незачем; доступ разграничивает ACL профиля пользователя.

До этого путь резолвился общим (unix-ориентированным) правилом `XDG_CONFIG_HOME` → `HOME` →
`.`, а на Windows первых двух переменных нет — то есть хранилище оказывалось **в рабочем каталоге
процесса** (`C:\Program Files\CitadelPQVPN` для установленного приложения). Следствия, которые
пришли как три отдельные жалобы:
- создание хранилища падало с «Отказано в доступе» — обычному пользователю в Program Files не писать;
- смена пароля «не работала при верном пароле»: ЧТЕНИЕ из Program Files разрешено, запись — нет,
  и отказ записи приходил в UI как «текущий пароль неверен»;
- обычный запуск и «от имени администратора» (другой рабочий каталог, а при вводе чужой
  учётной записи — и другой профиль) могли видеть РАЗНЫЕ хранилища.

Старое расположение вычисляется тем же правилом и, если новое ещё пустое, переносится целиком при
первом запуске (копия + удаление оригинала; не удалилось — предупреждение в журнал, работаем с
нового места). Путь виден в настройках приложения и копируется одним тапом — он нужен и для
проверки прав на папку, и в поддержке.

### 16.5 Выход из приложения (2026-07-30)

`windowManager.destroy()` на Windows — это `PostQuitMessage`, а не снос окна: цикл сообщений
выходит, и дальше рантайм разбирает движок Flutter, плагины и COM. В шаблоне Flutter окно живёт до
конца `wWinMain`, то есть разбирается уже **после `::CoUninitialize()`** и при живых нативных
потоках (захват stderr, воркеры движка, tokio) — класс «падений на штатном выходе» с окном WER.
Сделано двумя ходами: окно runner'а помещено в свою область видимости (деструктор до
`CoUninitialize`), а выход из приложения завершает процесс детерминированно (`desktop_exit_now`).
Это безопасно ровно потому, что к этому моменту всё состояние уже на диске: vault пишется атомарно
на каждую операцию, kill-switch снят `disconnect`'ом, служба уведомлена `TAG_QUIT`, иконка трея
удалена (иначе осталась бы «призраком» до наведения мыши).

### 16.6 Хранилище v4: мастер-ключ в слотах и вход по отпечатку (C9, 2026-08-13)

**Что изменилось в формате.** До v3 ключ файла выводился прямо из мастер-пароля
(`Argon2id(passphrase, salt) → AES-256-GCM`). Второго способа открыть хранилище в такой схеме нет
by-construction: любой альтернативный вход обязан знать пароль. С v4 данные шифрует случайный
мастер-ключ `MK`, а сам `MK` лежит в файле столько раз, сколькими способами хранилище разрешено
открыть (схема key slots, как у LUKS/FileVault):

```text
"CPQV" | ver=4 | m_kib | t | p | salt(16) | nonce(12) | slots_len(u16) | slots(CBOR) | AES-256-GCM(payload)
        └──────────────── всё это входит в AAD полезной нагрузки ────────────────┘
слот password: nonce‖AES-256-GCM(MK) под ключом Argon2id(пароль, salt, m/t/p)
слот platform: непрозрачный блоб ОС (Android Keystore), развернуть умеет только это устройство
```

Следствия, ради которых схема и менялась:
- **смена пароля не отзывает биометрию** — переворачивается только слот пароля, `MK` тот же;
- **апгрейд Argon2-параметров** (он делается на лету при открытии) тоже не трогает `MK`;
- **таблица слотов в AAD** — вычеркнуть слот пароля или пересадить слоты из чужого файла нельзя:
  тег полезной нагрузки перестаёт сходиться (тест `slot_table_is_bound_to_payload`);
- границы `slots_len`/числа слотов проверяются ДО криптографии — та же логика, что у
  Argon2-параметров в L-2 (подложенный файл не должен диктовать нам аллокацию).

v1/v2/v3 читаются и прозрачно мигрируют на v4 при первом открытии (как раньше v1→v2→v3); обратной
совместимости нет — старый клиент v4 не прочитает.

**Платформенная половина (Android).** `app/android/.../BiometricVault.kt`, канал
`citadel/biometric`; Dart-обёртка `app/lib/biometric.dart`. Ключ обёртки — `AndroidKeyStore`
AES-256-GCM с `setUserAuthenticationRequired(true)`, `setInvalidatedByBiometricEnrollment(true)`
(24+), `setUnlockedDeviceRequired(true)` (28+), auth-per-use (`setUserAuthenticationParameters(0,
AUTH_BIOMETRIC_STRONG)` на 30+, `…ValidityDurationSeconds(-1)` на 23–29), StrongBox при наличии.
`MainActivity` из-за требований `androidx.biometric` наследует `FlutterFragmentActivity`.

Три решения, которые здесь важнее кода:
1. **`BiometricPrompt` только с `CryptoObject`.** Вариант «спросить у ОС да/нет и открыть
   сохранённым паролем» даёт булево значение в памяти приложения — на рутованном устройстве оно
   подделывается хуком. Здесь расшифровку делает сам TEE и только после аутентификации.
2. **Только `BIOMETRIC_STRONG`, без `DEVICE_CREDENTIAL`.** Системный PIN знают все, кто видел
   разблокировку телефона; резервный путь к хранилищу должен быть один и честный — мастер-пароль.
3. **По умолчанию выключено, включает пользователь.** Биометрия меняет модель угроз: палец
   прикладывают под принуждением (досмотр), пароль остаётся в голове. Поэтому это опция, а не
   умолчание, и выключение мгновенно (слот из файла + ключ из Keystore).

**Транзит `MK` через канал и его затирание (2026-08-14).** Мастер-ключ пересекает границу дважды
(ядро → Keystore при включении, Keystore → ядро при входе), и каждая половина затирает свою копию:
Kotlin — `plain.fill(0)` сразу после `result.success` (кодирование ответа синхронно, поэтому это
безопасно), Dart — `BiometricUnlock.zeroize`. Затереть НЕЛЬЗЯ ровно одну копию: ответ канала
приезжает неизменяемым окном в буфер движка (`platform_dispatcher.dart`,
`_wrapUnmodifiableByteData`), запись в него запрещена — `fillRange` бросает `Unsupported operation:
Cannot modify an unmodifiable list`. Поэтому обёртка отдаёт наверх свою копию, её и затирает, а
транспортная живёт до сборки мусора. Попытка затирать буфер движка на месте роняла вход по
отпечатку **уже после** успешного открытия хранилища: ядро оставалось разблокированным, а человек
видел на экране входа системную ошибку (регрессия закрыта `app/test/biometric_test.dart`; там же
мок повторяет неизменяемость транспорта — обычный мок канала её не воспроизводит). Отсюда же
правило: неудача уборки не имеет права ронять разблокировку.

Остаточный риск, зафиксированный осознанно: выключение биометрии НЕ меняет `MK` (для этого нужен
пароль, а хранилище могли открыть тем же отпечатком). Старая копия `vault.bin` плюс живой ключ в
Keystore теоретически дают вход — закрыто тем, что ключ удаляется вместе со слотом; полное лечение
для утёкших резервных копий — смена пароля. Windows Hello / macOS Touch ID подключаются тем же
слотом `platform`, платформенная половина для них пока не написана, и настройка там не показывается.

## 17.3 Маскировка и батарея: что именно жгло заряд (2026-08-14)

Разбор и числа — в `docs/COVER-TRAFFIC-BATTERY-2026-08.md`; здесь — итог для тех, кто читает
архитектуру клиента.

Постоянный исходящий трафик давали **два независимых механизма**, и настройка «маскировка»
управляла только вторым:

| | было | стало |
|---|---|---|
| Собственный keep-alive | 2–4 с всегда (≈30 МБ/сут вместе с ACK'ами), модем не уходил в idle никогда | 15–28 с, если exit подтвердил длинный idle-таймаут; на exit'е маячка нет вовсе |
| Chaff при включённой маскировке | ~2.2 ГБ/сут **в простое** | 0 в простое; на всплеск — затухающий хвост ~11 пакетов, с байтовым бюджетом |
| Пробуждения pacer'а | 200/с всегда | 0 в простое |

Три решения, которые стоит помнить при правках:

1. **Окно chaff взводит только пользовательский трафик** (`dataplane::user_packets` — счётчик
   inner-датаграмм в обе стороны). Раньше в этой роли выступала любая выпущенная датаграмма,
   включая собственный маячок: простаивающий туннель сам себе открывал окно и маскировал ничто.
   Если однажды понадобится «взводить» окно чем-то ещё — это ровно то место, где ошибка стоит
   гигабайтов и не видна ни в одном тесте, кроме `keepalive_does_not_trigger_chaff`.
2. **Редкий маячок разрешает ПИР, а не мы.** Эффективный `max_idle_timeout` равен минимуму из
   объявленных сторонами, а quinn наружу его не отдаёт — поэтому exit называет своё значение
   хвостом капсулы `ADDRESS_ASSIGN` (`decode_idle_hint`), и только увидев ≥60 с клиент переходит
   на 15–28 с. Со старым exit'ом (15 с) остаётся прежние 2–4 с, иначе туннель рвался бы в простое.
   Верхняя граница держится ниже 30 с — типового UDP-таймаута CGNAT.
3. **Маскировка имеет цену, и цена названа.** Профили `off`/`lite`/`on` (32 и 128 КиБ/мин бюджета
   chaff) вместо булева тумблера; в режиме энергосбережения Android строгий понижается до
   экономного, но выключенная маскировка сама не включается никогда.
